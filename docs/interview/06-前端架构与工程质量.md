## 主题：技术栈与选型理由

### ① 一句话答案

React 18 + TS + Vite 5 打底，Tailwind 4 做样式，Zustand 管状态，Axios 管请求，Radix UI 提供无样式可访问组件，Framer Motion 做动效，ECharts 和 Mermaid 按需加载。

### ② 展开讲 30–60 秒

| 选型 | 理由 | 放弃了什么 |
| --- | --- | --- |
| **React 18 + TS** | 生态最熟；TS 能把接口字段约束在编译期 | 相比 Vue 上手成本略高 |
| **Vite 5** | 开发冷启动和 HMR 快；构建基于 Rollup，分包配置直观 | 相比 webpack 插件生态略窄 |
| **Tailwind CSS 4** | 原子类 + 设计令牌，配合 `DESIGN.md` 统一视觉 | HTML 里类名较长 |
| **Zustand** | 无样板代码、体积小、可以直接在 store 外用 `getState()/setState()` | 没有 Redux DevTools 的时间旅行调试 |
| **Axios** | 拦截器机制适合做统一解包、Token 注入、刷新重试 | 比 `fetch` 体积大 |
| **Radix UI** | 无样式但**自带可访问性**（焦点管理、键盘导航、ARIA） | 要自己写样式 |
| **Framer Motion** | 声明式动画 | 增加一个 chunk 体积 |
| **ECharts / Mermaid / KaTeX** | 图表、流程图、数学公式 | **体积大，必须按需加载** |

**为什么严格用 pnpm**：它在磁盘上用硬链接共享依赖、安装快，而且**对「幽灵依赖」（用了没声明在 package.json 里的包）更严格**，能暴露隐式的依赖问题。项目里锁了 `packageManager: pnpm@9.15.9` 和 `pnpm-lock.yaml`。

### ③ 代码落点

`frontend/package.json`、`frontend/vite.config.ts`、`DESIGN.md`。

### ④ 可能的追问 + 应答

- **Q：为什么不用组件库（Ant Design / MUI）？**
  A：博客前端视觉要自己控，整套引入组件库会带来大量用不到的样式和体积。基于 Radix 自建几个基础组件（Button/Modal/Dropdown/Switch/Tooltip/TextField 等），体积可控而且行为可预测。

- **Q：Zustand 和 Context 的区别？**
  A：Context 是「注入」机制，值一变所有消费者都重渲染；Zustand 是订阅式的，**组件只订阅它用到的字段**，配合选择器可以避免无关重渲染。另外 Zustand 可以在组件外读写（`getState()`），这对请求拦截器很关键——拦截器不在 React 树里。

### ⑤ 诚实边界

- 没有做 SSR/SSG（用 Prerender 给爬虫做预渲染替代），所以首屏是客户端渲染。
- 没有做微前端/模块联邦之类的大规模架构，因为规模不需要。

## 主题：路由与代码分割

### ① 一句话答案

路由集中在一个懒加载映射里，每个页面一个 `React.lazy` 异步 chunk；加载期间显示占位骨架，出错由错误边界兜住，受保护路由按角色判断。

### ② 展开讲 30–60 秒

- **懒加载**：`routes/lazyRoutes.ts` 集中声明页面 → 动态 import 的映射。这样首屏只下载首页需要的代码，管理后台、编辑器、问答页这些重页面在访问时才加载。
- **占位**：`RoutePending` 提供加载态；配合 `Skeleton` 相关组件避免布局跳动。
- **错误边界**：`ErrorBoundary` 捕获渲染期异常，展示友好错误而不是白屏。
- **受保护路由**：`ProtectedRoute` 按当前用户角色判断是否放行，不满足就跳登录或提示无权限。
- **滚动恢复**：`ScrollRestoration` 处理前进/后退时的滚动位置，这是 SPA 常见体验细节。

### ③ 代码落点

`frontend/src/routes/lazyRoutes.ts`、`frontend/src/App.tsx`、`frontend/src/components/ProtectedRoute.tsx`、`RoutePending.tsx`、`ErrorBoundary.tsx`、`ScrollRestoration.tsx`。

### ④ 可能的追问 + 应答

- **Q：前端路由守卫能替代后端鉴权吗？**
  A：**不能**。前端守卫只保证「用户看不到不该看的界面」，任何人打开 DevTools 或直接调接口都能绕过。所以真正的权限在服务端（路由层 + Logic 层双重校验）。前端守卫是体验，不是安全。

- **Q：懒加载会不会导致跳转时白屏？**
  A：会有一小段加载时间，所以配了 `RoutePending` 占位。更好的做法是**预加载**（比如鼠标悬停时预取 chunk），项目里有 `PreloadLink` 组件做这类优化。

### ⑤ 诚实边界

- 没有做「按需预取全部可能的下一跳」的智能预加载；预加载是显式使用 `PreloadLink` 的地方。

## 主题：状态管理分层与 Policy 纯函数

### ① 一句话答案

按职责拆几个 Zustand store（认证、界面、偏好、站点设置），并把**判断逻辑抽成纯函数 `*Policy.ts`**，让它们能被单元测试直接调用、不依赖浏览器。

### ② 展开讲 30–60 秒

**store 划分**：

| store | 管什么 |
| --- | --- |
| `auth` | Access Token、当前用户、是否已初始化、会话失效回调 |
| `ui` | 全局 loading 计数、toast 等界面状态 |
| `preferences` | 主题、语言等用户偏好（持久化） |
| `siteSettings` | 站点设置（站点名、导航可见性、功能开关） |

**Policy 纯函数是这个项目里我比较满意的一点**：把「判断」从「状态容器」里拿出来，写成不依赖 React、不依赖 DOM 的纯函数。例如：

- `authPolicy.ts`：给定用户角色和状态，判断能不能进入某个区域、要不要触发登出；
- `siteSettingsPolicy.ts`：给定站点设置，判断某个导航项/入口是否显示；
- `logoutPolicy.ts`：判断注销响应该怎么处理。

好处很直接：**这些函数可以在 Node 里直接测**（`frontend/tests/*.test.ts` 用的就是 `node --experimental-strip-types --test`），不需要 jsdom、不需要渲染组件、不需要 mock 网络。这让「策略是否覆盖了所有边界」变得可回归。

### ③ 代码落点

- store：`frontend/src/store/auth.ts`、`ui.ts`、`preferences.ts`、`siteSettings.ts`
- Policy：`frontend/src/store/authPolicy.ts`、`siteSettingsPolicy.ts`、`logoutPolicy.ts`
- 对应的测试：`frontend/tests/authPolicy.test.ts`、`siteSettingsPolicy.test.ts`、`logoutDraftPolicy.test.ts`
- 测试运行方式：`frontend/package.json` 的 `test` 脚本

### ④ 可能的追问 + 应答

- **Q：为什么把逻辑从组件里抽出来？**
  A：因为写在组件里的判断**只能通过渲染组件来测**，成本高、还容易测成「测实现细节」。抽成纯函数后，输入输出明确，测试变成一次函数调用 + 一个断言。

- **Q：Policy 和 store 的分工边界是什么？**
  A：store 只管「存什么、改什么」；Policy 管「给定状态应该得出什么结论」。所以 Policy 是纯函数，不 import store。

- **Q：那 `logoutPolicy` 这类业务逻辑放前端合适吗？**
  A：它只是**展示层的处理决策**（比如注销失败时该不该清本地状态），不是权限判断。真正的安全判断仍在后端。

### ⑤ 诚实边界

- Policy 只覆盖了一部分判断，不是所有逻辑都抽出来了。
- 没有做 store 的持久化版本迁移策略（改了持久化结构可能读到旧数据）——这在实际使用中需要留意。

## 主题：网络层（1）—— 统一响应与分级超时

### ① 一句话答案

一个 Axios 实例：`baseURL = /api/v1`、`withCredentials: true`；请求拦截器注入 Token、访客 ID 和**分级超时**；响应拦截器统一解包、失败转成 `AppError`。

### ② 展开讲 30–60 秒

**为什么用相对路径 `/api/v1`**：因为开发时 Vite 代理 `/api` 到 `http://127.0.0.1:19000`，生产时 Nginx 反代 `/api`，**前端代码在两种环境下不用改**。

**`withCredentials: true`**：因为 Refresh Token 在 HttpOnly Cookie 里，跨源请求必须带凭证。

**请求拦截器做三件事**：

1. 从 `auth` store 取 Access Token，注入 `Authorization: Bearer <token>`；
2. 注入持久化的 `X-Visitor-Id`（用于点赞去重，防止换 UA 刷赞）；
3. **分级超时**：不在实例上写死 `timeout`，而是在拦截器里按 method/路径注入。注释解释了原因——后端 `Timeout` 是 610 秒，写操作链路（MySQL/Redis/MQ）抖动时容易出现「前端超时但服务端其实已经写入」；所以给写请求更宽裕的窗口，导入导出这类长任务保留 600 秒，AI 供应商请求则由后台设置和服务端上限控制。

**响应拦截器**：

- 先处理 `blob`（下载类响应直接返回原始响应对象）；
- 然后判断是不是统一成功响应（`isSuccessResponse`），**成功就把 `data` 直接返回**，页面不用再剥壳；
- 失败则 reject 一个带 `code` 的 `AppError`；
- 同时把 loading 计数减掉（和请求拦截器的加一配对）。

### ③ 代码落点

`frontend/src/utils/http.ts:19`（实例配置）、`:94`（请求拦截器）、`:106`（分级超时注入）、`:112`（响应拦截器）、`:119`（成功解包）、`:123`（失败转 AppError）、`frontend/src/utils/timeoutPolicy.ts`、`frontend/src/utils/response.ts`。

### ④ 可能的追问 + 应答

- **Q：为什么成功时返回 `data` 而不是整个 `AxiosResponse`？**
  A：因为调用方只关心业务数据。这是**在拦截器里做的一次约定**，代价是类型上要做一次断言（代码注释里也说明了这点）。好处是所有 API 方法的返回类型都很干净。

- **Q：分级超时具体怎么分？**
  A：按 method 和路径决定：GET 较短、写操作较长、导入导出 600 秒、AI 请求交给服务端控制。具体数值以 `timeoutPolicy.ts` 为准，**不要背数字**。

### ⑤ 诚实边界

- 成功响应的类型断言（`as unknown as AxiosResponse`）是一个**类型上的妥协**：TS 看到的类型和运行时实际返回不一致。严格来说应该用泛型封装函数而不是改拦截器返回类型。这是已知的技术债。

## 主题：网络层（2）—— 401 刷新「单飞」

### ① 一句话答案

用一个**模块级的 Promise 变量**做单飞：第一个 401 触发刷新并把这个 Promise 存起来，其他并发 401 直接复用同一个 Promise，**最多只刷新一次**；还额外处理了「令牌轮换竞态」。

### ② 展开讲 30–60 秒

**为什么需要单飞**：一个页面可能同时发好几个请求（比如详情页同时取文章、分类、相关文章）。Access Token 一过期，这几个请求会**同时收到 401**。如果不做处理，就会同时发起多个 `/auth/refresh`。

而我的后端 refresh 是**会轮换令牌的**（每次刷新都撤销旧 Refresh Token 并签发新的）。多个并发刷新会导致：第一个成功轮换了令牌，后面几个拿着**已经被撤销的旧 Cookie** 去刷新，全部失败 → 前端误判为会话失效 → **用户被莫名其妙登出**。

**单飞的实现**：

```ts
let refreshTokenTask: Promise<string> | null = null;
const getRefreshTokenTask = () => {
  if (!refreshTokenTask) {
    refreshTokenTask = refreshAccessTokenInStore().finally(() => { refreshTokenTask = null; });
  }
  return refreshTokenTask;
};
```

关键点是 `.finally()` 里把变量清空，这样**刷新完成后新的 401 还能再次触发刷新**（否则第一次之后就永久失效了）。

**令牌轮换竞态修复**：在触发刷新之前，先比较「这个失败请求当时用的 Token」和「store 里当前最新的 Token」：

- 如果**不一致**，说明**已经被另一个并发 401 触发过刷新并且成功了**，此时不需要再刷新，直接把请求头换成最新 Token 重发即可。
- 如果一致，才真正去调用刷新任务。

这段逻辑是代码注释里明确写出来的（「旋转竞态修复」），它避免了「用旧 token 刷新失败导致强制登出」。

**会话失效只处理一次**：`sessionExpiredHandled` 标志保证「清 store + 提示 + 回调」这套动作只执行一次，不会因为多个并发失败弹出一堆 toast。而且这个标志在认证状态变化事件（`noa:auth-changed`）时会被重置。

### ③ 代码落点

`frontend/src/utils/http.ts:32`（单飞变量）、`:35`（失效只处理一次）、`:39`（事件重置标志）、`:43`（认证类接口不触发刷新）、`:67`（刷新并同步 store）、`:74`（单飞函数）、`:83`（会话失效处理）、`:146`（401 分支）、`:153`（竞态修复注释与逻辑）、`:163`（复用刷新任务）。

### ④ 可能的追问 + 应答

- **Q：为什么登录/注册/刷新/注销这几个接口不参与自动刷新？**
  A：因为它们本身就是认证接口，对它们做 401 刷新会形成**递归**。特别是**注销**：如果注销失败还去刷新，而刷新又失败，前端会把会话清掉并跳转，用户以为注销成功了，但服务端 Refresh Token 可能还在。所以这四类路径直接 reject。

- **Q：如果刷新接口也返回 401 呢？**
  A：刷新本身失败 → 走 `handleSessionExpired`：清 store、按错误给提示、调用 `onSessionExpired` 回调（通常是跳登录）。**并且只做一次。**

- **Q：怎么区分「密码错误」和「Token 过期」？**
  A：改密码接口会返回 401（当前密码错误），这**不能触发刷新**——否则会白白刷一次 Token 然后还是失败。所以有个 `isCurrentPasswordRejection` 判断专门把它排除掉。

### ⑤ 诚实边界

- **S02 是这条链路上的已知问题**：刷新异常分支**没有区分网络错误、5xx 和凭据失效**，三种情况都调用了会话失效处理；而 `logout()` 会删除当前用户的全部本地草稿。也就是说**刷新时网络抖动可能导致未保存草稿丢失**。正确做法是区分「暂时不可用」与「认证失效」，并把会话清理与草稿删除解耦。审查报告记录为静态风险，**未在线复现**。

## 主题：网络层（3）—— 写请求去重与幂等重试

### ① 一句话答案

在 **Axios adapter 层**对写请求做 in-flight 去重：同一 method + URI + payload + Authorization 的请求若已在飞行，后续调用复用同一个 Promise，不会真的发第二个请求；另外对**幂等 GET** 的网络错误自动重试一次。

### ② 展开讲 30–60 秒

**要解决的问题**：链路抖动时用户容易重复点击「保存」，导致重复提交。常见做法是在按钮上加 loading 禁用，但那要改每个页面；这里做在**网络层**，调用方完全无感。

**为什么在 adapter 层而不是拦截器层**：拦截器每次调用都会执行（各自维护自己的 loading 计数），而 adapter 才是**真正发出网络请求**的地方。在 adapter 层复用 Promise 才能做到「只发一个请求」，同时每个调用方的拦截器语义保持不变。

**去重的 key** 是 `[method, 完整URI, 稳定序列化的body, Authorization]`。其中 body 用 `stableStringify`（键排序）序列化，避免对象键顺序不同导致本该去重的请求被当成不同请求。

**排除规则**（这些情况不去重，避免误伤）：

- GET（本来就是幂等读）；
- `blob` 响应、`FormData`（上传，可能有进度语义）；
- 带 `signal` 的请求（调用方明确要管生命周期，比如搜索的取消）；
- `/ai/` 路径（AI 请求本来就是长耗时且用户可能想重试）；
- **重试请求**（`_retry` / `_networkRetry`）——因为重试时 Authorization 已经换了，复用原 Promise 会让重试失效；
- 通过 `localStorage` 设置 `NOA_DEDUPE=off` 可以整体关闭（便于调试）。

**幂等重试**：只有 GET、非 blob、非 AI 路径的网络错误（`ECONNABORTED` / `ERR_NETWORK`）才重试一次，**写操作绝不自动重试**（避免重复提交真实产生副作用）。重试前打 `_networkRetry` 标记防止无限循环。

### ③ 代码落点

`frontend/src/utils/http.ts:54`（重试条件）、`:176`（网络错误重试）、`:189`（去重的设计注释）、`:194`（in-flight Map）、`:196`（稳定序列化）、`:205`（可关闭开关）、`:230`（key 构造与排除规则）、`:262`（adapter 包装）、`:275`（结束清理）。

### ④ 可能的追问 + 应答

- **Q：为什么写请求不重试？**
  A：因为**无法确认上一次是否已经生效**。网络错误可能发生在「服务端已写入但响应没回来」的时刻，重试就会产生两条记录。要安全重试必须引入**幂等键**（客户端生成一个 request id，服务端去重）——这是我知道但目前没做的正确解法。

- **Q：去重会不会导致用户想改两次却只生效一次？**
  A：不会，因为 key 包含 payload。**内容不同就是不同的 key**。只有完全相同的重复提交才会被合并。

- **Q：两个不同组件同时提交相同内容会被合并吗？**
  A：会。这是有意行为（防止重复提交），但理论上可能是两个不同意图。保守的做法是把 key 里加上调用来源标识，我目前没有这么做。

### ⑤ 诚实边界

- 写请求**没有幂等键**，所以网络错误后不能安全重试。
- 去重是按「完全相同请求」判定的，理论上会合并两个不同来源的相同意图。

## 主题：错误处理与文案映射

### ① 一句话答案

所有失败统一转成 `AppError`（带 `code`），由 `utils/error.ts` 把错误码/状态码映射成中文文案，AI 相关错误另有专门文案表，统一走 toast 提示。

### ② 展开讲 30–60 秒

分层设计：

- **`AppError`**：统一的错误对象，带业务 `code` 和 `ERROR_KEYS`（稳定的机器可读键）；
- **`toAppError`**：把 Axios 的错误（网络错误、超时、HTTP 状态、业务失败）归一成 `AppError`；
- **`error.ts` 的映射表**：把 `ERROR_KEYS` / 状态码翻译成用户能看懂的中文；
- **`aiErrorMessages.ts`**：AI 场景有专门的文案（比如「模型未配置」「请求过于频繁」「上游不可用」），因为用户需要知道「是我配错了还是服务挂了」；
- **`notifyFromError` / `Toaster`**：统一弹提示。

**为什么后端返回英文 `message`**：让后端保持机器可读的稳定标识，前端负责本地化。这样改文案不用改后端，将来做多语言也天然支持（项目本身就有中英双语 i18n）。

**一个细节**：错误响应可能是 `blob`（比如下载接口失败时返回 JSON 但 `responseType` 是 blob），所以有个 `parseJSONBlobError` 把它解析回来再映射。

### ③ 代码落点

`frontend/src/utils/error.ts`、`frontend/src/utils/aiErrorMessages.ts`、`frontend/src/utils/notify.ts`、`frontend/src/components/Toaster.tsx`、`frontend/src/components/InlineNotice.tsx`。

### ④ 可能的追问 + 应答

- **Q：为什么要维护一个映射表而不是直接用后端 message？**
  A：三个理由：后端 message 是给开发看的、不适合直接展示；文案调整不需要动后端；多语言支持。代价是要维护一份映射，新增错误码时容易漏——这是需要注意的地方。

- **Q：用户看到错误后应该能做什么？**
  A：可恢复的错误（限流、网络）提示重试；不可恢复的（权限、配置错误）引导到具体设置页。我在 AI 设置页专门做了「错误原因 + 去哪修」的引导。

### ⑤ 诚实边界

- 映射表需要和新错误码同步维护，**没有编译期校验**（后端加了新 code，前端不会报错，只会走兜底文案）。

## 主题：Markdown 渲染管线

### ① 一句话答案

`react-markdown` + `remark-gfm`（表格、任务列表）+ `remark-math`/`rehype-katex`（公式）+ 自定义组件处理代码高亮、Mermaid 图和图片灯箱；**重依赖全部按需加载**。

### ② 展开讲 30–60 秒

- **GFM**：`remark-gfm` 提供表格、删除线、任务列表。
- **数学公式**：`remark-math` + `rehype-katex`。**KaTeX 单独拆成一个 chunk，只在文章内容真的含公式时才加载**（由 `DeferredMarkdownRenderer` 判断）。
- **代码高亮**：`react-syntax-highlighter`，但**语言语法是动态 import 的**——用到哪种语言才加载哪种语法的定义。未知语言或加载失败会**降级为普通代码块**，不会白屏。代码块还有工具栏（复制等）。
- **Mermaid**：作为**组件级的动态 import**，只有文章里有 ```mermaid 代码块才加载渲染器；渲染用 `securityLevel: 'strict'`（防止图表里的脚本被执行）。
- **安全**：Markdown **没有把原始 HTML 直接注入页面**的路径（审查报告复核确认过），组件里的 DOM 写入仅用于处理 Mermaid 自身生成的 SVG。
- **图片灯箱**：`ImageLightbox` 提供点击放大的阅读体验。

### ③ 代码落点

`frontend/src/components/MarkdownRenderer.tsx`、`MarkdownRendererWithMath.tsx`、`DeferredMarkdownRenderer.tsx`、`MarkdownCode.tsx`、`MarkdownCodeBlock.tsx`、`MarkdownCodeToolbar.tsx`、`MarkdownTable.tsx`、`MermaidCodeBlock.tsx`、`ImageLightbox.tsx`、`frontend/src/utils/markdownCodeLanguage.ts`、`markdownMath.ts`、`mermaidRender.ts`。

### ④ 可能的追问 + 应答

- **Q：Mermaid 为什么用 `securityLevel: 'strict'`？**
  A：因为 Mermaid 支持在图表里嵌入可点击链接和 HTML，如果放开，别人写的文章就可能塞进脚本或诱导性链接。严格模式会限制这些能力。**这是「把用户内容当不可信输入」的体现。**

- **Q：代码高亮按需加载会不会有闪烁？**
  A：语言定义加载完之前会先渲染成普通代码块，加载完成后切到高亮。这是可接受的取舍——总比为了高亮把几十种语法全打进首屏好。

- **Q：为什么不支持原始 HTML？**
  A：安全。允许原始 HTML 就等于把 XSS 的入口打开。所以**故意不支持**。

### ⑤ 诚实边界

- Mermaid 的 chunk 体积仍然较大（预算上限 raw 700 KiB），虽然已经从早期约 3 MB 的单体降下来了，但在移动端/弱网下仍有加载成本。
- 没有做「渲染结果缓存」。

## 主题：性能工程与包体积预算

### ① 一句话答案

三招：**路由级懒加载**、**重依赖组件级动态 import**、**构建期分包 + 自动化体积预算检查**；而且会**断言重资源 chunk 不能出现在 index.html 里**。

### ② 展开讲 30–60 秒

**分包策略**（`vite.config.ts` 的 `manualChunks`）把依赖按组拆开：`react`、`motion`、`markdown`、`katex`、`syntax-highlighter`、`echarts`。特别地，**代码高亮的语言语法文件被排除在分包之外**，因为它们是由动态 import 按需加载的，不能并进基础高亮 chunk（否则一加载高亮就把所有语言拖下来）。

**体积预算脚本**（`check-bundle-size.mjs`）对**每个 chunk 同时测 raw / gzip / brotli 三种体积**并设上限。真实门槛值：

| chunk | raw | gzip | brotli |
| --- | --- | --- | --- |
| 初始 JavaScript（入口） | 320 KiB | 110 KiB | 96 KiB |
| markdown | 185 KiB | 56 KiB | 48 KiB |
| katex | 310 KiB | 96 KiB | 80 KiB |
| mermaid 渲染器 | 700 KiB | 220 KiB | 180 KiB |
| syntax-highlighter | 64 KiB | 24 KiB | 20 KiB |
| echarts | 550 KiB | 185 KiB | 155 KiB |

**最关键的一条断言**：脚本会读 `dist/index.html`，检查 `markdown`/`katex`/`mermaid`/`syntax-highlighter`/`echarts` 这几个 chunk **是否被 index.html 直接引用**——如果是，直接判定失败。这条断言把「按需加载」从「口头承诺」变成了「构建期强制」，**防止以后有人不小心改 import 方式把它们变成首屏依赖**。

**构建流水线**：`pnpm build` = `lint` → `type-check` → `vite build` → `check:bundle-size`，任何一步失败整体失败。

### ③ 代码落点

`frontend/vite.config.ts:5`（分包组）、`:16`（语言路径排除）、`:26`（大 chunk 警告阈值 550 KB）、`frontend/scripts/check-bundle-size.mjs:49`（各 chunk 预算）、`:91`（index.html 断言）、`frontend/package.json`（build 脚本）、`docs/TESTING.md`。

### ④ 可能的追问 + 应答

- **Q：Vite 的大 chunk warning 要不要管？**
  A：它是**提示不是失败**。我的态度是：把它当作 review 信号——如果新增依赖导致某个 chunk 明显变大，就要评估是否该按需加载。而且我做了比 warning 更硬的东西：**自定义的体积预算会在超过上限时让构建失败**。

- **Q：为什么同时测 gzip 和 brotli？**
  A：因为服务器可能按 `Accept-Encoding` 返回不同压缩。brotli 通常比 gzip 小 15–20%，是现代浏览器的首选。只看 raw 会高估传输体积，只看一种压缩又不够。

- **Q：首屏体积到底是多少？**
  答：审查报告实测入口约 311.38 KiB（gzip 更高），并且指出**当时的预算只覆盖了入口文件，而 HTML 直接引用的入口 + React + Motion 三个脚本合计 563,332 字节（gzip 合计 186,015 字节）**。也就是说**我的预算口径当时偏乐观**，这是 O02 记录的问题。

### ⑤ 诚实边界

- **O02 未修复**：预算只检查入口 chunk，没有把 HTML 里直接引用/预加载的所有初始脚本一并纳入。正确的做法是把「初始资源总和」作为一个指标。
- 没有做真实设备/弱网的加载性能测量。

## 可能被问倒的 3 个问题

1. **「你的前端怎么处理并发请求导致的 Token 刷新问题？」**
   → 应答思路：三层。第一，**单飞**——用一个模块级 Promise 变量保证同一时刻只有一个刷新在进行，其他 401 复用这个 Promise。第二，**令牌轮换竞态修复**——触发刷新前先比较「失败请求用的 Token」和「store 里的最新 Token」，不一致说明已经被别的请求刷新过了，直接换头重发，不再触发新的刷新（否则会用已撤销的旧 Cookie 刷新导致强制登出）。第三，**会话失效只处理一次**——用一个标志位保证「清 store + 提示 + 跳转」不会因为多个并发失败而重复执行。另外登录/注册/刷新/注销这四类路径**不参与自动刷新**，避免递归。

2. **「用户重复点击提交按钮会产生两条数据吗？」**
   → 应答思路：一般不会，因为我在 **Axios adapter 层做了写请求 in-flight 去重**——key 是 `method + 完整 URI + 稳定序列化的 body + Authorization`，完全相同的请求会复用同一个 Promise，不会真的发第二个请求；而且排除规则考虑得比较细（GET、FormData、带 signal 的、AI 路径、重试请求都不去重）。但我要诚实说明两点：**一是我没有做幂等键，所以网络错误之后写请求不能安全重试**（因为无法确认上一次是否已生效）；二是去重按「完全相同的请求」判定，理论上会合并两个不同来源的相同意图。

3. **「首屏为什么能这么小？你怎么保证不反弹？」**
   → 应答思路：三个动作。路由级懒加载把管理后台、编辑器、问答页拆出去；重依赖（KaTeX / Mermaid / ECharts / 代码高亮语言）用**组件级动态 import**，只有用到才加载；构建期用 `manualChunks` 手工分包。**最关键的是我不只靠自觉**——体积预算脚本会对每个 chunk 的 raw/gzip/brotli 三种体积设上限让构建失败，还会读 `dist/index.html` **断言这些重资源 chunk 不能出现在初始引用里**，把「按需加载」变成了构建期的硬约束。诚实说：O02 记录了一个缺口——我当时的预算只覆盖入口 chunk，没有把 HTML 直接引用的全部初始脚本合起来看。
