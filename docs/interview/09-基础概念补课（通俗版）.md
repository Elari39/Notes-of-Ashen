# 09 · 基础概念补课（通俗版）

## A. Web 与 HTTP 基础

### HTTP / HTTPS

**大白话**：浏览器和服务器之间传数据的「语言和信封」。HTTPS 就是给这个信封加了加密和身份验证，别人在路上截到也看不懂、也改不了。
**打个比方**：HTTP 是明信片，谁经手都能看；HTTPS 是上了锁的信封，锁的钥匙只有你和收件人知道。
**项目里用在哪**：生产要求 `APP_REQUIRE_PUBLIC_SITE_URL=true` 时站点地址必须是 HTTPS（`cmd/notes-of-ashen/main.go:66`）；HSTS 由 1Panel 上游 HTTPS 反代注入（`deploy/nginx/security-headers.conf:2`）；Cookie 的 `Secure` 属性由 `APP_AUTH_COOKIE_SECURE` 控制（`.env.example:21`）。
**面试一句话**：HTTPS 在 HTTP 之上加了 TLS，解决传输加密和服务端身份认证。

### HTTP 状态码

**大白话**：服务器用三位数字告诉你「这次请求怎么样了」。1xx 是「还在处理」，2xx 成功，3xx 让你去别的地方，4xx **是你（客户端）的问题**，5xx **是我（服务器）的问题**。
**打个比方**：去餐厅点菜——200 是菜来了；401 是「你还没出示会员卡」；403 是「你是会员但这个包间不给你进」；404 是「菜单上没这道菜」；429 是「你点太快了，缓缓」；503 是「厨房正在整修，暂时不做」。
**项目里用在哪**：401 未认证 / 403 无权限 / 404 功能未开放 / 413 请求体过大 / 429 限流 / 503 服务不可用，见 `internal/errors/errors.go` 与 `internal/logic/rag/rag.go:238`（页面没开返回 404 而不是 403，少泄露信息）。
**面试一句话**：401 是「没认证」，403 是「认证了但没权限」，这两个最容易被搞混。

### REST

**大白话**：一种接口设计风格，核心是**用 URL 表示资源、用 HTTP 方法表示动作**：GET 查、POST 建、PUT 改、DELETE 删。
**打个比方**：像图书馆的规则——书是「资源」，你要么「取」（GET）、要么「还」（PUT）、要么「扔掉」（DELETE），而不是喊一句「帮我处理下那本书」。
**项目里用在哪**：`internal/handler/routes.go` 全部按这个方法约定写，比如 `POST /api/v1/articles` 建文章、`PUT /api/v1/articles/:id` 全量更新、`PATCH /api/v1/articles/:id/status` 只改状态。
**面试一句话**：REST 是用资源 + 方法来组织接口，好处是语义统一、便于缓存和调试。

### 中间件

**大白话**：在请求真正到达业务代码之前（或之后）统一插一段处理逻辑，比如鉴权、限流、打日志。像流水线上的关卡。
**打个比方**：进办公楼要先过门禁（认证）、再登记（日志）、有些楼层还要刷卡（权限），最后才能到工位（业务代码）。
**项目里用在哪**：`internal/handler/routes.go:32` 起的注册顺序：RequestID → 安全访问日志 → 维护模式 → 认证 → 限流/并发。每个中间件都是 `func(http.HandlerFunc) http.HandlerFunc` 的包装。
**面试一句话**：中间件是横切关注点的统一入口，好处是业务代码不用重复写鉴权和限流。

### 反向代理

**大白话**：用户以为自己在跟一个服务器说话，其实是「前台」把请求转给了后面的真服务器。用户看不到后面有几台。
**打个比方**：公司只有一个对外前台电话，打进来后前台根据你要办的事转给不同部门。
**项目里用在哪**：Nginx 把 `/api` 反代到 `http://api:19000`（`deploy/nginx/default.conf:104`），同时自己提供静态前端文件，所以宿主机只暴露一个端口 `127.0.0.1:1270`。
**面试一句话**：反向代理是「服务端对外统一入口」，好处是隐藏内部拓扑、集中做 TLS/限流/缓存。

### CORS

**大白话**：浏览器的安全规则——**默认不允许** A 网站用 JS 去读 B 网站的响应，除非 B 明确说「我允许 A」。
**打个比方**：你邻居家的门对你关着，除非邻居在门口贴了「欢迎你来拿快递」。
**项目里用在哪**：**本项目未使用 CORS 配置**。因为前端和接口同源（前端静态文件与 `/api` 都由同一个 Nginx 提供），同源请求不触发 CORS。
**面试一句话**：CORS 是浏览器的同源策略保护；同源部署就不需要它——这也是我不需要配 CORS 的原因。

### SPA 路由回退

**大白话**：前端路由是「假的」——`/article/123` 这个地址在服务器上并不存在文件。所以服务器要在找不到文件时**统一返回 `index.html`**，让前端 JS 自己解析路径。
**打个比方**：你去商场找「3 楼 5 号店」，但商场其实没有这层楼——前台统一给你一本导览手册，你按手册自己找。
**项目里用在哪**：`deploy/nginx/default.conf:202` 的 `try_files $uri $uri/ /index.html`。注意 `/healthz`、`/livez`、`/rss.xml` 有**独立的 location**，注释说明它们不能落入 SPA fallback。
**面试一句话**：SPA 部署必须配 fallback 到 index.html，否则刷新子路由会 404。

### 静态资源缓存与文件名 hash

**大白话**：Vite 构建出的 JS/CSS 文件名里带一段内容哈希（如 `index-a1b2c3.js`）。内容一变文件名就变，所以可以放心设置「缓存一年且永不校验」。
**打个比方**：书每次改版都换新书名，所以图书馆可以把旧书名的书永远放在架上不用检查是否过时。
**项目里用在哪**：`deploy/nginx/default.conf:97` 对 `.js/.css/...` 设 `expires 1y` + `Cache-Control: public, immutable`；媒体文件同样一年不可变，因为它用 SHA-256 做文件名（`internal/logic/media/media.go:471`）。
**面试一句话**：内容寻址 + 长期缓存是前端性能优化的标配，因为文件名和内容强绑定。

## B. 认证与安全

### JWT（JSON Web Token）

**大白话**：一个自带签名的小纸条，服务器不用查数据库就能确认「这张纸条是我发的、内容没被改过」。里面装着用户 ID、角色这些信息。
**打个比方**：游乐园的手环——上面有防伪标记，工作人员看一眼就知道是真的，不用回办公室查名单。
**项目里用在哪**：`internal/authutil/token.go:18` 定义 Claims（含 `userId`/`role`/`tokenVersion`），`:41` 用 **HS256** 签发，`:56` 解析时限定只接受 HS256（防止算法混淆攻击）。
**面试一句话**：JWT 是无状态的令牌，签名保证不可篡改；缺点是签发后无法直接撤销，所以我要额外加版本号校验。

### Access Token 与 Refresh Token

**大白话**：一个短命、一个长命。短命的用来干活（每次请求都带），长命的只用来换新的短命令牌。
**打个比方**：Access Token 是门禁卡（每天换），Refresh Token 是办卡的凭证（能换门禁卡，平时锁在抽屉里）。
**项目里用在哪**：Access 默认 1800 秒走 `Authorization: Bearer` 头；Refresh 默认 604800 秒走 HttpOnly Cookie（`internal/logic/auth/cookie.go:11`、`.env.example:16`）。刷新接口 `/api/v1/auth/refresh`。
**面试一句话**：拆成两个令牌是为了兼顾安全性（短命降低泄露损失）和体验（不用频繁登录）。

### Cookie 的 HttpOnly / Secure / SameSite

**大白话**：给 Cookie 加的三道锁。`HttpOnly` 让 JS 读不到；`Secure` 只在 HTTPS 下发送；`SameSite` 限制跨站请求能不能带上它。
**打个比方**：`HttpOnly` 是「这个抽屉的钥匙不在你手上」；`Secure` 是「这把钥匙只在保险柜里才有效」；`SameSite` 是「不是你本人来拿，不给」。
**项目里用在哪**：`internal/logic/auth/cookie.go:20` 同时设了 `HttpOnly: true`、`Secure: 配置值`、`SameSite: SameSiteStrictMode`、`Path: "/"`。本地 HTTP 开发必须把 `APP_AUTH_COOKIE_SECURE` 设成 `false`，否则浏览器不保存 Cookie。
**面试一句话**：HttpOnly 防 XSS 偷 Token，SameSite 防 CSRF，Secure 防明文传输。

### bcrypt 与加盐

**大白话**：一种专门用来存密码的哈希算法。它故意算得慢（让暴力破解成本高），而且每次都会加一段随机数据（盐），所以同一个密码两次哈希结果不同。
**打个比方**：把密码丢进一台很慢但每次都会撒不同调料的绞肉机——同样的肉出来两份不一样的肉馅，别人没法靠「对照表」反推。
**项目里用在哪**：`internal/logic/auth/auth.go:109` 用 `bcrypt.DefaultCost`；因为自带盐，所以数据库里**不需要额外的 salt 列**。
**面试一句话**：bcrypt 自带盐且可调成本；它的坑是**只处理前 72 字节**（这是项目里已知的一个校验不一致问题）。

### 图形验证码与邮箱验证码

**大白话**：图形验证码是防机器（识别图片），邮箱验证码是证明「这个邮箱真是你的」。
**打个比方**：图形验证码像小区门口的机器人识别；邮箱验证码像快递送到你家门口，能拿到就说明你住这儿。
**项目里用在哪**：`internal/security/code.go:23`（图形码 5 分钟 TTL，用 `base64Captcha`）、`:21`（邮箱码 5 分钟 TTL）。两者都在 Redis 里按**用途**隔离 key；消费用 **Lua 脚本**保证「比对 + 删除」原子（`:26`）。首个管理员在用户表为空且邮箱服务关闭时可以跳过邮箱验证。
**面试一句话**：验证码存 Redis 并设 TTL；消费必须原子，否则并发下同一个码能被用两次。

### 限流：固定窗口、滑动窗口、令牌桶

**大白话**：限制「一定时间内最多多少次」。固定窗口是按时段切格子计数；滑动窗口看「最近 N 秒」；令牌桶是往桶里匀速放令牌，有令牌才能过。
**打个比方**：固定窗口像「每分钟只能进 5 个人」；令牌桶像自助餐厅每 10 秒发一张餐券，攒着可以一次用几张。
**项目里用在哪**：`internal/middleware/ratelimit.go:60` 的 Lua 脚本是**固定窗口**（`INCR` + 首次 `PEXPIRE`）；RAG 并发用的是 ZSET（`internal/middleware/concurrency.go:60`）。固定窗口的代价是边界处可能放过约 2 倍流量。
**面试一句话**：固定窗口简单省内存但有边界突刺；滑动窗口/令牌桶更精确但更复杂。

### fail-open 与 fail-closed

**大白话**：当依赖（这里是 Redis）挂了，是「先放行」还是「先拒绝」。
**打个比方**：门禁系统坏了——fail-open 是「门自动打开，先让人进」；fail-closed 是「门自动锁死，谁也别进」。
**项目里用在哪**：`internal/middleware/ratelimit.go:29` 的 `failClosed` 字段。登录/注册/发验证码/改密/RAG 是 fail-closed（返回 503）；图形验证码/点赞/流量上报/AI 辅助是 fail-open。
**面试一句话**：安全相关宁可拒绝，体验相关宁可放行——这是分级降级的思路。

### CSRF

**大白话**：攻击者诱导你**在已登录状态下**去访问一个会执行操作的链接（比如「转账」），浏览器会自动带上你的 Cookie，服务器就以为是你在操作。
**打个比方**：别人拿你的工牌去刷门禁——门禁认牌不认人。
**项目里用在哪**：主要靠 Refresh Cookie 的 `SameSite=Strict`（`internal/logic/auth/cookie.go:27`），跨站请求带不上它；再加上 CSP 的 `form-action 'self'`。另外写操作的 Access Token 走 `Authorization` 头，浏览器不会自动带。
**面试一句话**：SameSite Cookie + 非 Cookie 载体的令牌，是防 CSRF 的两条主要路线。

### XSS

**大白话**：攻击者在你的页面里塞进一段 JS，让它在别的用户浏览器里执行，从而偷数据或伪造操作。
**打个比方**：有人在公告栏贴上「请把钥匙交给保安」的假通知，路过的人照做了。
**项目里用在哪**：Access Token 放在前端内存（不是 localStorage）；Refresh Token 在 HttpOnly Cookie 里 JS 读不到；CSP 设了 `script-src 'self'` **禁止内联脚本**（`deploy/nginx/security-headers.conf:10`）；Markdown **故意不支持原始 HTML**；Mermaid 用 `securityLevel: 'strict'`。
**面试一句话**：XSS 的根本解法是「不信任任何用户内容」——不渲染原始 HTML、加 CSP、敏感凭证不放 JS 可读的地方。

### SSRF

**大白话**：攻击者让**你的服务器**去访问他自己访问不到的内部地址（内网服务、云元数据接口），拿服务器当跳板。
**打个比方**：你让前台帮忙去隔壁公司送个文件，结果对方在文件里写「请把这栋楼所有办公室的门都打开」。
**项目里用在哪**：`internal/aiclient/http.go:149` 的 `newPublicDialContext`——每次建连重新解析域名，**任一结果命中受限地址就整体拒绝**，并直接连校验过的 IP；同时 `Proxy: nil`（不继承代理）和禁止重定向（`:54`、`:63`）。
**面试一句话**：防 SSRF 的关键是「校验和连接用同一份解析结果」，否则 DNS rebinding 会绕过。

### 可信代理与 X-Forwarded-For

**大白话**：请求经过代理后，服务器看到的来源 IP 是代理的，真实客户端 IP 被放在 `X-Forwarded-For` 头里。但这个头**是可以伪造的**，所以不能无条件相信。
**打个比方**：信封背面写着「寄件人：张三」，但这行字是寄件人自己写的，只有当你确认这封信是从可信的邮局转来时才能采信。
**项目里用在哪**：`internal/httphelper/helper.go` 的 `Meta` 只在 `RemoteAddr` 命中 `APP_TRUSTED_PROXY_CIDRS` 时才用转发头；Nginx 侧 `set_real_ip_from ${WEB_TRUSTED_PROXY_CIDR}` 且注释要求**禁止配置宽泛公网网段**（`deploy/nginx/default.conf:46`）。这条规则同时保护限流、来源统计和链接生成。
**面试一句话**：先确认「谁在跟我说话」，再决定信不信他转发的信息——否则限流可以被伪造头绕过。

### CSP（内容安全策略）

**大白话**：一个响应头，告诉浏览器「本页面只允许加载哪里的脚本、样式、图片」。即使被注入了恶意 JS，浏览器也会拒绝执行。
**打个比方**：给页面列一张白名单宾客表，不在表上的人一律不准进。
**项目里用在哪**：`deploy/nginx/security-headers.conf:10`：`script-src 'self'`（禁内联脚本）、`style-src 'self' 'unsafe-inline'`（**Mermaid/KaTeX 会注入内联样式，所以这里必须放开**）、`frame-src 'none'`、`object-src 'none'`、`frame-ancestors 'self'`。文件开头写了 Nginx 的 `add_header` 继承陷阱，所以每个自带 `add_header` 的 location 都要重复 include。
**面试一句话**：CSP 是 XSS 的最后一道防线；难点是要和前端框架的内联样式需求做平衡。

## C. 数据库

### 索引与 B+Tree

**大白话**：索引就像书的目录，让你不用一页页翻。MySQL 的索引底层是 B+Tree——一种「矮胖」的多叉平衡树，所以查一条数据只需要几次磁盘 IO。
**打个比方**：查字典。没有目录你得一页页找；有目录（而且还分了笔画/拼音两种）就几步定位。B+Tree 就是那个「层次很少但每层很多分支」的目录结构。
**项目里用在哪**：`deploy/mysql/migrations/000001_initial_schema.sql:54`（文章标题正文全文索引）、`000005`（公开列表排序索引）、`000014`/`000015`/`000018`（多个查询路径的索引）。这些迁移里有专门一批是**为了查询性能补索引**的。
**面试一句话**：B+Tree 的叶子节点连成链表，所以它既支持等值查询，也天然支持范围查询和排序。

### 联合索引与最左前缀

**大白话**：一个索引可以包含多个字段，比如 `(a, b, c)`。查询条件必须从最左字段开始连续匹配才能用上这个索引——只能用在 `a`、`a+b`、`a+b+c`，跳不过 `a`。
**打个比方**：电话簿先按姓排、同姓再按名排。你可以查「所有姓张的」或「姓张且叫三的」，但没法用来查「所有名字叫三的」。
**项目里用在哪**：`deploy/mysql/migrations/000005_add_article_pin_priority.sql:50` 建的 `idx_articles_display_order(status, scheduled_at, is_pinned, display_priority, published_at, id)`——**`status` 放在最左，因为公开列表查询必然带状态条件**。
**面试一句话**：联合索引的字段顺序是按查询模式设计的，不是按表字段顺序；最左前缀决定它能不能被用上。

### 覆盖索引

**大白话**：如果查询需要的字段**全都在索引里**，数据库就不用回表去读数据行了，直接在索引上就能拿到结果。
**打个比方**：你想知道「这本书多少页」，目录上就写了页码，不用真去翻书。
**项目里用在哪**：上面那个 `idx_articles_display_order` 的最后带上 `id`，就是为了让「按排序取 ID」这类查询尽量减少回表。`000014` 的 `article_tags(tag_id, article_id)` 也是典型的「只取两个 ID」的覆盖场景。
**面试一句话**：把查询需要的列补进索引末尾做成覆盖索引，是常见的读性能优化手段。

### 全文索引

**大白话**：专门给「文字内容里搜关键词」用的索引，普通 B+Tree 索引只能做前缀匹配，做不到「正文里包含某个词」。
**打个比方**：普通索引像按书名查书，全文索引像给整本书建了关键词索引表。
**项目里用在哪**：`deploy/mysql/migrations/000001_initial_schema.sql:54` 建了 `FULLTEXT KEY (title, content)`；`000012_add_article_fulltext_index.sql:21` 又加了一个 `ft_articles_title_content`——注意这个迁移**先检查索引是否已存在**（`:11` 查 `INDEX_TYPE = 'FULLTEXT'`），避免重复建。
**面试一句话**：MySQL 全文索引是搜索能力不可用时的降级方案；专业场景还是交给 Meilisearch 这类检索引擎。

### 事务与隔离级别

**大白话**：事务是「一组要么全成功要么全失败的操作」。隔离级别决定并发事务之间能看到对方多少中间状态。
**打个比方**：转账要么两边都记账成功，要么都不记。隔离级别就是你转账时别人能不能看到你账户「钱已扣但还没到账」的中间状态。
**项目里用在哪**：`model/db.go:197` 的 `WithTx` 辅助函数；**`Commit` 失败时也会回滚**，因为此时事务状态未定，不能让业务误以为写入成功。文章保存和 RAG 同步任务入队就在同一个事务里（`model/article.go:139`）。
**面试一句话**：事务边界要和业务边界对齐；项目里我特意把「业务写入 + 异步任务入队」放进同一事务，避免出现「数据写了但任务没入队」。

### 连接池

**大白话**：预先维护一批数据库连接重复使用，避免每次请求都重新建立 TCP + 认证握手（那很慢）。
**打个比方**：餐厅不用每位客人来了才去招一个服务员，而是常备几个服务员轮流接待。
**项目里用在哪**：`model/db.go:29` 配置 `MaxOpenConns` / `MaxIdleConns`，并且设了 `ConnMaxLifetime=1h` 和 **`ConnMaxIdleTime=10m`**——后者是因为云环境的安全组/NAT 常在 5–10 分钟静默断掉空闲 TCP，连接池留着死连接下次就会拿到 `bad connection`。
**面试一句话**：连接池参数是保护数据库的手段（不是越大越好），而且要注意空闲连接被中间设备静默断开的问题。

### N+1 查询

**大白话**：本可以一次查完的数据，被写成了「先查一个列表，再对每条记录各查一次」。100 条记录就是 101 次查询。
**打个比方**：想知道全班 50 人的家长电话，你可以一次拿到名单再统一查，也可以问 50 次——后者就是 N+1。
**项目里用在哪**：`model/article.go:645` 的 `ArticleTagsBatch` 就是「批量查标签再在内存里聚合」，而不是每篇文章查一次标签。
**面试一句话**：N+1 是 ORM 时代最常见的性能坑；解法是批量查询 + 内存分组。

### 数据库迁移

**大白话**：用编号脚本管理数据库结构的变化，保证每个环境的表结构都能按同样顺序演进到同一个状态。
**打个比方**：盖楼的施工图纸按版本编号归档，每栋楼都按同样的顺序施工，不会出现「A 楼有电梯 B 楼没有」。
**项目里用在哪**：`deploy/mysql/migrations/` 下 28 个不可变编号迁移，用 `embed.FS` 内嵌进二进制（`deploy/mysql/migrations/embed.go`）；Compose 里是独立的一次性任务；启动时 `validateState` 检测「数据库已应用了镜像不认识的迁移」。
**面试一句话**：迁移一旦发布就不可修改，只能新增前向迁移——否则环境之间会产生结构差异。

### 软删除与状态字段

**大白话**：不真的删数据，而是标记一个状态（比如 `deleted_at` 或 `status=archived`），查询时过滤掉。
**打个比方**：文件不是撕掉，而是扔进「回收站」文件夹，正常查找看不到但还能恢复。
**项目里用在哪**：文章用**状态字段**而不是软删除标记：`draft`/`published`/`archived`/`scheduled`（`model/article.go:13`），公开可见性由 `IsArticlePubliclyVisible` 统一判断（`:1031`，状态已发布 + 定时发布时间已到）。RAG 的历史消息用的是 `hidden_at` 软隐藏（`deploy/mysql/migrations/000026_add_rag_foundation.sql:64`）——**数据保留、不对外展示、不作为证据**。
**面试一句话**：状态字段比软删除更贴业务（草稿/发布/归档本身就是业务概念），而且便于统一可见性判断。

## D. Redis

### 缓存

**大白话**：把读得多、变得少的数据放在内存里，省掉每次查数据库。核心难点不是「怎么存」，而是「什么时候失效」。
**打个比方**：把常用电话存在手机快捷键里，不用每次翻通讯录；但对方换号了你得记得更新。
**项目里用在哪**：站点设置、文章列表、**认证用户快照**（快照结构只含 `role` 和 `status` 两个字段，见 `internal/middleware/auth.go:35`；TTL 30 秒见 `:40`）。关键设计是**缓存是优化不是依赖**——未命中或 Redis 故障就直查数据库（`:149`），不返回 500。
**面试一句话**：缓存的价值在于挡住热点读；风险在于一致性，所以要用「主动失效 + TTL 兜底」而不是只靠 TTL。

### 过期策略

**大白话**：给 key 设一个存活时间，到点自动删掉，避免内存被垃圾数据占满。
**打个比方**：冰箱里的牛奶贴上保质期，过期自动丢掉。
**项目里用在哪**：限流 key 用 `PEXPIRE` 设置窗口（`internal/middleware/ratelimit.go:63`，**必须和 `INCR` 在同一段 Lua 里原子执行**，否则并发下可能丢掉过期设置导致永久封禁）；验证码 5 分钟；认证缓存 30 秒。
**面试一句话**：设过期时要注意「第一次写入才设」的原子性，否则并发场景会漏设过期时间。

### 原子操作与 Lua 脚本

**大白话**：Redis 是单线程执行命令的，所以一段 Lua 脚本执行期间不会被其他命令插入——天然就是原子的。
**打个比方**：只有一个收银员，你排到柜台他一定把手头这笔结完才叫下一位，不会算到一半跑去算别人的。
**项目里用在哪**：限流（`INCR` + `PEXPIRE` 原子化，`internal/middleware/ratelimit.go:60`）；验证码消费（比对 + 删除，`internal/security/code.go:26`）；并发租约的领取/释放/续租（`internal/middleware/concurrency.go:60`、`:74`、`:87`）。
**面试一句话**：「读-改-写」这类操作必须用 Lua 或 `SET NX` 保证原子，否则并发下会出现竞态。

### 分布式锁与租约（lease）

**大白话**：多个服务实例要抢着做同一件事，需要一把「大家都能看到的锁」。而**租约**是带自动过期的锁——持有者要定期续租，不续就自动失效，防止持有者崩溃后永久死锁。
**打个比方**：会议室登记表。谁登记了谁用（锁）；但登记上写了「30 分钟内必须回来续签，否则视为弃权」（租约）。
**项目里用在哪**：RAG 索引重建租约（`internal/rag/worker.go:113`、`deploy/mysql/migrations/000027_add_rag_rebuild_lease.sql`）、整站恢复租约（`internal/security/restore_lease.go`）、RAG 并发槽位租约（`internal/middleware/concurrency.go`）。**都用「令牌 + 到期时间 + 续租」的模式。**
**面试一句话**：分布式锁必须带过期，否则持有者崩溃就永久死锁；带续租的租约是更稳的形态。

### ZSET 与「活跃数」限制

**大白话**：ZSET 是「带分数排序的集合」。把分数当「到期时间戳」，成员当「每个请求的唯一令牌」，就能实现「数一数现在有几个活跃请求」。
**打个比方**：会议室的签到板，每个人写上自己的名字和预计离开时间。要来的人先擦掉已过期的名字，再看看板上还剩几个名字。
**项目里用在哪**：`internal/middleware/concurrency.go:57` 的注释解释了**为什么不能用简单计数器**——长于 TTL 的旧请求在计数器过期后结束，会错误释放后来请求的槽位。用 ZSET 可以原子清理过期项，而且释放时只删自己的令牌。
**面试一句话**：ZSET 用到期时间做 score，可以原子地实现「带过期的并发槽位」——比计数器安全得多。

### Redis 挂了怎么办

**大白话**：先问「这个用途是安全相关还是体验相关」，再决定拒绝还是放行。
**打个比方**：门禁系统坏了——管金库的门要锁死（fail-closed），管大门的通道可以先放人（fail-open）。
**项目里用在哪**：限流分 fail-closed（登录/注册/验证码/改密/RAG → 503）和 fail-open（图形验证码/点赞/流量上报/AI 辅助 → 放行）；认证缓存故障降级直查数据库（`internal/middleware/auth.go:149`）；RAG 并发控制直接 503 并**主动取消上游流**（`internal/middleware/concurrency.go:124`）。
**面试一句话**：Redis 故障的处理必须按用途分级，不能一刀切全部 500 或者全部放行。

## E. 架构与工程

### 分层架构

**大白话**：把代码按职责分层，上层依赖下层，下层不知道上层。这样改一处不会牵动全身。
**打个比方**：餐厅里服务员（接入层）只管点菜上菜，厨师（业务层）只管做菜，采购（数据层）只管买菜——服务员不用懂配方，厨师不用管客人坐哪。
**项目里用在哪**：`handler` → `logic` → `model` 三层（见 `02` 那一册）。Handler 只做解析/鉴权/转发四件事。
**面试一句话**：分层的价值是「可测试 + 可复用」——业务逻辑抽出来后，单测不需要起 HTTP 服务，后台任务也能复用同一份逻辑。

### 依赖注入

**大白话**：不在代码里自己 `new` 依赖，而是由外部「装配好」再传进来。好处是换实现（比如测试时换假对象）不用改业务代码。
**打个比方**：你不用自己造螺丝刀，工具箱里有什么就用什么；想换电动的也随时能换。
**项目里用在哪**：`internal/svc/servicecontext.go` 的 `NewServiceContext` 一次性装配数据库、Redis、缓存、邮件、搜索、Worker 等，然后通过 `svcCtx` 传给各 logic 函数。认证中间件也通过 `WithUserCache` / `WithTokenCutoff` 注入可选依赖（`internal/middleware/auth.go:49`、`:59`），传 `nil` 就退化成直查数据库。
**面试一句话**：Go 里用显式构造函数传依赖比反射注入更清楚——看一个 `ServiceContext` 就知道服务依赖什么。

### 幂等

**大白话**：同一个操作执行一次和执行多次，结果一样。
**打个比方**：「把灯打开」是幂等的（按十次还是开着）；「往账户加 100 块」不是（按十次就加了一千）。
**项目里用在哪**：GET 天然幂等；`PUT` 全量更新是幂等的；点赞用「访客哈希 + 唯一约束」做到重复点赞不重复计数（`model/article.go:426`）；RAG 向量的 point ID 由 `epoch|articleId|chunkIndex|sourceHash` 生成（`internal/rag/worker.go:718`），所以同一内容重复索引结果一致。
**面试一句话**：设计重试和消息消费时必须先确认操作幂等，否则会出现重复写入。

### 优雅停机

**大白话**：收到停止信号后，先停止接受新请求，把手上正在处理的请求做完，再关闭数据库连接等资源。
**打个比方**：打烊时不再放新客人进来，但会等已经在店里的人吃完，最后才关灯锁门。
**项目里用在哪**：`cmd/notes-of-ashen/main.go:100` 用 `defer` 的 **LIFO** 特性：先注册 `ctx.Close()` 再注册 `server.Stop()`，所以实际先停服务再关连接池。代码注释里写明了原因。
**面试一句话**：注意 `defer` 是后进先出——注册顺序和实际执行顺序是反的。

### 异步消息队列

**大白话**：把「不着急、可以稍后做」的事情丢进队列，让另一个消费者慢慢处理，请求路径不用等。
**打个比方**：餐厅点单后厨慢慢做，服务员不用站在灶台前等。
**项目里用在哪**：操作日志通过 RabbitMQ 投递，exchange `notes-of-ashen.events`、queue `notes-of-ashen.operation_logs`（`etc/notes-of-ashen.yaml:54`）。**RAG 的索引同步没有用 MQ，而是用了 MySQL outbox 表**——因为入队必须和文章写入在同一个事务里。
**面试一句话**：MQ 解耦了生产者和消费者，但**不能保证和数据库写入的原子性**；要原子就得用 outbox 模式。

### 乐观锁与悲观锁

**大白话**：悲观锁是「我先锁住，谁都别动」；乐观锁是「我先改，提交时检查有没有人改过，改过就失败重试」。
**打个比方**：悲观锁是进洗手间先反锁门；乐观锁是大家随便进，出来时发现东西被挪了就重来一遍。
**项目里用在哪**：**没有用行锁（`SELECT ... FOR UPDATE`）**。但用了类似乐观锁的**条件更新**思想：RAG 的状态回写带 `epoch + fingerprint + lease_token` 条件，只有条件成立才更新（`internal/rag/worker.go:406`、`:549`）。这就是 **fencing token** 的思路。
**面试一句话**：乐观锁靠「条件更新 + 影响行数判断」实现，适合冲突少的场景；本项目在索引状态管理上用了带 fence 条件的条件更新。

## F. AI 与 RAG

### LLM 与 token

**大白话**：大语言模型按「token」处理文本——token 是比字更小的单位，一个中文字大约 1–2 个 token。模型有「上下文窗口」限制（最多能看多少 token），所以**塞得越多越贵、还可能塞不下**。
**打个比方**：模型像一个记性有限但很会总结的人，你一次给他看的材料有限，看多了他会忘掉前面。
**项目里用在哪**：AI 辅助各动作的 `max_tokens` 按输出体积配（`internal/aiclient/prompt.go:60`）；RAG 生成上限 1800（`internal/ragclient/dashscope.go:270`）；历史只带 6 条（`internal/logic/rag/rag.go:27`）——**这些都是为了让上下文可控**。
**面试一句话**：token 是成本和窗口的计量单位；工程上要靠裁剪历史、限制证据数量、设 max_tokens 来控制。

### 提示词工程

**大白话**：不是「问个问题」那么简单，而是**把角色、任务、输出格式、约束和示例都写清楚**，让模型稳定产出你要的东西。
**打个比方**：给实习生派活——说「写个总结」他会给你五花八门的东西；说「用 100 字，分三点，不要说没提到的内容」，结果就稳定了。
**项目里用在哪**：`internal/aiclient/prompt.go:5` 每个动作一个 system prompt，包含角色、字段约束、示例 JSON 和「不虚构正文没有的信息」；**解析层还做容错**（`internal/aiclient/parse.go:9`）。
**面试一句话**：提示词工程的核心是「约束 + 示例」，不是玄学；而且输出一定要能在代码里被稳定解析。

### embedding 向量

**大白话**：把一段文字变成一串数字（比如 1024 个浮点数）。语义相近的文字，这两串数字的方向也相近。
**打个比方**：给每段话在地图上标一个坐标——讲同一件事的话会落在同一个区域。
**项目里用在哪**：`internal/ragclient/dashscope.go:131` 调 `/embeddings`，默认模型 `text-embedding-v4`、默认 1024 维（`internal/rag/settings.go:19`）。**必须校验返回维度等于配置值**（`:167`），否则进库就是错的。
**面试一句话**：embedding 是「把语义映射到向量空间」，所以它能做语义检索而不只是关键词匹配。

### 余弦相似度

**大白话**：比较两个向量的**方向**有多接近（不管长度）。值越接近 1 越相似。
**打个比方**：两支箭头指向差不多方向就是相似，一支长一支短不影响判断。
**项目里用在哪**：Qdrant collection 建的时候用 `distance: "Cosine"`（`internal/ragclient/qdrant.go:72`）。
**面试一句话**：文本 embedding 关心方向不关心长度，所以用余弦相似度而不是欧氏距离。

### 向量数据库 / ANN / HNSW

**大白话**：向量库是专门存向量并做「最近邻搜索」的数据库。数据量大时逐个算相似度太慢，所以用 **ANN（近似最近邻）**算法，牺牲一点点准确率换巨大的速度提升；**HNSW** 是最常用的一种——用多层图结构快速跳转。
**打个比方**：在图书馆找「最像这本书的书」，ANN 是先靠分区快速缩小范围再细找，不保证绝对最准但足够快。
**项目里用在哪**：用 **Qdrant** 存向量（`internal/ragclient/qdrant.go`）。**诚实说：创建 collection 时我只指定了维度和距离度量，没有显式配置 HNSW 参数**，用的是 Qdrant 默认索引。
**面试一句话**：ANN/HNSW 是「用一点召回率换速度」的工程折中，是向量检索能规模化的前提。

### chunk 切分与重叠

**大白话**：把长文章切成小段再向量化。切太小信息不全，切太大语义被稀释；相邻段之间留一点重叠，避免一句话正好被切断导致两边都不完整。
**打个比方**：把一本书拆成卡片，每张卡片写一个完整观点；卡片之间故意重复半句话，防止意思断在边上。
**项目里用在哪**：`internal/rag/chunk.go:11` 的 800 rune 上限 + 120 rune 重叠；`:149` 优先按标题和空行切；**每段前面拼上「标题路径」**（`:171`）保证孤立段落仍有上下文；代码块内容不做压缩（`:34`）。
**面试一句话**：切分是 RAG 效果的第一道关卡——按语义边界切、带上下文前缀、留重叠，是实践中最有效的三个手段。

### rerank 重排

**大白话**：先用便宜的向量检索粗筛一批候选，再用一个更精确但更慢的模型给「问题 + 候选」逐对打分排序。
**打个比方**：先海选（向量检索），再面试（重排）——海选看简历关键词，面试才是真正判断合不合适。
**项目里用在哪**：`internal/ragclient/dashscope.go:187` 调 DashScope 原生 Text Rerank（默认模型 `qwen3-vl-rerank`）；`internal/logic/rag/rag.go:316` 对最多 12 个候选重排，取前 6。
**面试一句话**：向量检索是双编码器（快但粗），rerank 是交叉编码器（慢但准），组合起来是标准的漏斗结构。

### RAG vs 微调

**大白话**：RAG 是「**临时查资料再回答**」，微调是「**把知识烤进模型参数里**」。
**打个比方**：RAG 是开卷考试（可以翻书），微调是把这个学生专门培训成某个领域的专家（闭卷也能答）。
**项目里用在哪**：整个 `05` 那一册都在讲 RAG 的实现；项目**没有做微调**。
**面试一句话**：知识频繁更新、要求可溯源就用 RAG；要固定风格或格式才考虑微调。

### 幻觉与缓解

**大白话**：模型一本正经地编造不存在的事实。
**打个比方**：一个不懂装懂的聊天对象，说得特别自信，但细节全是编的。
**项目里用在哪**：三层缓解——系统提示词明确「只能依据证据回答，证据不足要说没有依据」（`internal/logic/rag/rag.go:333`）；检索时**过滤掉已下线或内容变更的文章**（`:300`），保证证据真实；要求标注 `[1][2]` 引用，让用户能回原文核对（`:341`）。
**面试一句话**：缓解幻觉的关键是「给它一个合法的说不知道的出口」+ 让答案可溯源，而不是单纯祈祷模型不说谎。

### SSE 与 WebSocket

**大白话**：SSE 是**服务器单向**往浏览器推数据（基于普通 HTTP）；WebSocket 是**双向**长连接（独立协议）。
**打个比方**：SSE 像收音机广播（只能听），WebSocket 像打电话（能说能听）。
**项目里用在哪**：RAG 问答用 SSE（`internal/handler/rag/rag.go:242`），响应头 `text/event-stream` + `X-Accel-Buffering: no`，Nginx 单独配 location 关掉缓冲和 gzip（`deploy/nginx/default.conf:120`）。
**面试一句话**：只需要服务端推流就用 SSE（能复用 HTTP 生态、实现简单）；需要双向实时通信才上 WebSocket。

### 流式输出

**大白话**：不等模型把整段回答生成完，而是每生成一小段就立刻推给用户。体感上「打字机」一样逐字出现。
**打个比方**：不是等整锅菜做完才上桌，而是做好一道上一道。
**项目里用在哪**：上游 OpenAI 兼容 SSE 每吐一段就回调 `onDelta`（`internal/ragclient/dashscope.go:259`），后端立刻用 `event: delta` 写回浏览器并 `Flush()`；**必须收到 `[DONE]` 才算完整**（`:337`），提前 EOF 会报错，避免把半截回答保存成完整回答。
**面试一句话**：流式显著改善体感延迟，但代价是「中途失败时的一致性处理」变复杂——必须明确什么状态才算完成。

### 上下文窗口与历史裁剪

**大白话**：模型一次能看的文本有限，所以要主动裁剪历史对话和参考资料。
**打个比方**：跟人交接工作，一次只能说有限的几件事，重要的先说。
**项目里用在哪**：历史最多 6 条且**跳过被隐藏的消息**（`internal/logic/rag/rag.go:27`、`:334`）；证据最多 6 段；每条证据片段预览截断到 240 rune（`:647`）。
**面试一句话**：上下文是稀缺资源，裁剪策略要按「对当前问题最有用」来排，而不是简单截断最早的消息。

### 成本控制

**大白话**：AI 调用按 token 和调用次数收费，所以要减少不必要的调用、缩短输入输出。
**打个比方**：打车按里程和时长计费——能走直线就别绕路。
**项目里用在哪**：只索引**公开**文章、向量索引视为可再生数据不备份、embedding 逐条调用（避免顺序错位这种更贵的错误）、RAG 限流 12 次/分 + 同 IP 并发 2、生成 `max_tokens` 1800。
**面试一句话**：成本控制的手段是「减少调用次数 + 缩短输入输出 + 限制并发和频率」，而不是只盯着单价。

## G. Go 语言

### goroutine

**大白话**：Go 的轻量级「线程」，由 Go 运行时调度，创建成本极低，几万个也没问题。
**打个比方**：不是雇一个全职员工做一件事，而是有个任务池，派出去的人很便宜。
**项目里用在哪**：`internal/middleware/concurrency.go:144` 的心跳续租 goroutine；`internal/logic/system/health.go:52` 里 7 项健康检查**并行执行**；限流/缓存的 Lua 调用本身也是并发的。
**面试一句话**：goroutine 很便宜但不是免费的——需要退出条件，否则会泄漏。

### channel

**大白话**：goroutine 之间安全传递数据的管道，也是 goroutine 之间同步的手段。
**打个比方**：传送带——一头放，另一头取，天然不用抢。
**项目里用在哪**：`internal/logic/system/health.go:50` 用一个带缓冲的 channel 收集 7 个并行检查的结果，**并按 `index` 回填到固定位置**，保证返回顺序稳定；`internal/middleware/concurrency.go:139` 用 `stop`/`done` 两个 channel 做心跳的优雅停止。
**面试一句话**：channel 既是通信也是同步；用它收并发结果时要注意超时和关闭，否则会死等。

### context 与取消传播

**大白话**：`context` 用来在调用链上传递「取消信号」和超时。上游取消了，下游的数据库查询和 HTTP 请求都能被及时中断，不会白干活。
**打个比方**：领导说「这个项目不做了」，所有下属立刻停手，而不是继续做完再报告。
**项目里用在哪**：所有限流/缓存/超时调用都用 `context.WithTimeout`；**并发租约丢失时主动 `cancelStream()` 取消下游**，对 SSE 就是立刻中止上游模型请求（`internal/middleware/concurrency.go:124`）。这是「fail-closed 要真的能停下来」的关键。
**面试一句话**：context 是 Go 里做超时和取消的标准方式；关键是**每一层都要把它传下去**，否则取消信号到不了底层。

### defer 与 LIFO

**大白话**：`defer` 注册的函数在函数返回前执行，多个 `defer` 按**后进先出**执行（最后注册的最先跑）。
**打个比方**：叠盘子——最后放上去的最先被拿走。
**项目里用在哪**：`cmd/notes-of-ashen/main.go:100` 正是利用这一点：先注册 `ctx.Close()`、后注册 `server.Stop()`，所以先停服务（等在途请求做完）再关连接池。AI 客户端也用 `defer` 在函数出口统一做错误脱敏（`internal/aiclient/client.go:98`）。
**面试一句话**：defer 的 LIFO 特性可以用来编排「资源释放顺序」——但注册顺序要和执行顺序反着想。

### interface 与依赖倒置

**大白话**：调用方定义「我需要什么能力」（接口），而不是依赖具体实现。这样测试可以传假实现，生产可以传真实现。
**打个比方**：你只需要一个「能打印的东西」，不管是喷墨还是激光，能打就行。
**项目里用在哪**：`internal/middleware/auth.go:20` 定义 `UserFinder` 接口（只需要 `FindUserByID` 和 `UserTokenVersion` 两个方法）；`:28` 定义缓存接口 `AuthUserCache`；`redisLimiter` / `redisConcurrencyLimiter` 都是**故意收窄的接口**，注释说明这样可以在没有真实 Redis 的情况下做单元测试。
**面试一句话**：Go 的接口是隐式实现且应当由使用方定义——「接口越小越好」让测试和替换都更容易。

### GC 与内存

**大白话**：Go 有自动垃圾回收，不用手动释放内存。但频繁分配会增加 GC 压力，所以性能敏感的地方要复用对象、预分配切片容量。
**打个比方**：有专人打扫房间（GC），但如果你不停扔垃圾，他就得一直扫——不如少制造垃圾。
**项目里用在哪**：大量使用 `make([]T, 0, cap)` 预分配（如 `internal/rag/chunk.go:110`、`:180`、`internal/logic/rag/rag.go:297`）；共享 HTTP 连接池复用连接（`internal/aiclient/http.go:37`）。
**面试一句话**：Go 里最便宜的优化通常是「减少分配」，预处理容量和复用对象比调 GC 参数更有效。

### go test 与 sqlmock

**大白话**：`go test` 跑单元测试；`sqlmock` 让数据库调用可以在**没有真实 MySQL** 的情况下被断言（包括检查 SQL 语句本身）。
**打个比方**：`sqlmock` 像汽车碰撞测试用的假人——不用真出事就能验证安全设计。
**项目里用在哪**：`model/*_sqlmock_test.go`（比如 `model/user_sqlmock_test.go`、`model/media_sqlmock_test.go`）验证 SQL 与扫描逻辑；另有 `model/user_mysql_integration_test.go` 和 `test/integration/http_integration_test.go` 做**真实数据库/真实 HTTP 全链路**验证。
**面试一句话**：单测快但要 mock，集成测试真但慢——两者分工而不是互相替代。

## 最容易答错的 5 个概念

**1. 401 vs 403**
- ❌ 错误答法：「401 是没权限，403 是没登录。」
- ✅ 正确答法：「401 是**没认证**（你是谁还没确定），403 是**已认证但没权限**（知道你是谁，但你不能做这件事）。」

**2. 索引是不是越多越好**
- ❌ 错误答法：「索引越多查询越快，所以多建。」
- ✅ 正确答法：「索引加速读但**拖慢写**（每次写入都要维护索引）并占空间。要按实际查询模式建，用不到的索引应该删。」

**3. fail-open / fail-closed 记反**
- ❌ 错误答法：「fail-open 是失败时打开保护、fail-closed 是失败时关闭保护。」
- ✅ 正确答法：「依赖故障时 **fail-open = 放行请求**，**fail-closed = 拒绝请求**。安全敏感的接口要 fail-closed。」

**4. 缓存和数据库谁先写**
- ❌ 错误答法：「先更新数据库再更新缓存，这样最快。」
- ✅ 正确答法：「**先更新数据库，再删除缓存**（不是更新缓存）。删除比更新更安全，因为并发更新缓存可能写入更旧的值；TTL 作为兜底。」

**5. RAG 和微调谁更新知识**
- ❌ 错误答法：「RAG 是把模型训练得更懂我的数据。」
- ✅ 正确答法：「**RAG 不训练模型**，它在推理时检索资料再喂给模型；**微调才改变模型参数**。RAG 更新知识只需重新索引。」
