## 本册速记卡

- **一个入口端口**：宿主机只暴露 `127.0.0.1:1270`，Nginx 在这里既提供静态前端，又反代 `/api`、`/media`、`/rss.xml`、`/sitemap.xml`。
- **核心四件套**：`web`、`api`、`mysql`、`redis` 默认启动；`rabbitmq`/`meilisearch`/`qdrant` 分别属于 `messaging`/`search`/`rag` **profile**，必须与环境变量开关**双向一致**。
- **三个一次性任务**：`migrate`（迁移）、`config-check`（可选依赖开关校验）、`public-site-check`（生产站点地址门禁）；`api` 要等这三个都成功退出才启动。
- **镜像**：两个 Dockerfile 都是多阶段构建，**非 root 运行**，基础镜像锁 `@sha256` digest。
- **健康检查三层**：`/livez`（204，只证明 Nginx 活着）→ `/healthz`（200/503，只给整体状态）→ `/api/v1/admin/system/health`（管理员看 7 项依赖明细 + 延迟）。
- **Nginx**：安全头/CSP、`/api` 限流 10r/s、SSE 专属 location 关缓冲关 gzip、静态资源 `immutable` 缓存一年。
- **重建过一次构建上下文**：从约 846 MB 降到约 3.11 MB（419 个文件）。

## 主题：整体部署形态

### ① 一句话答案

单机 Docker Compose：Nginx 容器对外只开一个端口，其余服务只在内部网络可见；数据库和 Redis 是必需依赖，其余是可选能力。

### ② 展开讲 30–60 秒

**为什么只暴露一个端口**：

- 安全上，MySQL、Redis、Meilisearch、Qdrant、RabbitMQ **全部只用 `expose`**（容器网络内可见，宿主机不可见），暴露面从「6 个服务」收敛到「1 个反向代理」；
- 运维上，1Panel 或任何外层反代只需要指向 `127.0.0.1:1270`，不用理解内部拓扑；
- 代价是排障必须 `docker exec` 进容器，不能从宿主机直连数据库。

**网络设计**：自定义 bridge 网络 `172.30.127.0/24`，Web 容器固定 IP `172.30.127.10`。固定 IP 是为了让可信代理链可靠：Nginx 只信任直接上游（Compose 网桥网关 `172.30.127.1/32`）传来的 `X-Forwarded-For`，API 只信任 Web 容器地址。

**端口与超时**：`WEB_PORT` 默认 `1270`；`APP_TIMEOUT` 默认 610000 毫秒（约 610 秒），与 Nginx 的 `proxy_read_timeout 610s` 对齐——**这两个值必须配套**，否则会出现 Nginx 已经放弃、后端还在写的问题。

### ③ 代码落点

`docker-compose.yml:17`（端口映射）、`:108`（api 的 expose）、`:417`（网络定义）、`deploy/nginx/default.conf:33`（server 块）、`.env.example:5`（`WEB_PORT`）、`:7`（`APP_TIMEOUT`）。

### ④ 可能的追问 + 应答

- **Q：为什么不用 Kubernetes？**
  A：单机自用，K8s 的编排、存储、网络复杂度远超收益。Compose 一个文件说清全部拓扑，重启和回滚都简单。**如果真要多副本，我在代码层已经做了并发防护（迁移独立、索引重建租约），但集群的存储和调度问题没解决。**

- **Q：为什么数据库和 Redis 也放在 Compose 里？**
  答：为了「一条命令跑起来」的部署体验。生产上也支持外部 Redis（有 `docker-compose.external-redis.yml` 覆盖文件），以及通过 `APP_DATABASE_DSN` 指向远程 MySQL。

- **Q：数据会不会丢？**
  A：所有有状态服务都挂了命名卷（MySQL/Redis/RabbitMQ/Meilisearch/Qdrant/媒体）。所以 `docker compose down`（不带 `-v`）不会丢数据。**但卷不等于备份**——真正的备份走 `scripts/backup.ps1` 和后台加密整站备份。

### ⑤ 诚实边界

- 单机没有高可用；宿主机故障即服务中断。
- 媒体用的是本地卷，**没有接对象存储**。

## 主题：可选能力与 profile 机制

### ① 一句话答案

可选能力要**同时满足两个条件**才会启动：Compose 里开对应的 `profile`（决定容器起不起），环境里开对应的 `APP_*_ENABLED`（决定后端连不连）。这两者不一致会被启动校验拦住。

### ② 展开讲 30–60 秒

| 能力 | Compose profile | 环境变量开关 | 不开启时的降级 |
| --- | --- | --- | --- |
| 异步操作日志 | `messaging` | `APP_RABBITMQ_ENABLED=true` | 不投递操作事件，核心功能不受影响 |
| 全文搜索 | `search` | `APP_SEARCH_ENABLED=true` | **回退到 MySQL 全文索引查询** |
| RAG 问答 | `rag` | `APP_RAG_ENABLED=true` | 问答接口返回不可用；导航入口隐藏 |
| 邮箱验证码 | 无需 profile（对外 SMTP） | `APP_EMAIL_ENABLED=true` | 验证码无法发送（首个管理员有特例） |
| 爬虫预渲染 | 无需 profile（对外服务） | `PRERENDER_ENABLED=1` | 爬虫拿到的是 SPA 空壳 |

**为什么要「双向一致」**：只开 profile 不开开关 → 白起一个容器浪费内存；只开开关不开 profile → 后端会去连一个不存在的主机，启动或运行时报错。所以项目里有个独立的一次性任务 `config-check` 专门校验这件事，**不一致就不让 API 启动**。

**启动命令的差别**：默认 `docker compose up -d --build` 只起核心四件套；要开能力得显式带 profile（比如 `docker compose --profile rag up -d --build`）并同时设 `COMPOSE_PROFILES`。

### ③ 代码落点

`docker-compose.yml:313`（rabbitmq profile）、`:347`（meilisearch）、`:380`（qdrant）、`:196`（config-check 服务，命令是 `-validate-optional-dependencies-only`）、`.env.example:33`（profile 与开关的说明注释）、`cmd/notes-of-ashen/main.go:75`（校验入口）。

### ④ 可能的追问 + 应答

- **Q：为什么要这么麻烦，不能自动推导吗？**
  A：因为 Compose 的 profile 是**宿主机侧**的编排决定，后端的 `APP_*_ENABLED` 是**容器内**的配置决定，两者属于不同层，Compose 不会自动同步。我的做法是**用启动校验把它们绑在一起**：宁可启动失败给出明确提示，也不要带着错误配置跑。更好的设计是把它们收敛成一个变量再由编排派生，这是我认可的改进方向。

- **Q：搜索关闭时真的能回退吗？**
  A：能。搜索建议接口会先判断 `Search.Enabled()`，不可用或调用失败时会**记录日志并回退到 MySQL 查询**（代码里有明确的 fallback 分支）。

- **Q：Qdrant 需要备份吗？**
  A：不需要，它是**可再生派生数据**。真正要备份的是 MySQL 和媒体目录。

### ⑤ 诚实边界

- 三层开关（Compose profile / 进程开关 / 数据库设置）目前是「校验一致性」而不是「统一声明」，配置项较多时容易漏。
- 没有实现「运行时热开关可选能力」（比如不重启就加载 Qdrant 客户端）。

## 主题：启动顺序与一次性任务

### ① 一句话答案

`mysql`/`redis` 健康后 → `config-check` 和 `migrate` 成功退出 → `public-site-check` 成功 → `api` 启动 → `web` 等 `api` 健康后启动。

### ② 展开讲 30–60 秒

这是把「部署期错误」提前暴露的设计。四个服务承担不同职责：

| 服务 | 命令 | 作用 |
| --- | --- | --- |
| `config-check` | `-validate-optional-dependencies-only` | 校验可选依赖的开关与 profile 是否一致 |
| `migrate` | `-migrate-only` | 只连数据库跑迁移；**故意不依赖 Redis 和认证密钥** |
| `public-site-check` | `-validate-public-site-url` | 生产门禁：要求数据库里的 `siteBaseUrl` 是合法 HTTPS |
| `api` | 正常启动 | 等前面全部 `service_completed_successfully` |

**为什么迁移要独立**：如果让 API 启动时顺手跑迁移，多副本部署时多个实例会**同时执行 DDL**，互相竞争甚至锁表。独立的一次性任务 + `service_completed_successfully` 依赖，保证「迁移成功才算完成，API 才允许启动」。

**为什么迁移不能依赖 Redis 和认证密钥**：迁移是纯粹的数据库操作。如果它还要求 Redis 可用或密钥合法，就会因为**无关配置**把部署卡死——比如你只想补一次迁移，却因为 Redis 密码没配而被拒绝。所以 `-migrate-only` 分支里只读取数据库 DSN。

**失败的表现**：任务以非零退出，API 不会启动，容器日志保留供排查。**这是「失败就起不来」而不是「带着半截结构硬跑」**。

### ③ 代码落点

`docker-compose.yml:51`（api 的 depends_on 四项条件）、`:135`（migrate）、`:153`（`-migrate-only`）、`:166`（public-site-check）、`:196`（config-check）、`cmd/notes-of-ashen/main.go:53`（migrate-only 分支注释：「只依赖数据库，不能因 Redis、认证密钥或可选服务配置而失败」）。

### ④ 可能的追问 + 应答

- **Q：迁移失败了怎么排查？**
  A：三个诊断参数：`-migration-version` 打印镜像内最高迁移版本；`-schema-version` 打印数据库已应用的最高版本；直接看 `migrate` 容器日志。这两个数字一比就能判断是「迁移没跑」还是「跑了一半」。

- **Q：迁移有破坏性操作怎么办？**
  A：项目约定是「迁移不可变、只能新增前向迁移」。真正危险的操作（删列、改类型）需要额外评估和执行前的备份。**目前没有自动的迁移前快照机制**，这是运维上应该补的。

### ⑤ 诚实边界

- 没有自动的「迁移前备份」步骤（依赖人工按 `docs/OPERATIONS.md` 走流程）。
- 迁移在真实大数据量下的执行时长未评估。

## 主题：镜像构建

### ① 一句话答案

两个 Dockerfile 都是多阶段构建：**构建阶段**装全量工具链产出制品，**运行阶段**只放最小运行时；都以**非 root** 运行，基础镜像锁 digest。

### ② 展开讲 30–60 秒

**API 镜像**（`Dockerfile.api`）：

- 构建阶段 `golang:1.25-alpine`：先 `COPY go.mod go.sum` 再 `go mod download`（**利用层缓存**，源码变了不用重下依赖），然后 `COPY . .` 编译；
- 编译参数 `CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w"`：静态二进制（不依赖 libc）、`-trimpath` 去掉本地路径信息、`-s -w` 去掉符号表和调试信息**减小体积**；
- 运行阶段 `alpine:3.22`：只装 `ca-certificates`（HTTPS 要用）、`tzdata`（时区）、`wget`（健康检查要用）；
- **创建 uid 10001 的普通用户并 `chown` 应用与媒体目录，然后 `USER appuser`** —— 以非 root 运行，降低容器被攻破后的影响面。

**Web 镜像**（`Dockerfile.web`）：

- 构建阶段 `node:22-alpine` + `corepack enable`，`pnpm install --frozen-lockfile`（**锁定依赖版本，保证可复现**），然后 `pnpm build`（等于 lint + 类型检查 + 构建 + 体积检查）；
- 运行阶段用 **`nginxinc/nginx-unprivileged`** —— 这是官方的非 root Nginx 镜像，worker 以 uid 101 运行，监听**非特权端口 8080**；
- 把 `default.conf` 作为**模板**复制（`templates/` 目录下，Nginx 启动时做环境变量替换），并把安全头和限流配置分别放到 `snippets/` 和 `conf.d/`。

**digest 锁定**：`mysql:8.4@sha256:...`、`redis:7.4-alpine@sha256:...`、`qdrant/qdrant:v1.16.3@sha256:...` 等基础镜像全部锁 digest，保证「同一个 tag 拉到的内容永远一样」。

**一次真实的构建优化（很好的素材）**：审查发现 Docker 构建上下文高达约 **846.63 MB**（`.gocache` 约 464.61 MiB + `.tmp` 约 335.62 MiB 被一起打包发送）。虽然 Git 已经忽略这些目录，但 **Docker 的 `.dockerignore` 没排除它们**。补齐规则后实测构建上下文降到 **419 个文件、3,106,215 字节（约 3.11 MB）**，并且验证了 13 个构建必需文件仍存在且 SHA-256 与工作区一致。

### ③ 代码落点

`Dockerfile.api:1`（构建阶段）、`:12`（先拷 go.mod 利用缓存）、`:16`（编译参数）、`:18`（运行阶段）、`:30`（非 root 用户）、`Dockerfile.web:1`、`:10`（frozen lockfile）、`:13`（构建）、`:16`（非特权 nginx）、`:24`（配置与模板复制）、`docker-compose.yml:231`（mysql digest）、`:268`（redis）、`:346`（meilisearch）、`:379`（qdrant）、`:312`（rabbitmq）、`.dockerignore`、`docs/PROJECT-REVIEW-2026-09-14.local.md` 第 4 节 O01。

### ④ 可能的追问 + 应答

- **Q：为什么不把 Go 二进制做成 `scratch` 镜像？**
  A：因为需要 `ca-certificates`（访问 HTTPS 的 AI 和 SMTP）、`tzdata`（时区正确）和 `wget`（Compose 健康检查用）。用 `alpine` 是体积和可用性的折中。

- **Q：为什么基础镜像要锁 digest 而不是只锁 tag？**
  A：因为 **tag 是可变的**。同一个 `v1.16.3` 理论上可以被重新推送成不同内容（这个项目自己的发布流程就出现过 tag 复用问题）。锁 digest 才能保证「今天和半年后拉到的是同一份」。

- **Q：非 root 有什么坑？**
  A：主要坑是文件权限。媒体目录要可写，所以镜像创建时就 `chown` 给 appuser；另外不能监听 1024 以下的端口，所以 Nginx 监听 8080。**这些都是显式处理过的。**

### ⑤ 诚实边界

- API 镜像用的是 `alpine` + `wget` 做健康检查，`wget` 是为了探针而装的（略微增大镜像）。
- **发布制品追溯不可靠**：同一 tag 被重新构建后指向了不同镜像，发布历史里的镜像 ID 和实际运行的不一致（见发布那一节）。

## 主题：Nginx 配置

### ① 一句话答案

一个 server 块承担静态托管 + 反代 + 限流 + 安全头 + 缓存 + 爬虫预渲染；其中 SSE、备份恢复、`/healthz`、RSS/Sitemap 都有**独立的 location**，因为它们的超时/缓冲需求不同。

### ② 展开讲 30–60 秒

**通用 `/api/`**：`limit_req zone=api_limit burst=20 nodelay`（每 IP 10 请求/秒，突发 20 不延迟），`proxy_pass http://api:19000`，补齐 `X-Real-IP` / `X-Forwarded-For` / `X-Forwarded-Proto`，超时 610 秒与后端对齐。

**SSE 专属 location**（`= /api/v1/rag/chat/stream`）：注释写明了原因——**不能落进通用 `/api/` location，否则 gzip 或代理缓冲会合并 token，导致浏览器迟迟收不到首段回答**。所以设了 `proxy_buffering off`、`proxy_cache off`、`gzip off`、`proxy_set_header Connection ""`。后端也会设 `X-Accel-Buffering: no` 作为第二道保险。

**备份恢复 location**：单独把 `client_max_body_size` 提到 `${WEB_BACKUP_MAX_BODY_SIZE}`（默认 1025m），因为整站归档可能接近 1 GiB。**这个值和后端的 `APP_BACKUP_MAX_UPLOAD_BYTES` 必须联动**。

**`/healthz` 反代到后端**（并 `Cache-Control: no-store`），**`/livez` 直接 `return 204`**（Nginx 自己的存活探针，`access_log off`）。注释明确指出：对外 readiness 必须反映 API、数据库、Redis 和 schema 状态，**不能落入 SPA fallback**。

**RSS/Sitemap**：这两个 location 用 `proxy_set_header Host $http_host`，注释解释是「保留客户端显式端口；规范站点地址由 `siteBaseUrl` 固定，避免依赖请求 Host」。

**静态资源缓存**：Vite 构建的资源名带 hash，所以 `expires 1y` + `Cache-Control: public, immutable`，并且 `access_log off`。媒体路径（`/media/`）同样一年不可变，因为它们也是**内容寻址**的（文件名是 SHA-256）。

**一些细节**：

- `server_tokens off`（隐藏 Nginx 版本号）；
- `port_in_redirect off` + `server_name_in_redirect off`（重定向不泄露内网端口和配置）；
- 显式 404 掉 `*.map`（**不暴露 source map**）和 `/media/.restore-*`、`.upload-*`、`.delete-*`（**内部恢复暂存目录不能被静态路径读到**）；
- gzip 只对文本类型开启（`gzip_min_length 1024`，级别 5）；
- 爬虫预渲染：用 `map` 判断 User-Agent 命中爬虫列表或 `_escaped_fragment_`，命中就走 `@prerender` 反代到 Prerender 服务。

### ③ 代码落点

`deploy/nginx/default.conf:42`（resolver）、`:44`（client_max_body_size）、`:46`（可信上游）、`:74`（安全头 include）、`:77`（map 404）、`:82`（暂存目录 404）、`:87`（媒体缓存）、`:97`（静态资源缓存）、`:104`（通用 /api）、`:120`（SSE location 与注释）、`:138`（/healthz）、`:150`（/livez）、`:158`（备份恢复体积）、`:172`（RSS）、`:182`（Sitemap）、`:197`（SPA fallback）、`:205`（prerender）。

### ④ 可能的追问 + 应答

- **Q：为什么 `add_header` 要重复 include 安全头？**
  A：这是 **Nginx 的一个著名陷阱**：如果子 location 里出现了 `add_header`，父级的 `add_header` 会**全部失效**（不会继承）。所以我把安全头集中在 `security-headers.conf`，并在每个自带 `Cache-Control` 的 location 里**显式重复 include**。文件开头就写了这条注释。

- **Q：CSP 具体限制了什么？**
  A：`default-src 'self'`、**`script-src 'self'`（禁止内联脚本）**、`style-src 'self' 'unsafe-inline'`（**需要 unsafe-inline，因为 Mermaid/KaTeX 会注入内联样式**）、`img-src 'self' data: blob: https:`、`connect-src 'self'`、`frame-src 'none'`、`object-src 'none'`、`base-uri 'self'`、`form-action 'self'`、`frame-ancestors 'self'`。还有 `upgrade-insecure-requests` 只在 HTTPS 下追加（用 `map $scheme` 控制，因为 HTTP 测试环境下加了它会让 WebKit 把同源资源升级成 HTTPS 导致连不上）。

- **Q：HSTS 呢？**
  A：**HSTS 由 1Panel 上游的 HTTPS 反代统一注入**，不在这一层配。因为这一层可能跑在 HTTP 下（本地/测试），配 HSTS 会把自己锁死。

### ⑤ 诚实边界

- **R01 是这一层的真实事故**：静态 `proxy_pass http://api:19000` 在**加载配置时**解析地址，容器重建导致 IP 变化后，Nginx 还在连旧 IP；`resolver` 指令并不会让这种「字面域名写法」持续更新解析结果。表现是：`/healthz` 经 Web 返回 502，而直连 API 返回 200；Web 容器自己还是 healthy（**它的探针只探静态首页**）。当时用 `nginx -s reload` 缓解。正确改法是配一个能跟随 Docker DNS 更新的 upstream（变量化 `proxy_pass` + `resolver`），并把 Web 的就绪检查覆盖到 API 反代链路。
- 没有做 WAF 或更严格的出站/入站过滤。

## 主题：限流与防护的双层分工

### ① 一句话答案

**Nginx 层**做粗粒度的每 IP 请求速率限制（10r/s，突发 20），**Go 层**按接口做细粒度的业务限流（登录 5/分、RAG 12/分等）。

### ② 展开讲 30–60 秒

为什么两层都要：

| 层 | 优点 | 局限 |
| --- | --- | --- |
| **Nginx** | 在到达应用之前就挡住，**不消耗 Go 进程资源**；对全站统一生效 | 做不了业务维度（比如「登录失败次数」「按用户」）；没法感知 Redis 故障 |
| **Go 中间件** | 能做接口级精细阈值、fail-open/fail-closed 语义、复用可信代理 IP 判定 | 请求已经进入应用，消耗了一部分资源 |

所以 Nginx 是「防洪堤」，Go 层是「分水闸」。测试环境专门提供了一份放宽的 `deploy/test/nginx/10-limits-test.conf`，因为集成测试会高并发跑接口，默认限流会把测试打挂。

### ③ 代码落点

`deploy/nginx/10-limits.conf:4`（`limit_req_zone ... rate=10r/s`）、`deploy/nginx/default.conf:106`、`deploy/test/nginx/10-limits-test.conf`、`internal/middleware/ratelimit.go`、`internal/handler/routes.go:39`。

### ④ 可能的追问 + 应答

- **Q：为什么 Nginx 用 10r/s？**
  A：这是「防滥用」的粗线，不是精确配额。正常用户浏览一个页面的并发请求远低于这个值，而脚本刷接口会被挡住。细粒度控制交给 Go 层。

- **Q：两层限流会不会互相干扰？**
  A：不会，因为它们作用在不同粒度上。但要注意**测试环境必须放宽 Nginx 层**，否则会出现「业务逻辑没问题但测试因为限流失败」的假故障——这也是我单独做测试配置的原因。

### ⑤ 诚实边界

- Nginx 层的限流基于 `$binary_remote_addr`，**如果前面还有一层不可信代理，取到的是代理 IP**。所以 `set_real_ip_from` 的配置必须正确（见 `03` 的可信代理那节）。

## 主题：健康检查三层设计（信息暴露的取舍）

### ① 一句话答案

三层各有受众：`/livez` 给容器探针（只证明 Nginx 活着）、`/healthz` 给部署探针和外部监控（只给整体状态，不泄露依赖明细）、`/api/v1/admin/system/health` 给管理员（7 项依赖明细 + 延迟）。

### ② 展开讲 30–60 秒

**为什么要把健康检查分开**：这是**信息暴露（information disclosure）**的取舍。一个公开的、带依赖明细的健康检查等于把内部拓扑白送给攻击者——「Redis 挂了」「Meilisearch 未启用」「备份 schema 未升级」这些信息对攻击者有价值。

具体设计：

| 端点 | 返回 | 谁用 |
| --- | --- | --- |
| `/livez` | **204**，无正文 | Nginx/容器存活探针。只要 Nginx 还能响应就说明「进程没死」 |
| `/healthz` | `{"status":"ok"}` 或 `{"status":"degraded"}`，HTTP **200/503** | 部署探针、外部监控。**不输出任何依赖明细** |
| `/api/v1/admin/system/health` | 7 项检查（mysql/redis/meilisearch/rabbitmq/smtp/media/backup_schema）+ 每项状态与延迟 | 管理员排障 |

**`/healthz` 实际探测什么**：DB ping、Redis ping、**schema 校验**（两项：`migration.Check` 验证迁移文件与数据库记录完全一致，`SchemaReady` 验证运行时字段就绪）。任一必需依赖 down，整体就是 `degraded`，返回 503，让探针能直接判定。每项探测超时 **2 秒**。

注释里有一句很关键的话：**「仅检查运行时字段会遗漏历史 SQL 被改写、某个索引/清理迁移未执行等升级链路问题」**——所以它做的是「迁移文件与数据库记录一致性」的完整校验，而不是只看几个字段在不在。

**管理员接口的设计**：7 项检查**并行**执行（每项 3 秒超时）、结果按固定顺序回填、整体有 **30 秒缓存**（可以 `force` 绕过）。未启用的能力不报错，而是返回 `disabled` + 「未启用」，这样管理员一眼能区分「没开」和「坏了」。媒体检查是真的在媒体目录里**创建再删除一个临时文件**（验证可写），而不只是看目录是否存在。

**MQ 和 Search 在 `/healthz` 里只报告启用状态、不做真实探测**（注释说明：没有轻量 ping 接口，避免增加复杂度）——真实探测放在管理员接口里。

### ③ 代码落点

`internal/logic/site/health.go:19`（只暴露整体状态的注释）、`:25`（2 秒超时）、`:32`（三项必需检查）、`:82`（schema 校验的两步）、`:105`（200/503 决策）、`internal/logic/system/health.go:16`（30 秒缓存）、`:50`（并行 + 固定顺序）、`:58`（3 秒超时）、`:71`（7 项检查）、`:76`（媒体可写性实测）、`deploy/nginx/default.conf:138`（/healthz 反代）、`:150`（/livez 204）、`docker-compose.yml:114`（api 健康检查用 `/healthz`）、`:25`（web 健康检查只探静态首页）。

### ④ 可能的追问 + 应答

- **Q：为什么 `/healthz` 不返回依赖明细？**
  A：因为它是**公开端点**（不需要认证）。把「哪个依赖挂了」暴露出去，等于告诉攻击者当前哪个组件最脆弱。管理员有专门的鉴权接口看明细。

- **Q：`/livez` 和 `/healthz` 有什么区别？**
  A：`/livez` 回答「进程还活着吗」（liveness），**不检查任何依赖**——因为如果依赖挂了就把容器重启，是错误的自愈策略（重启解决不了数据库宕机，反而会加剧）。`/healthz` 回答「能对外服务吗」（readiness），会检查依赖，失败时返回 503 让流量不进来。

- **Q：为什么 Web 容器的探针只探静态首页？**
  A：这正是 **R01 事故的根因**——Web 探针只验证 Nginx 能不能返回首页，所以「Nginx 活着但 API 反代全挂」时 Web 依然报 healthy，编排层看不出问题。**正确做法是让 Web 的就绪检查覆盖到 API 反代链路。**

### ⑤ 诚实边界

- Web 容器探针不覆盖 API 链路（R01 的根因），**未修复**。
- `/healthz` 的 schema 校验每次都跑迁移一致性检查，成本高于简单 ping；在有缓存的探针场景下可用，但如果高频轮询要注意开销。

## 主题：可观测与日志

### ① 一句话答案

四个抓手：**请求 ID 串联日志**、**项目自研的安全访问日志**（不记敏感内容）、**Prometheus 指标端点**（仅容器网络可见）、**管理员健康页**。

### ② 展开讲 30–60 秒

- **请求 ID**：中间件链最前面注入 `X-Request-Id` 并放进 context，错误日志都带它。排障时按一个 ID 就能把一条请求的完整日志串起来。
- **安全访问日志**（自研）：**只记录请求元数据，禁止输出查询串、Header、Cookie 和请求正文**。为什么不用框架自带的？因为 go-zero 内置访问日志会在 5xx 时**转储完整请求**，而请求里可能有认证凭证和 AI API Key。
- **Prometheus 指标**：go-zero 内置，`etc/notes-of-ashen.yaml` 里配了 `0.0.0.0:9101`、路径 `/metrics`。注释说明：**仅 `expose` 不映射宿主机端口**，由编排环境（1Panel/内网）按需抓取。
- **日志收敛**：所有容器都是 `json-file` driver，并且**限制 `max-size: 10m`、`max-file: 3`**，避免磁盘被日志写满。
- **错误摘要化**：RAG/AI 的错误在写日志前会被归约成固定摘要（如 `upstream http status 429`），避免把上游回显的正文写进日志。

### ③ 代码落点

`internal/middleware/requestid.go`、`internal/middleware/accesslog.go`、`cmd/notes-of-ashen/main.go:83`（关闭内置日志的注释）、`etc/notes-of-ashen.yaml:6`（Prometheus）、`docker-compose.yml:34`（日志限制）、`internal/ragclient/dashscope.go:75`（安全错误摘要）。

### ④ 可能的追问 + 应答

- **Q：度量和日志怎么配合排查？**
  A：指标看趋势（错误率、延迟是否整体上升），日志按 `X-Request-Id` 看单条请求。**如果只有指标没有请求 ID，就只能在海量日志里猜是哪条请求出了问题。**

- **Q：没有分布式链路追踪吗？**
  A：**没有接入**（go-zero 依赖里有 OpenTelemetry/Zipkin 的间接依赖，但项目没有配置 exporter）。当前靠 `X-Request-Id` 做单体内串联。跨服务追踪对这个单体应用不是必需。

- **Q：访问日志不含正文，那怎么排查业务问题？**
  A：业务问题靠**业务日志**（logic 层按需记录），访问日志只负责「谁在什么时候请求了什么路径、结果如何」。这是有意识的分离——避免为了排障方便就把敏感内容全记下来。

### ⑤ 诚实边界

- 没有接入分布式追踪、没有告警系统（没有「错误率超阈值通知」）。
- 没有日志聚合（ELK/Loki），靠 `docker compose logs` 和文件。

## 主题：发布与回滚

### ① 一句话答案

发布用 `scripts/release.ps1`：构建带不可变 tag 的镜像、记录镜像 ID 到发布历史文件；回滚靠切回之前的 tag/digest。**但当前流程有「tag 可复用」的追溯缺陷。**

### ② 展开讲 30–60 秒

**发布流程大致是**：确定不可变 tag（比如 `v20260726-1646-61020d0`，含时间和 commit 短哈希）→ 构建 API 与 Web 镜像 → 通过 tag 查本地镜像并记录镜像 ID 到 `deploy/release-history.local.jsonl` → 用该 tag 启动 Compose。

**已知缺陷（`docs/PROJECT-REVIEW.md` 第 4 节记录）**：

- **同一个 tag 可以被重新构建并覆盖**，导致「tag → 镜像内容」不是一一对应；
- 审计时发现：发布历史里某个 tag 对应的镜像 ID **和实际运行的镜像 ID 不一致**（镜像创建时间也对不上），说明该 tag 被重新构建过；
- `release.ps1` 在**工作区有未提交改动时只发警告仍继续**，所以记录的 Git commit 也不能完整代表镜像内容。

**影响**：tag 不再是不可变发布标识，仅凭 Compose 文件和发布历史**无法确定当前运行的是哪份代码**；如果回滚脚本依赖被覆盖的本地 tag，可能拿不到原始发布制品。

**正确改法**（我写在审查报告的建议里）：

1. 禁止已存在的发布 tag 再次构建或覆盖，tag 必须与不可变 commit 一一对应；
2. 发布记录同时保存**镜像内容 digest**、Git commit、构建时工作区状态和构建时间，不只依赖可变 tag；
3. 发布前对脏工作区**默认失败**，确需发布未提交内容时用显式参数并在记录中标注「不可复现」；
4. 回滚优先使用**已验证的 digest 或镜像 ID**，并在部署前校验目标制品确实存在且与记录一致。

### ③ 代码落点

`scripts/release.ps1`、`deploy/release-history.local.jsonl`（本地发布历史，被 `.gitignore` 排除）、`docker-compose.yml:1`（`IMAGE_TAG` 的注释：未设置时 fallback 到 `latest` 仅用于本地开发）、`.env.example:29`（要求替换为不可变版本号或 commit hash）、`docs/PROJECT-REVIEW.md` 第 4 节。

### ④ 可能的追问 + 应答

- **Q：那你怎么回滚？**
  答：把 `IMAGE_TAG` 换成上一个已验证的 tag 并重新 `up -d`。**但我要诚实说**：如果那个 tag 被覆盖过，回滚到的可能不是当初的制品。所以更可靠的做法是记录并使用镜像 **digest**，这是我明确知道的改进方向。

- **Q：数据库结构变了怎么回滚？**
  A：**迁移是不可变且只向前**，所以「回滚代码」不等于「回滚数据库结构」。新版加了列，旧版代码通常还能跑（多出来的列不影响）；如果新版删了列或改了语义，回滚就需要额外的数据修复。项目约定是**破坏性变更必须单独评估并先备份**。这是这类系统里最难的运维问题之一。

- **Q：发布前要做什么检查？**
  A：按 `docs/OPERATIONS.md` 走：先备份 MySQL 数据卷或远程库、确认 Redis/RabbitMQ 持久化策略、`docker compose config --quiet` 校验配置、然后 `docker compose up -d --build`。生产还要确认 `siteBaseUrl` 已配置正式 HTTPS 域名。

### ⑤ 诚实边界

- **没有做过真实版本回滚演练**；审查报告明确说「真实版本回滚」未执行。
- 发布历史文件是本地文件（`*.local.jsonl`，已被 gitignore），**不随仓库分发**。

## 主题：备份与恢复

### ① 一句话答案

两条路径：**`scripts/backup.ps1`** 做数据库/数据卷级备份（适合定时任务），**后台「加密整站备份」** 做应用级全量导出（含媒体，age 加密，可在新环境一键恢复）。

### ② 展开讲 30–60 秒

两者的分工：

| | `backup.ps1` | 后台加密整站备份 |
| --- | --- | --- |
| 触发 | 命令行/计划任务 | 管理后台（需管理员密码 + 口令） |
| 内容 | 数据库转储（和/或数据卷） | **数据库快照 + 媒体文件 + 清单**，一个加密归档 |
| 用途 | 日常定时备份、异地副本 | 迁移/灾难恢复/整站重建 |
| 加密 | 取决于脚本实现 | **age（scrypt 口令派生）** |
| 校验 | 由脚本/外部工具保证 | 归档内含 `manifest.json`，逐文件 SHA-256 + 计数校验 |

**后台整站备份的关键安全设计**：

- 导出和恢复都要求**管理员密码 + 口令**双要素；
- 归档里有**清单**：版本号、导出时间、`data.json` 的 SHA-256、媒体文件列表（每个文件的 SHA-256 和大小）、各类记录数；
- 恢复时校验：**入口数量必须精确匹配**（`len(entries) == len(manifest.Files) + 2`）、清单路径不能重复、数据 SHA-256 必须一致、媒体 key 必须符合内容寻址格式、计数必须与快照一致——这些是**防 zip 炸弹和防篡改**的多重校验；
- 恢复过程用 **Redis 租约 + 进程内锁**串行化；
- 媒体恢复走「暂存目录 + 数据库 marker + 发布」三段式，进程崩溃后启动时会**重新收敛**（有 marker 就完成发布，没有就回滚暂存）。

**运维要求**（`docs/OPERATIONS.md`）：日常用 `backup.ps1`；备份要有**异地副本**；要定期做**恢复演练**（没演练过的备份等于没有备份）。

### ③ 代码落点

`scripts/backup.ps1`、`internal/logic/backup/backup.go:64`（Export）、`:86`（data SHA-256）、`:122`（媒体清单）、`:147`（age 加密）、`:188`（Restore）、`:202`（租约）、`:218`（age 解密）、`:253`（清单校验）、`:344`（启动恢复收敛）、`:409`（大小上限）、`:473`（入口数量校验）、`:544`（快照校验）、`internal/logic/media/restore.go`、`internal/security/restore_lease.go`、`docs/OPERATIONS.md`。

### ④ 可能的追问 + 应答

- **Q：为什么备份要加密？**
  A：归档包含**全部用户数据和媒体文件**。放在磁盘上或传到异地，一旦泄露就是全量泄露。age + scrypt 让归档本身是密文，口令不入库。

- **Q：恢复会不会把线上数据搞坏？**
  答：恢复是**覆盖式**的，界面上明确提示会覆盖用户、内容、配置和媒体，并清空会话、日志、流量与 AI 密钥。所以它适合「灾难恢复」而不是「部分回滚」。工程上我用租约 + marker + 暂存目录保证「中途失败不会留下半覆盖状态」。

- **Q：备份文件能跨版本恢复吗？**
  A：清单里有**归档版本号**，只支持受支持的版本（`supportedArchiveVersion`）；旧版本归档在读取时会校验并可能被拒绝。**跨版本恢复需要先在旧版本导出、升级后再导入，或者做数据迁移。**

### ⑤ 诚实边界

- 承诺的**恢复演练未在真实隔离环境完整执行**（审查报告列为待办）。
- 异地副本、跨主机恢复未验证。
- 数据库备份与媒体目录的一致性依赖「同一时间点」假设；**恢复时没有做严格的跨资源时间点对齐**。

## 主题：CI 与测试门禁

### ① 一句话答案

两个 workflow：前端 CI 跑 lint/类型/单测/构建/体积检查；集成 E2E 跑 `core`（每次 push 和 PR）和 `extended`（main push + 每日定时）。

### ② 展开讲 30–60 秒

- **`frontend-ci.yml`**：前端静态检查与构建（含包体积预算），保证前端不会带着 lint 错误或体积超限合入。
- **`integration-e2e.yml`**：
  - `core` 在**任意 push 和 PR** 时运行：Go 黑盒 HTTP 集成测试（真实 API + MySQL + Redis + Web Nginx）、历史 schema 自动迁移、并发 migrate、Redis 认证与错误密码 fail-fast、以及三个浏览器项目的 E2E（桌面 Chromium、Pixel 7 Chromium、iPhone 13 WebKit）。
  - `extended` 作为**发布门禁**在 `main` push 时运行，并且**每日 `Asia/Shanghai` 02:00（UTC 18:00）** 和手动触发时运行，覆盖其余并发与恢复失败注入测试。

**隔离性是关键设计**：每个阶段生成**全新的 Docker 项目名、独立卷、随机数据库/认证凭据、随机 Docker 子网和 loopback 随机端口**；结束时 `docker compose down --volumes --remove-orphans --rmi local` 清理。成功时删除临时目录和凭据；失败时保留**不含临时环境文件**的 Compose 日志，并上传 Playwright 报告、trace 和截图。

**测试环境固定关闭**邮件、RabbitMQ、Meilisearch 与 Prerender；**只有在测试环境才设 `APP_AUTH_COOKIE_SECURE=false`**（让 HTTP loopback 的 Chromium 能验证 Refresh Cookie），生产配置不受影响。

### ④ 可能的追问 + 应答

- **Q：为什么 `extended` 要每天定时跑？**
  答：因为它比 `core` 慢且更重（含并发和故障注入），不适合每次 push 都跑；但**不能只在发布时跑**——每天的定时运行能在问题积累成故障之前发现它（比如并发迁移在新环境下的行为）。

- **Q：集成测试会不会污染本地开发数据？**
  A：不会。脚本用的是独立项目名、独立卷、随机凭据和随机端口，不会碰你正在用的实例。而且审查报告特别说明：E2E 会真的注册用户/改角色/上传媒体，所以**不能对着正在使用的实例跑**。

- **Q：测试环境为什么要放宽 Nginx 限流？**
  A：因为默认 10r/s 会把高并发的集成测试打挂，产生「业务没问题但测试失败」的假故障。所以要单独准备 `10-limits-test.conf`。

### ⑤ 诚实边界

- **O06 是环境相关的问题**：宿主 Go 1.27.1 执行 `go test ./...` 时 gRPC 对 `http2.TrailerPrefix` 的引用编译失败，用项目声明的 Go 1.25.0 则测试、vet 和无 CGO 编译都通过。结论是**必须固定受支持的工具链**，升级 Go 时要单独验证 gRPC 与 `golang.org/x/net` 的兼容性。
- 没有做性能/负载测试的 CI。

## 可能被问倒的 3 个问题

1. **「你的健康检查为什么要做成三层？」**
   → 应答思路：因为受众不同、信息敏感度也不同。`/livez` 给容器探针用，返回 204，**不检查任何依赖**——依赖挂了重启容器解决不了问题，反而会加剧。`/healthz` 给部署探针和外部监控用，检查 DB、Redis 和 **schema 一致性**（迁移文件与数据库记录必须完全匹配），失败返回 503，但**只输出整体状态不输出明细**，因为它是公开端点，暴露「哪个依赖挂了」等于给攻击者送情报。管理员有鉴权接口看 7 项明细和每项延迟，未启用的能力显示 `disabled` 而不是报错，**让「没开」和「坏了」能区分开**。

2. **「容器重建之后你的站点还能用吗？」**
   → 应答思路：这就是审查里发现 R01 的地方，我要如实讲。静态 `proxy_pass http://api:19000` 是在**加载配置时**解析地址的，容器重建导致 IP 变化后，Nginx 还在连旧 IP，表现为 `/healthz` 经 Web 返回 502 而直连 API 返回 200。更糟的是 **Web 容器的探针只探静态首页**，所以编排层完全看不出问题。当时用 `nginx -s reload` 缓解。正确改法是用能跟随 Docker DNS 更新的 upstream 写法（变量 + `resolver`），并且把 Web 的就绪检查覆盖到 API 反代链路上。**这个案例说明「容器健康 ≠ 服务可用」。**

3. **「你怎么保证发布出去的东西半年后还能拉回来？」**
   → 应答思路：诚实说**目前做得不够**。我用 tag 记录发布，但审计发现同一个 tag 被重新构建后指向了不同镜像，发布历史里的镜像 ID 和实际运行的不一致（`docs/PROJECT-REVIEW.md` 第 4 节）。基础镜像我是锁了 `@sha256` digest 的，但**自己构建的应用镜像没有锁 digest**。正确做法是：禁止复用 tag、记录并校验镜像 digest、脏工作区默认拒绝发布、回滚用 digest 而不是 tag。这是我很清楚但还没落地的改进。
