## 本册速记卡

- **配置存哪**：AI 连接配置**只存数据库** `site_settings`，不是环境变量；管理员改了立即生效，不用重启。
- **Key 怎么存**：AES-GCM 密文，前缀 `v3:`，密钥 = `sha256("notes-of-ashen:ai-settings:" + APP_AUTH_ACCESS_SECRET)`，**按用途派生**。
- **两种协议**：`openai`（`Authorization: Bearer` + `/chat/completions`）和 `anthropic`（`x-api-key` + `/messages`），统一抽象成一个客户端。
- **提示词**：每个动作一个 system prompt，**强制只输出 JSON**（OpenAI 侧还用 `response_format: json_object`），解析时容错（从第一个 `{` 到最后一个 `}`）。
- **出站安全**：每次拨号重新解析域名、拦内网与保留地址、不继承代理、不跟随重定向。
- **错误脱敏**：上游错误信息里的 API Key 会被替换成 `[REDACTED]`；错误体只保留「安全摘要」。
- **降级**：未配置 AI 时功能整体关闭，不影响博客主流程；AI 辅助限流 20 次/分（fail-open）。

## 主题：AI 连接配置与密钥加密

### ① 一句话答案

AI 连接配置（API 格式、Base URL、API Key 密文、模型名、超时）只保存在数据库的 `site_settings` 里；**API Key 用 AES-GCM 加密、前缀 `v3:`，加密密钥由 `APP_AUTH_ACCESS_SECRET` 按「ai-settings」这个用途独立派生**，接口从不返回明文。

### ② 展开讲 30–60 秒

**为什么放数据库而不是环境变量**：因为它需要**运行时由管理员在后台改**。改成环境变量就意味着改一次要重启进程，而且要把密钥写进 `.env` 和部署配置里，扩散面更大。项目约定明确写了：**AI 连接配置通过管理后台写入数据库，不得新增进程级 AI 密钥配置**。

**加密是怎么做的**（这是重点，面试官很容易追问）：

1. **密钥派生**：不是直接用 `APP_AUTH_ACCESS_SECRET`，而是 `sha256("notes-of-ashen:ai-settings:" + secret)` 取 32 字节当 AES 密钥。
2. **加密**：AES-GCM，随机 nonce 前置到密文前，整体 base64，最后加 `v3:` 前缀标识版本。
3. **为什么按用途派生**：RAG 的密钥用的是 `sha256("notes-of-ashen:rag-settings:" + secret)`，**两个派生域完全不同**。这样即使某个字段泄露或者某个用途的密钥被猜出来，也不能横向解密另一类配置。这就是「密钥隔离」的思路。
4. **版本前缀的意义**：密文带版本号，将来换算法时可以并存识别。代码里还有 `v2:` 的历史格式——`v2` 密文**必须由管理员重新录入**，因为旧格式无法用新密钥解；没有版本前缀的更老密文在读取时兼容，并在后续保存时迁移到 `v3:`。
5. **状态查询**：接口返回的是「是否已配置」和「是否需要更新」两个布尔值（`apiKeyStatus`），**永远不返回明文**。

**有个重要的运维后果**：因为密文由 `APP_AUTH_ACCESS_SECRET` 派生，所以**轮换这个密钥时必须重新录入所有 AI Key**。这一点写进了 README 和配置注释里。

### ③ 代码落点

- 加解密与版本前缀：`internal/logic/ai/settings.go:30`（`v2:`）、`:31`（`v3:`）、`:415`（`encryptSecret`）、`:427`（`decryptSecret`）、`:435`（`decryptAIAPIKey`，处理 v2/v3/无前缀）、`:456`（`encryptSecretPayload`）、`:475`（`decryptSecretPayload`）
- 密钥派生域：`internal/logic/ai/settings.go:501`
- 状态查询与更新决策：`internal/logic/ai/settings.go:382`（`apiKeyStatus`）、`:394`（`apiKeyCipherForUpdate`）
- 响应体不含明文：`internal/logic/ai/settings.go:367`（`aiSettingsResp`）
- 项目约定：`AGENTS.md`「项目已知约束」、`README.md:199`、`etc/notes-of-ashen.yaml:20`
- 对比 RAG 的独立派生域：`internal/rag/secrets.go:85`

### ④ 可能的追问 + 应答

- **Q：为什么不直接把密钥明文存数据库？**
  A：数据库备份、`mysqldump`、误查日志都可能泄露明文。加密后即使拿到数据库快照，没有 `APP_AUTH_ACCESS_SECRET` 也解不开。

- **Q：加密密钥为什么不用专门的 KMS？**
  A：这是个人项目，引入 KMS 会增加部署复杂度。用「由主密钥派生 + 用途隔离」在成本和收益上更平衡。**如果要上生产，用 KMS 或至少把主密钥托管到独立密钥服务是更好的选择**——这是我知道的局限。

- **Q：`v3:` 前缀到底解决什么问题？**
  A：解决**算法演进**。如果将来从 AES-GCM 换成别的算法，或者派生方式变了，可以靠前缀识别出旧密文该怎么处理（提示重录），而不是直接解密失败崩掉。

- **Q：轮换密钥会怎样？**
  A：所有已保存的 AI Key 和 RAG Key 都解不开了，必须重新录入。这是**设计上的强耦合**，好处是密钥只有一个来源，坏处是轮换成本高。我会在文档里明确提示这一点。

### ⑤ 诚实边界

- 密钥存在同一个进程（同主密钥派生），**没有硬件级密钥保护**，进程被攻破则密钥可被提取。
- `v2:` 密文必须重录这一点意味着**升级会带来一次人工操作**，我在 README 里写了迁移说明。

## 主题：双协议适配（OpenAI 与 Anthropic）

### ① 一句话答案

用 `APIFormat` 区分两种上游协议，把差异收敛在**请求构造、鉴权头、响应解析、端点拼接**四个地方，上层业务只调用统一的 `Assist` / `ListModels` / `TestModel`。

### ② 展开讲 30–60 秒

两种协议的差异不止是 URL，具体有这些：

| 差异点 | OpenAI 兼容 | Anthropic |
| --- | --- | --- |
| 鉴权头 | `Authorization: Bearer <key>` | `x-api-key: <key>` + `anthropic-version: 2023-06-01` |
| 对话端点 | `/chat/completions` | `/messages` |
| system 提示词位置 | `messages` 数组里一条 `role: "system"` | **顶层 `system` 字段**，`messages` 里只有 user |
| 强制 JSON | `response_format: {type: "json_object"}` | 无此字段，靠 prompt 约束 |
| 响应正文位置 | `choices[0].message.content` | `content[]` 数组里 `type == "text"` 的块**拼接** |
| 模型列表 | `GET /models` | `GET /models?limit=1000` |
| Base URL 习惯 | 通常已含 `/v1` | 若未含 `/v1` 且没有已知端点后缀，自动补 `/v1` |

**端点拼接的容错**：管理员填 Base URL 时可能填成完整端点（比如已经带了 `/chat/completions`）。所以拼接前会先检查并**剥掉已知的端点后缀**，再拼上目标路径，避免出现 `/chat/completions/chat/completions` 这种错误。

**归一化**：`NormalizeAPIFormat` 把空值当 `openai` 处理（兼容老配置），其他值报错。

### ③ 代码落点

- 格式常量与归一化：`internal/aiclient/client.go:14`、`:86`
- 端点拼接容错：`internal/aiclient/http.go:256`（`endpointFor`）
- 鉴权头差异：`internal/aiclient/http.go:102`
- OpenAI 请求与解析：`internal/aiclient/openai.go:28`、`:38`
- Anthropic 请求、模型 URL、解析：`internal/aiclient/anthropic.go:26`、`:36`、`:47`
- 配置校验与超时校验：`internal/logic/ai/settings.go:287`（格式）、`:307`（Base URL）、`:322`（超时）

### ④ 可能的追问 + 应答

- **Q：为什么要支持两种而不是只做一种？**
  A：因为使用者可能用官方 OpenAI、Azure、国内的兼容服务，或者 Claude。抽象一层之后，切换上游只需要改配置，不用改代码。这也是**面向接口编程**的一个实际应用。

- **Q：抽象是怎么做的？**
  A：`requestCompletion` 是统一入口：它根据格式决定用 `newOpenAIChatRequest` 还是 `newAnthropicRequest` 构造 payload，发出去之后再按对应格式解析。上层 `Assist` 完全不知道底层是哪家。

- **Q：如果上游是"部分兼容"的第三方呢？**
  A：兼容差异靠容错兜住。比如 rerank 响应我同时接受 `output.results`（DashScope 原生）和顶层 `results`（某些代理），并且用指针区分「分数是 0」和「字段缺失」。流式解析里也放大了 scanner buffer，因为某些兼容服务会在单行里输出较长的 reason 字段。

### ⑤ 诚实边界

- 只支持「对话补全」和「模型列表」两类接口，**没有实现 function calling / tool use、多模态、流式 function call**。
- Anthropic 侧没有用它的 `response_format` 类能力（它本身也没有 OpenAI 那种强制 JSON 字段），只靠 prompt 约束，所以理论上 JSON 解析失败率会比 OpenAI 侧高一点——这也是我为什么做了宽松解析。

## 主题：提示词工程与动作设计

### ① 一句话答案

每个写作动作对应一个独立的 system prompt，**明确要求只输出 JSON 并给出字段说明和示例**；user prompt 只放标题和正文；不同动作用不同的 `max_tokens`。

### ② 展开讲 30–60 秒

**动作清单**（7 个）：

| 动作 | 作用 | max_tokens | 返回字段 |
| --- | --- | --- | --- |
| `complete` | 一键补全：标题、slug、摘要、SEO 三件套、分类建议、标签建议 | 1200 | `title`/`slug`/`summary`/`seoTitle`/`seoDescription`/`seoKeywords`/`categorySuggestion`/`tagSuggestions` |
| `metadata` | 只补摘要与 SEO | 800 | `summary`/`seoDescription`/`seoKeywords` |
| `proofread` | 校对错别字与病句 | 12000 | `revisedContent`/`suggestions` |
| `polish` | 润色 | 12000 | 同上 |
| `expand` | 扩写 | 4000 | 同上 |
| `shorten` | 缩写 | 4000 | 同上 |
| `translate` | 翻译（中↔英） | 4000 | 同上 |

**提示词里几个刻意的设计**：

1. **"必须只输出一个 JSON 对象，不要输出 Markdown 或解释"** —— 减少包装文本。
2. **给出字段级约束**：比如 slug「必须是语义清晰的小写 ASCII kebab-case，只能包含 a-z、0-9 和连字符」；`seoTitle` 不超过 160 字；`tagSuggestions` 最多 5 项且去重。
3. **给一个示例 JSON** —— few-shot 里「示例」比「描述」更有效。
4. **写"不虚构正文没有的信息"** —— 抑制幻觉。
5. **对改写类动作强调"保留原意和 Markdown 结构"** —— 因为输出会被直接写回编辑器，破坏结构就等于毁掉文章格式。

**temperature 用 0.3**（偏确定性），因为这是「信息抽取/结构化」任务，不是创意写作。

### ③ 代码落点

- system prompt 全集：`internal/aiclient/prompt.go:5`
- user prompt 组装：`internal/aiclient/prompt.go:48`
- 各动作 max_tokens：`internal/aiclient/prompt.go:60`
- temperature：`internal/aiclient/client.go:107`
- 返回结构定义：`internal/aiclient/client.go:56`

### ④ 可能的追问 + 应答

- **Q：为什么用 JSON 而不是让模型直接返回 Markdown？**
  A：因为一次要返回**多个结构化字段**（标题、slug、SEO、标签数组）。如果让它自由输出，解析就要靠正则猜，非常脆弱。JSON 是机器可读的契约。

- **Q：怎么保证它一定返回合法 JSON？**
  A：三层保障：① prompt 明确要求 + 给示例；② OpenAI 侧加 `response_format: json_object` 强制；③ **解析时容错**——`ParseAssistantJSON` 不直接 `Unmarshal` 整段内容，而是先找**第一个 `{`** 和**最后一个 `}`**，截取中间部分再解析。这一步能容忍模型在外面包了 ```json 代码块或者加了一句解释。

- **Q：为什么 proofread/polish 的 max_tokens 高达 12000？**
  A：因为这两个动作要**输出整篇修订后的正文**，而文章可能很长。其他动作只输出摘要或短段落，所以额度小。这是按「输出体积」而不是按「任务难度」配的。

- **Q：temperature 可以调吗？**
  A：**目前没有暴露给管理员配置**，硬编码 0.3。这是可以改进的点（不同动作理想温度不同，翻译和校对需要更低温）。

### ⑤ 诚实边界

- prompt 没有做系统性评测（没有评测集、没有对比不同 prompt 的效果）。**不要声称做过 prompt 调优实验。**
- 没有做输出内容的二次校验（比如 slug 是否真的符合 kebab-case 只靠 prompt 约束，后端没有强校验）。这是可以补的点。

## 主题：宽松解析与容错

### ① 一句话答案

模型输出不稳定，所以解析层刻意做得宽松：JSON 靠首尾花括号截取、响应缺字段不报错、错误体只取安全摘要。

### ② 展开讲 30–60 秒

**JSON 容错**：`ParseAssistantJSON` 的处理是——先 `TrimSpace`，空就直接报错；找到第一个 `{` 和最后一个 `}`，截取这一段再 `Unmarshal`。这样能容忍：

- 模型输出被 ```json ... ``` 包起来；
- 前面加了一句「这是结果：」；
- 后面多了一句「希望有帮助」。

**缺字段不报错**：`Response` 结构里所有字段都是 `string` / `[]string`，`Unmarshal` 时缺失字段就是零值。业务层按需取用（比如只关心 `title` 和 `slug` 是否填了）。这意味着**解析成功不等于字段都有效**，业务层需要自己判断。

**错误体处理**：上游返回非 2xx 时，会尝试从响应体里提取 `error.message` 或 `message`，但：

- 先做**密钥脱敏**（把 API Key 及其 URL 编码形式替换成 `[REDACTED]`）；
- 再做**长度截断**（最多 4096 字节）；
- 如果响应体太大或读不出来，就退化成 HTTP 状态文本。

### ③ 代码落点

- JSON 容错解析：`internal/aiclient/parse.go:9`
- 探针响应校验：`internal/aiclient/parse.go:26`
- 错误体提取与脱敏：`internal/aiclient/http.go:218`、`:241`
- 密钥脱敏实现：`internal/aiclient/http.go:342`
- 整体错误包装：`internal/aiclient/http.go:331`（`sanitizeError`）

### ④ 可能的追问 + 应答

- **Q：脱敏为什么要把 URL 编码形式也替换？**
  A：因为密钥可能出现在 URL 里（比如被拼进 query 或 path），此时它们在错误信息中会以 `%XX` 转义形式出现，只替换原始串会漏掉。

- **Q：为什么用首尾花括号截取，而不是用正则找 JSON？**
  A：正则匹配嵌套 JSON 很难写对。首尾截取是「足够好」的启发式：模型很少会输出两个独立 JSON 对象。**它也会误判**（比如正文里本来就有 `{` `}`），这是已知局限。

- **Q：解析失败怎么办？**
  A：返回错误给上层，接口返回可读的失败信息，并在前端做文案映射。**不会把原始模型输出直接回吐给前端**。

### ⑤ 诚实边界

- 首尾花括号截取是启发式，可能误判。
- 没有做「结构化输出重试」：解析失败不会自动让模型重试一次。这是一个明确的改进点。

## 主题：出站请求的 SSRF 防护与超时设计

### ① 一句话答案

AI 上游地址是管理员可配的，所以出站请求做了三层防护：**保存时**校验 URL 语法、**建连时**重新解析并拦截受限地址、**传输层**禁用代理与重定向；同时用「首字节超时 + 总超时 + 响应体上限」控制资源消耗。

### ② 展开讲 30–60 秒（这段是 AI 岗最容易被深挖的地方）

**攻击场景**：如果管理员账号被盗（或者管理员自己填错），把 Base URL 填成 `http://172.30.127.2:3306`、`http://169.254.169.254/...`（云元数据）或某个内网服务，那么后端就会**替攻击者去访问内网**。这就是 SSRF。

**防护动作**：

1. **保存时（语法层）**：校验必须是合法的 HTTP/HTTPS URL；**禁止携带 userinfo（凭据）、query 和 fragment**。这条对 RAG 上游更严格，因为通用 URL 校验（头像那种）允许 query，而模型服务 URL 不允许——避免管理员误把额外凭据保存下来并透传给上游。

2. **建连时（网络层，最关键）**：自定义 `DialContext`，**每次新建 TCP 连接前重新解析域名**，然后：
   - 只要解析结果里**有任何一个是受限地址，就整体拒绝**（不是只过滤掉那个 IP）—— 这同时防住「公私混合解析」和 **DNS rebinding**（第一次解析给公网 IP 骗过校验，真正连接时解析到内网）；
   - 校验通过后，**直接连到已经校验过的 IP**，而不是把域名再交给系统去解析（否则等于又给了重新解析的机会）；
   - 对透明代理的 **Fake-IP（`198.18.0.0/15`）** 做了特殊处理：443 端口如果只解析到这个网段，视为 Fake-IP，保留域名交给系统拨号；填显式 IP 或用其他端口仍然拒绝。

3. **传输层**：`Proxy: nil`（**不继承环境代理**，因为代理会在代理端重新解析域名，本进程就无法保证连接落点）；`CheckRedirect` 返回 `ErrUseLastResponse`（**不跟随重定向**，否则 302 到内网就白防了）。

**超时与体积三重限制**：

- **首字节超时**：默认 60 秒（`ResponseHeaderTimeout`），避免连接建立后上游一直不吐数据；
- **总请求超时**：默认 600 秒（通过 `context.WithTimeout` 控制）；
- **响应体上限**：1 MiB；**错误信息上限**：4096 字节。

另外连接池是共享的，**首字节超时变化时会重建 Client 并关闭旧空闲连接**（避免复用旧超时配置的连接）。

- 受限客户端构造：`internal/aiclient/http.go:71`（`NewPublicHTTPClient`）
- 连接池与代理/重定向设置：`internal/aiclient/http.go:37`、`:54`（`Proxy: nil`）、`:63`（`CheckRedirect`）
- 拨号时的解析与校验：`internal/aiclient/http.go:149`

- RAG 复用同一个受限客户端：`internal/ragclient/dashscope.go:117`

### ④ 可能的追问 + 应答

- **Q：为什么 Qdrant 不用这个受限客户端？**
  A：因为 Qdrant 是**进程配置提供的内部依赖**（`APP_QDRANT_URL`，默认 `http://qdrant:6333`），地址本身就在 Docker 私有网络里，用公网校验反而会被自己拒绝。所以 Qdrant 用独立的内部客户端，但**同样禁止重定向、限制响应体大小、并在错误时不传播响应体**（因为错误体里可能含文章分段）。

- **Q：怎么防 DNS rebinding？**
  A：核心是「**校验和连接使用同一份解析结果**」。校验后直接连校验过的 IP，不把域名再解析一次。再加上「只要有一个 IP 受限就整体拒绝」，混合解析也绕不过。

- **Q：为什么错误信息要限制大小？**
  A：上游错误页可能很大，甚至是个 HTML 页面；同时也可能**回显你发给它的请求内容**（含文章片段或密钥）。所以既限制读取量，又不把响应体本身放进错误对象。

### ⑤ 诚实边界

- 受限地址判定依赖 `validator.IsBlockedHostIP` 的实现，具体覆盖的网段清单需要看代码；本文不逐一列出，避免答错。
- Fake-IP 的特殊处理是针对透明代理环境的兼容，**真实企业代理环境未验证**。

## 主题：模型列表、连通性探测与降级

### ① 一句话答案

后台可以拉取上游模型列表，也可以对某个模型做一次低 token 的 JSON 探针测试并返回耗时；AI 未配置或不可用时，所有 AI 功能整体关闭，不影响博客主流程。

### ② 展开讲 30–60 秒

**模型列表**：`GET /models`（Anthropic 加 `limit=1000`），拿到后做**去空、去重、按字典序排序**，避免前端下拉框里出现重复项或顺序抖动。

**连通性探测（`TestModel`）**：给模型发一个固定的极简请求——system 说「只返回一个合法 JSON 对象，不要 Markdown」，user 说「返回 `{"ok":true}`」，`max_tokens` 只有 512。然后校验返回里确实有 `ok: true`。

这里有两个细节值得说：

1. **探针要求 JSON 而不只是要求文本** —— 因为真正的业务场景要的就是 JSON，如果模型连这个都做不到，说明它不适合当这个用途的模型。
2. **即使失败也返回耗时** —— `TestModel` 用 `defer` 记录 `time.Since(startedAt)`，所以超时和网络错误也能告诉你「花了多久才失败」，这对排查超时配置很有用。

**降级路径**：

| 状态 | 表现 |
| --- | --- |
| AI 未配置（无 Key 或字段不全） | `EffectiveConfig` 返回「不可用」，AI 相关接口给出明确提示，编辑器里不显示 AI 按钮（前端策略函数判断） |
| 上游返回错误 | 映射成可读错误（含密钥脱敏），前端按错误类型给文案 |
| AI 限流超限 | 429，提示太频繁（AI 辅助 20 次/分，fail-open） |
| 整个 AI 能力不想要 | 后台清空配置即可，博客功能完全不受影响 |

- 模型列表：`internal/aiclient/client.go:116`、归一化 `:210`
- 探针：`internal/aiclient/client.go:156`、`internal/aiclient/parse.go:26`
- 探针 token 上限：`internal/aiclient/client.go:17`

- 前端错误文案：`frontend/src/utils/aiErrorMessages.ts`、`frontend/src/pages/admin/aiSettingsPolicy.ts`

### ④ 可能的追问 + 应答

- **Q：为什么「测试」要用真实模型请求而不是只 ping 一下？**
  A：因为连通性不等于可用性。服务能连上，但模型名填错、没有该模型权限、或者不支持 JSON 输出，这些只有在真实调用时才会暴露。用探针能一次把这些问题都测出来。

- **Q：为什么测试接口也要限流？**
  A：因为它会**真的消耗上游额度**。同一个 `aiRateLimit`（20 次/分）也挂在模型列表和测试接口上，防止管理员误点或脚本刷。

- **Q：AI 不可用会不会影响发文章？**
  A：不会。AI 是纯增强功能，所有调用点都有「不可用就隐藏入口/给出提示」的处理。**这是「可选能力不能拖垮主流程」原则的一部分。**

### ⑤ 诚实边界

- 上游模型的实际可用性、限流额度、计费行为**我只在本地验证过链路可用**（审查报告记录模型列表请求成功、`qwen-plus` 探测成功），没有做并发与成本评估。
- 没有做「上游故障自动切换备用模型」的容灾。

## 可能被问倒的 3 个问题

1. **「你的 AI Key 是怎么保护的？如果有人拿到了你的数据库备份呢？」**
   → 应答思路：三层。第一，Key 是 AES-GCM 密文，不是明文；第二，解密密钥不是数据库里的东西，而是由进程环境里的 `APP_AUTH_ACCESS_SECRET` 派生出来的，所以光有数据库备份解不开；第三，密钥按用途隔离（`ai-settings` 和 `rag-settings` 两个派生域），一类泄露不影响另一类。**同时要诚实说明**：这是应用层加密，主密钥还是在进程环境里，没有 HSM/KMS 级别的保护。

2. **「管理员可以随便填 AI 的 Base URL，这安全吗？」**
   → 应答思路：这正是我做 SSRF 防护的原因。三层：保存时校验语法并禁止 URL 里带凭据/query/fragment；建连时每次重新解析域名，任一解析结果命中内网或保留地址就整体拒绝，并直接连校验过的 IP 以防 DNS rebinding；传输层禁用环境代理和重定向。**但我也要承认**：这防的是「后端替攻击者访问内网」，防不住「管理员故意把内容发给某个外部服务」——那是数据外发的合规问题，不是 SSRF。

3. **「如果模型返回的不是合法 JSON 你会怎么办？」**
   → 应答思路：解析层是宽松的——先截取第一个 `{` 到最后一个 `}` 再解析，能容忍 Markdown 包装和前后解释；OpenAI 侧还会用 `response_format: json_object` 强制。如果真解析失败，就返回可读错误并且**不会把原始输出回吐给前端**。诚实说：**目前没有做自动重试**，这是可以补的改进点。
