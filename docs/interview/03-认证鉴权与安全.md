## 本册速记卡

- **双 Token**：Access Token 走 `Authorization: Bearer`（默认 1800 秒），Refresh Token 走 **HttpOnly + SameSite=Strict Cookie**（默认 604800 秒）。
- **Refresh Token 落库**：数据库只存 **SHA-256 哈希**，不存明文。
- **两层会话失效**：`token_version`（用户级版本号）+ Redis 的「签发起始时间」截断值。
- **密码**：bcrypt（`DefaultCost`），未知账号也跑一次等开销比对来**抹平登录时序**。
- **限流**：Redis Lua 固定窗口；敏感接口 **fail-closed**（Redis 挂了直接拒），其余 fail-open。
- **并发控制**：Redis ZSET 租约（不是简单计数器），带心跳续租。
- **权限**：`user`/`editor`/`admin` 三级，路由层 + Logic 层**双重校验**。
- **可信代理**：默认不信任 `X-Forwarded-*`，只有 `RemoteAddr` 命中可信网段才使用。

## 主题：双 Token 认证总览

### ① 一句话答案

用 **Access Token 短期访问 + Refresh Token 长期续签**的组合：Access Token 放在 `Authorization: Bearer` 头里（前端内存持有），Refresh Token 放在 **HttpOnly Cookie** 里（JS 读不到），过期时前端调 `/auth/refresh` 换新的。

### ② 展开讲 30–60 秒

**为什么要两个令牌**：如果只有一个长期令牌，它一旦泄露，攻击者可以长期冒充你；如果只有一个短期令牌，用户就得频繁重新登录。所以拆成两个：

- **Access Token**：有效期 1800 秒（30 分钟），放在请求头里。它短命，即使泄露影响窗口也小。
- **Refresh Token**：有效期 604800 秒（7 天），放在 **HttpOnly + SameSite=Strict + Secure** 的 Cookie 里。前端 JS **无法读取**，所以 XSS 也偷不走它；浏览器每次请求自动带上。

**为什么 Refresh Token 不存 localStorage**：localStorage 对 JS 完全开放，任何一个 XSS 都能把它读走并长期使用。HttpOnly Cookie 从机制上提升了攻击门槛。

| 项 | Access Token | Refresh Token |
| --- | --- | --- |
| 载体 | `Authorization: Bearer` 请求头 | `noa_refresh_token` Cookie（HttpOnly） |
| 默认有效期 | 1800 秒 | 604800 秒 |
| 内容 | JWT（HS256），含 `userId`/`role`/`tokenVersion` | 32 字节随机数的 hex（**不是 JWT**） |
| 服务端存储 | 不存（无状态校验） | 数据库存 **SHA-256 哈希** |
| 能否被 JS 读取 | 能（前端内存 store 里） | **不能** |
| 环境变量 | `APP_AUTH_ACCESS_EXPIRE` | `APP_AUTH_REFRESH_EXPIRE` |

### ③ 代码落点

- JWT 签发与解析：`internal/authutil/token.go:18`（Claims）、`:41`（签发，HS256）、`:56`（解析并限定算法）
- Refresh Token 生成与哈希：`internal/authutil/token.go:75`、`:84`
- Cookie 读写：`internal/logic/auth/cookie.go:11`（名字）、`:20`（设置）、`:32`（清除）、`:46`（读取）
- 默认值：`etc/notes-of-ashen.yaml:19`、`.env.example:16`
- 前端携带凭证：`frontend/src/utils/http.ts:19`（`withCredentials: true`）、`:94`（注入 Bearer）

### ④ 可能的追问 + 应答

- **Q：为什么 Refresh Token 不是 JWT？**
  A：因为它需要**可撤销**。JWT 是无状态的，签发后在过期前一直有效，除非额外维护黑名单。Refresh Token 我用「随机串 + 数据库存哈希」的方式，撤销就是改数据库状态，天然支持「退出登录立即失效」。

- **Q：Cookie 为什么用 SameSite=Strict？**
  A：严格模式意味着**跨站请求不会带上这个 Cookie**，可以有效阻断 CSRF（攻击者从第三方页面发起的请求带不上 Refresh Token）。代价是从外部链接跳转进来时，某些场景下 Cookie 不会立即生效。

- **Q：`Secure` 属性怎么配？**
  A：由 `APP_AUTH_COOKIE_SECURE` 控制。**生产 HTTPS 必须是 true**；本地 HTTP 开发要设 `false`，否则浏览器根本不会保存这个 Cookie，刷新页面就恢复不了会话。这是本地开发最容易踩的坑。

- **Q：Access Token 里的 `role` 会不会过期？**
  A：可能会短暂滞后（用户改角色后旧 Access Token 里还是旧 role），但我**不依赖 Token 里的 role 做权限判断**——认证中间件每次都去查（或读 30 秒缓存）当前的 role 和 status。Token 里的字段只是冗余信息。

### ⑤ 诚实边界

- Access Token **没有**服务端黑名单/白名单（无状态校验），失效完全依赖 `tokenVersion` 和 Redis 截断值两个机制。
- Refresh Token 的轮换（rotation）在刷新时进行；审查报告记录了一个**尚未在线复现的竞态（S01）**：刷新的「撤销旧令牌」与「签发新令牌」之间如果插入改密，理论上可能拿到改密后仍有效的会话。详见本册最后。

## 主题：会话失效（改密码后旧令牌为什么立刻不能用）

### ① 一句话答案

两个机制配合：**用户级 `token_version`**（改密/改角色/改状态就 +1）负责让「某个用户的全部旧令牌」失效；**Redis 中的签发起始时间截断值**负责让「某个时间点之前签发的所有令牌」失效。

### ② 展开讲 30–60 秒

**机制一：`token_version`（精确到用户）**

签发 Access Token 时把当前用户的 `token_version` 写进 JWT 声明。认证中间件每次都会：

1. 解析出 `claims.TokenVersion`；
2. 从数据库读当前 `token_version`；
3. **两者不一致就拒绝**。

这样只要在「改密码 / 改角色 / 改状态」时执行 `token_version = token_version + 1`，该用户所有已签发的 Access Token 立刻失效——不需要维护令牌黑名单。

**机制二：Redis 截断值（批量失效）**

Redis 里存一个「Access Token 签发起始时间」的截断值。如果令牌的 `IssuedAt` 早于这个值，就拒绝。用于需要「一次性让所有令牌失效」的场景（比如怀疑大面积泄露时的紧急手段）。项目里同时保留了本地默认值和 Redis 值，**取两者中较大的**。

**为什么两个都要**：`token_version` 是「按用户精确失效」的常规手段；截断值是「全局紧急失效」的兜底。两者职责不同，不重复。

### ③ 代码落点

- Claims 含版本：`internal/authutil/token.go:18`
- 版本比对：`internal/middleware/auth.go:107`、`:114`
- 截断值判定：`internal/middleware/auth.go:132`
- 版本自增：`model/user.go:239`（改密）、`:319`（改状态/角色）
- 读取版本：`model/user.go:256`

### ④ 可能的追问 + 应答

- **Q：为什么不用 Redis 黑名单存失效的令牌？**
  A：黑名单要为每个令牌存一条记录到它过期为止，7 天的 Access 令牌会积累大量键；而版本号只需**一个整数**就能让该用户的所有旧令牌失效。用更少的存储解决同一问题。

- **Q：认证每次都查数据库，不会很慢吗？**
  A：所以我在前面加了一层 **30 秒 TTL 的用户快照缓存**，只缓存 `role` 和 `status` 两个字段。而 `token_version` 是每次都实时查的（这个便宜且必须准确）。缓存未命中或 Redis 故障时降级直查数据库。

- **Q：改密码后 Refresh Token 也要失效吗？**
  A：要。改密的事务里同时递增 `token_version` 并撤销该用户的 Refresh Token，然后清认证缓存。

### ⑤ 诚实边界

- 认证缓存有最多 30 秒的窗口，但**改角色/禁用等操作会主动删除缓存**，所以正常路径下是立即生效的。
- S01 竞态：`刷新流程先撤销旧 Refresh Token，再签发新令牌`，两步之间如果插入改密，理论上存在问题。**这是已知但未在线复现的风险**，正确解法是把「校验凭据时的版本」与「签发」绑定在同一个事务里。

## 主题：注销流程为什么用「可选认证」

### ① 一句话答案

`/auth/logout` 用的是**可选认证**：Access Token 有效就带上用户上下文，无效/过期也**继续执行**，因为撤销 Refresh Token 靠的是 Cookie 而不是 Access Token。

### ② 展开讲 30–60 秒

这里有个容易做错的细节：用户点了「退出登录」时，他的 Access Token **很可能已经过期了**（30 分钟有效期）。如果注销接口要求必须通过认证，那么「过期的用户退不出去」，而且 Refresh Cookie 也没被清掉——下次打开页面又自动登录回来了，体验很糟。

所以我给注销用可选认证：解析出用户就注入上下文（可以用来收尾会话记录），解析不出来也照样往下走，而是用 Cookie 里的 Refresh Token 完成撤销并清理 Cookie。

另外前端也有配合：注销请求**失败时不触发 refresh**。因为如果注销失败还去刷新，而刷新又因为网络问题失败，前端会把会话清掉并跳转，用户会以为「注销成功了」，但服务端的 Refresh Token 可能还在。

### ③ 代码落点

- 路由使用可选认证：`internal/handler/routes.go:83`
- 中间件两种模式：`internal/middleware/auth.go:64`（必须）、`:78`（可选，注释解释了只能用于会话收尾）
- 前端不刷新注销请求：`frontend/src/utils/http.ts:43`

### ④ 可能的追问 + 应答

- **Q：可选认证会不会被滥用成「绕过鉴权」？**
  A：`HandleOptional` 的注释里我明确写了它**只用于注销这类可以由其他凭据完成的会话收尾操作，普通受保护接口必须用 `Handle`**。这是靠约定 + 代码审查保证的。

- **Q：匿名调注销会怎样？**
  A：会返回 200 并清理 Cookie（幂等）。审查报告里也实测过这条：匿名 `POST /api/v1/auth/logout` 返回 200 并清理 Refresh Cookie。这样设计是为了避免暴露「这个 Cookie 有效吗」的信息。

### ⑤ 诚实边界

- RAG 聊天接口也用了可选认证，因为它支持匿名访问级别。**这引出了一个已知问题（R04）**：过期的 Access Token 会被当作匿名处理，导致访问级别检查返回 403 而不是 401，前端不会触发续期。见本册最后。

## 主题：密码安全与登录时序抹平

### ① 一句话答案

密码用 **bcrypt** 存储（自带随机盐），成本用 `DefaultCost`；登录时**无论账号是否存在都执行一次 bcrypt 比对**，避免通过响应时间判断「这个账号注册过没有」。

### ② 展开讲 30–60 秒

**bcrypt 的两个特性**：

1. **自带盐**：每次哈希都用随机盐，所以同一个密码两次哈希结果不同，彩虹表失效。所以数据库里不需要额外的 salt 列。
2. **可调成本**：`DefaultCost`（10）意味着故意算得慢，让暴力破解的成本上升。

**时序攻击是什么**：如果「账号不存在」时直接返回错误，而「账号存在但密码错」时要跑一次 bcrypt（耗时几十毫秒），攻击者就能通过**响应时间差异**枚举出哪些账号是有效的。

我的处理是：预置一个 `dummyPasswordHash`，当账号不存在时也拿这个假哈希跟用户输入的密码跑一次 bcrypt 比对（结果丢弃），让两条分支的耗时一致。

### ③ 代码落点

`internal/logic/auth/auth.go:24`（引入 bcrypt）、`:109`（注册时 `GenerateFromPassword` + `DefaultCost`）、`:196`（`dummyPasswordHash` 注释）、`:223`（未知账号也跑一次比对）、`:231`（正常比对）。

### ④ 可能的追问 + 应答

- **Q：bcrypt 有什么坑？**
  A：**72 字节上限**。bcrypt 只处理前 72 字节，超过的部分被忽略；而且超过时不同版本的库行为不一致（有的直接报错）。我的业务校验是按「字符数」限制 8–128，没有统一到 UTF-8 字节，导致 73 字节的 ASCII 密码注册会返回 500 而不是可理解的 4xx。**这是审查报告 R05 记录的实测问题**，正确做法是统一按 UTF-8 字节校验，且长度校验必须早于验证码消费。

- **Q：为什么不用 Argon2？**
  A：Argon2 在抗 GPU 破解上更强，但 bcrypt 在 Go 生态里更成熟、`golang.org/x/crypto` 直接提供，且对当前场景足够。取舍是承认它不是最强选项。

- **Q：密码错误次数有限制吗？**
  A：有 IP 维度的登录限流（每分钟 5 次，fail-closed）。**但没有按账号的锁定策略**——这是可以补的点（按账号计数 + 指数退避）。

### ⑤ 诚实边界

- 密码长度校验与 bcrypt 72 字节不一致（R05），是**未修复的已知问题**。
- 找回密码和修改密码的调用链里，验证码是在生成哈希之前被消费的，这可能导致「无效的超长密码同时消耗掉验证码」。审查报告记录为静态问题，**未在线复现**。

## 主题：验证码体系

### ① 一句话答案

两类验证码都存在 Redis：**图形验证码**（base64Captcha 生成，5 分钟过期）和**邮箱验证码**（按用途隔离 key，5 分钟过期，带冷却）；还有一个特例——**首个管理员注册可以跳过邮箱验证码**。

### ② 展开讲 30–60 秒

**图形验证码**：用 `base64Captcha` 驱动生成图片，答案是随机码，存 Redis（key 带用途，5 分钟 TTL），校验时用 Lua 脚本原子比对并消费（防重放）。

**邮箱验证码**：也是随机数字，按「用途 + 邮箱」隔离 key，所以我用同一个邮箱在「注册」和「找回密码」之间不会串码。有 5 分钟 TTL，并且有一个「冷却 key」防止连续轰炸。

**首个管理员特例**：项目约定是「第一个注册用户自动成为 admin」。如果邮箱服务默认关闭，首个管理员注册时**没有渠道拿验证码**，所以这里允许跳过邮箱验证码。判断条件是「用户表为空 且 邮箱服务关闭」；后续注册仍然需要 `register` 用途的邮箱验证码。

### ③ 代码落点

`internal/security/code.go:21`（邮箱码 TTL）、`:23`（图形码 TTL）、`:26`（消费用的 Lua 脚本）、`:48`（图形验证码生成）、`:80`（校验）、`:105`（存邮箱码）、`:135`（消费邮箱码）、`:195`–`:223`（各种 key 的构造）、`:249`（captcha 驱动）。首个管理员逻辑在 `internal/logic/auth/auth.go`。

### ④ 可能的追问 + 应答

- **Q：为什么用 Lua 脚本消费验证码？**
  A：为了保证「比对 + 删除」是**原子**的。如果用 `GET` 再 `DEL`，两个并发请求可能都通过校验（都读到了同一个正确码），然后各自删除。Lua 在 Redis 里单线程执行，能避免这种竞态。

- **Q：验证码接口会不会泄露「这个邮箱注册过没有」？**
  A：**会，这是已知问题（R06）**。当前实现里「邮箱占用查询」先于「图形验证码校验」执行，所以用同一个无效图形验证码请求不同邮箱，会拿到 409（已注册）和 400（验证码过期）两种不同响应，攻击者不用通过人机校验就能枚举邮箱。改法是调整执行顺序，并在确认邮箱归属前统一公开响应。**这是很好的「我发现并定位了安全细节问题」的素材。**

### ⑤ 诚实边界

- R06 未修复，只是识别出来了。
- 未做短信验证码；邮箱验证码只在 SMTP 配置好时可用。

## 主题：限流体系（fail-closed vs fail-open）

### ① 一句话答案

限流用 **Redis + Lua 的固定窗口**实现；**敏感接口（登录、注册、发验证码、找回/改密、RAG）在 Redis 不可用时直接拒绝（fail-closed）**，其余接口在 Redis 故障时放行（fail-open）。

### ② 展开讲 30–60 秒

**实现方式**：一段 Lua 脚本做 `INCR`，如果结果是 1（第一次）就 `PEXPIRE` 设置窗口过期时间，最后返回当前计数；超过上限就返回 429。用 Lua 是为了让「自增 + 首次设过期」原子执行，避免并发下丢掉过期设置导致键永不过期（那就变成永久封禁了）。

**为什么用固定窗口而不是滑动窗口**：固定窗口实现简单、内存占用小（一个键一个整数）。代价是边界效应——窗口交界处理论上可以放过约 2 倍流量。对于「防暴力破解」这个目的够用了。

**fail-open / fail-closed 的取舍**（这是这一节最值得讲的点）：

| 模式 | Redis 不可用时的行为 | 用在哪些接口 | 为什么 |
| --- | --- | --- | --- |
| **fail-closed** | 直接返回 **503** 拒绝 | 登录(5/分)、注册(5/分)、发验证码(5/分)、找回密码(5/分)、改密(5/分)、RAG 聊天(12/分) | 这些接口一旦失去限流保护就会变成**暴力破解/滥用入口**，宁可短暂不可用 |
| **fail-open** | 放行请求 | 图形验证码(30/分)、流量上报(120/分)、点赞(60/分)、AI 辅助(20/分) | 这些是体验型接口，Redis 抖动时不该让整个站点不可用 |

设计原则是：**安全相关宁可拒绝，体验相关宁可放行**。

另外每个限流调用都有 200 毫秒超时（`rateLimitRedisTimeout`），避免 Redis 慢查询把请求拖死。

### ③ 代码落点

`internal/middleware/ratelimit.go:27`（failClosed 字段与注释）、`:32`（默认构造 = fail-open）、`:52`（fail-closed 构造）、`:58`（200ms 超时）、`:60`（Lua 脚本）、`:68`（处理逻辑）、`:70`（client 为 nil 的处理）、`:85`（eval 失败处理）、`:94`（超限返回 429）。各项限流的注册与数值：`internal/handler/routes.go:39`。

### ④ 可能的追问 + 应答

- **Q：固定窗口的边界问题怎么缓解？**
  收：可以改成滑动窗口（用 ZSET 存时间戳）或者令牌桶。代价是内存和复杂度上升。我这里的 RAG 并发控制其实就用了 ZSET，因为它需要的是「当前活跃数」而不是「单位时间次数」。

- **Q：限流按什么维度？**
  A：按 **IP**。IP 的取值遵循可信代理规则（见下一节），所以伪造 `X-Forwarded-For` 不会绕过限流。

- **Q：为什么登录限流是每分钟 5 次？**
  A：经验值，兼顾防爆破和不影响正常用户输错密码。生产环境如果要更严，可以加按账号维度 + 指数退避。

### ⑤ 诚实边界

- 固定窗口的理论突刺问题存在；**没有做过攻击流量压测**，阈值是经验值而不是测出来的。
- 未实现按账号维度的锁定策略。

## 主题：分布式并发租约（比限流更值得讲的设计）

### ① 一句话答案

SSE 长连接不能用「计数器」限制并发，我用 **Redis ZSET 存「租约令牌 → 到期时间」**：领取时原子清理过期项、满了拒绝；释放时只删自己的令牌；运行期用心跳续租，**续租失败主动取消上游请求**。

### ② 展开讲 30–60 秒

**为什么不能用简单计数器**：这是代码注释里写明的核心问题——如果只是 `INCR`/`DECR`，一个**超过 TTL 的旧请求**（比如用户挂着一个 SSE 很久）在计数器过期之后才结束，它的 `DECR` 会把**后来请求**占用的槽位错误地释放掉。结果就是并发限制形同虚设。

**用 ZSET 的解法**：

- **score 是每个租约的到期时间**，member 是**每个请求唯一的令牌**（16 字节随机数的 hex）。
- **领取**：Lua 脚本先 `ZREMRANGEBYSCORE` 清理已过期的成员，再看 `ZCARD` 是否达到上限；没满就 `ZADD` 自己的令牌并把整个 key 的过期时间设为最晚租约到期时间。
- **释放**：只 `ZREM` 自己的令牌，不会影响别人；如果集合空了就删 key。
- **续租**：后台心跳每 `TTL/3` 续一次；**如果续租返回失败（令牌已不在集合里，说明租约被别人抢了或者 Redis 出问题），就调用 `cancelStream()` 主动取消下游 context**。

最后这一步是最关键的：对于 SSE，取消下游 context 会**立即中止上游模型请求**。这就保住了 fail-closed 的语义——宁可不回答，也不能在失去全局配额的情况下继续烧模型额度。

**参数**：RAG 并发上限 2、租约 TTL 12 分钟（比模型单次请求超时更长，避免长回答被误判过期）。

### ③ 代码落点

`internal/middleware/concurrency.go:26`（注释：为什么必须 fail-closed）、`:57`（核心注释：为什么用令牌而不是计数器）、`:60`（领取脚本）、`:74`（释放脚本）、`:87`（续租脚本）、`:103`（Redis 不可用直接 503）、`:124`（租约丢失时取消下游）、`:137`（心跳，间隔 = TTL/3）、`:194`（令牌生成）。注册：`internal/handler/routes.go:49`。

### ④ 可能的追问 + 应答

- **Q：心跳为什么是 TTL/3？**
  A：留两次容错机会。如果一次心跳因为网络抖动失败，还有两次机会续上，不至于把活跃请求误判为过期。间隔太密会增加 Redis 压力，太疏则容错不足。

- **Q：租约令牌泄露有风险吗？**
  A：令牌不返回给客户端、不作为鉴权凭据，只用于在 Redis 集合里标识自己。代码里 `crypto/rand` 极罕见失败时会回退到纳秒时间戳形式。

- **Q：多实例部署下这个方案成立吗？**
  A：成立，而且正是为多实例设计的——租约在 Redis 里，任意实例都能正确领取和释放。不过**真实的跨主机多副本并发行为没有做过压测**，只有逻辑上的原子性保证。

### ⑤ 诚实边界

- 单机验证；多副本并发未压测。
- 续租失败会中断用户正在进行的问答，这是**有意的取舍**（可用性换配额安全）。

## 主题：权限模型与越权防护

### ① 一句话答案

三级角色 `user` / `editor` / `admin`；**路由层做一次鉴权，Logic 层再做一次业务校验**；并且有管理员自我保护规则。

### ② 展开讲 30–60 秒

**双重校验（defense in depth）**：

- **路由层**：`authRequired` 包装保证「必须登录」，把用户 ID 和 role 放进 context。
- **Logic 层**：业务函数再检查一次权限。比如所有 `/admin/*` 接口在 logic 入口会调 `RequireAdmin`（RAG 的 `Settings`/`Rebuild` 等第一行就是它）。

**为什么要两次**：路由层只能判断「登录了没」，判断不了「这个操作符不符合业务规则」。而且如果将来有人加路由时忘了包装中间件，logic 层的检查能兜底——**权限检查不应该是单点**。

**管理员自我保护规则**：

- 管理员不能给自己降权、不能禁用自己（否则一处误操作就把自己锁在外面）；
- 最后一个 active admin 不能被移除（否则就没有人能管理系统了）；
- 角色/状态变化会递增 `token_version` 并撤销目标用户的 Refresh Token，让变更立即生效。

### ③ 代码落点

- 双重校验示例：`internal/logic/admin/admin.go`、`internal/logic/rag/rag.go:44`（`RequireAdmin`）
- 路由鉴权包装：`internal/handler/routes.go:51`
- 角色/状态变更与版本自增：`model/user.go:319`
- 边界规则复核：`docs/PROJECT-REVIEW.md` 第 5 节「角色与管理员边界」
- 前端角色判断：`frontend/src/components/ProtectedRoute.tsx`、`frontend/src/store/authPolicy.ts`

### ④ 可能的追问 + 应答

- **Q：前端也做了角色判断，是不是就够了？**
  A：不够，前端判断只是**体验**（不该显示的菜单别显示），**真正的权限必须在服务端**。前端的任何判断都能被绕过（改 JS、直接调接口）。

- **Q：editor 和 admin 的区别是什么？**
  A：editor 能做内容相关操作（写/改文章等），但用户管理、站点设置、AI/RAG 设置、备份恢复这些系统级操作只有 admin 能做。具体边界以 `internal/logic` 里的 require 调用和路由分组为准。

- **Q：怎么防止横向越权（看别人的私有数据）？**
  A：按资源归属过滤。比如 RAG 会话是私有的，读取时会话必须属于当前用户；后台文章列表则按角色决定可见范围。**这类判断我在 logic 层做，不放 SQL 之外的地方。**

### ⑤ 诚实边界

- 我没有做完整的**权限矩阵文档化**（哪些角色能调哪些接口的表格），目前靠路由分组 + logic 检查。这是一个可改进项。
- 跨账号隔离的自动化测试覆盖了一部分（集成测试里的权限用例），但审查报告提到**真实跨账号 E2E 还需要在隔离环境补做**。

## 主题：可信代理链（容易被忽视的加分点）

### ① 一句话答案

**默认不信任任何转发头**。只有当请求的 `RemoteAddr` 落在 `APP_TRUSTED_PROXY_CIDRS` 里时，才使用 `X-Forwarded-For` / `X-Real-IP` 来判断客户端 IP。

### ② 展开讲 30–60 秒

如果没有这条规则会怎样：攻击者直接请求服务，自己伪造一个 `X-Forwarded-For: 1.2.3.4`，如果你的代码无条件相信这个头，那么：

- **限流可被绕过**：攻击者每次换一个伪造 IP，就永远命中不了限流；
- **流量统计被污染**：来源统计全是假数据；
- **链接生成可能被污染**：绝对链接可能基于伪造的 Host/IP 生成。

所以规则是：**先确认「谁在跟我说话」（RemoteAddr），再决定信不信他转发的信息**。

Nginx 侧也做了对应的收窄：只 `set_real_ip_from` 直接上游（默认是 Compose 网桥网关 `172.30.127.1/32`），并且要求 `WEB_TRUSTED_PROXY_CIDR` **禁止配置宽泛公网网段**。API 侧默认只信任 Web 容器的固定地址。

### ③ 代码落点

- 可信代理判定：`internal/httphelper/helper.go`（`Meta` / `ForwardedOptions`）
- 中间件传入可信网段：`internal/handler/routes.go:147`
- Nginx 侧：`deploy/nginx/default.conf:46`
- 环境变量：`.env.example:11`（`WEB_TRUSTED_PROXY_CIDR`）、`:105`（`APP_TRUSTED_PROXY_CIDRS`）、`docker-compose.yml:106`
- 项目约定：`AGENTS.md`「项目已知约束」最后一条

### ④ 可能的追问 + 应答

- **Q：多层代理怎么办？**
  A：配置里支持逗号分隔多个 CIDR（Web 前面若还有可信外层代理，把 Web 的 /32 和它的出口 CIDR 都写上）。核心原则是**只信任你确实控制的那一跳**。

- **Q：为什么链接生成也要受这个影响？**
  A：因为有些链接需要「绝对地址」（RSS、Sitemap、分享链接）。如果信了伪造的 Host，生成的链接就会指向攻击者的域名。这个项目里更稳的做法是**用站点设置里的 `siteBaseUrl` 固定规范地址**，只有它为空时才回退到请求地址。

### ⑤ 诚实边界

- `siteBaseUrl` 为空时回退到请求基址，这在本地没问题，但**生产必须填正式 HTTPS 域名**（`docs/PROJECT-REVIEW.md` 把它列为发布前必办项）。这就是审查报告里那条 P2/P3 问题。

## 主题：出站安全（SSRF）与数据/文件安全（概览）

### ① 一句话答案

**出站**：AI 上游地址由管理员配置，所以建连时重新解析域名、拦截内网与保留地址、不继承代理、不跟随重定向。**数据与文件**：备份归档加密 + 清单校验 + 恢复租约；媒体用内容哈希寻址并原子发布。

### ② 展开讲 30–60 秒

**SSRF 三个关键动作**（详细在 `04-AI大模型接入.md`）：

1. **保存时**校验 URL 语法，并且**禁止携带凭据、query 和 fragment**（避免管理员误把额外凭据存进去并转发给上游）；
2. **建连时**（每次新建 TCP 连接）重新解析域名，只要解析结果里有**一个**受限地址就整体拒绝——这同时防住了 DNS rebinding 和「公私混合解析」；
3. **不继承环境代理、不跟随重定向**——因为代理会在代理端重新解析域名，重定向可以把你带到内网。

**备份与恢复的安全点**：

- 导出用 **age**（scrypt 口令派生）加密；
- 归档里有 `manifest.json`，记录每个媒体文件的 SHA-256 和大小；恢复时逐个校验；
- 校验入口数量、清单大小、解压后总大小（防 zip 炸弹）；
- **恢复租约**（Redis 实现）+ 进程内锁，保证同一时间只有一个恢复在跑；
- 数据库里有**恢复标记（marker）**，配合媒体目录的暂存/发布语义，让进程崩溃后能重新收敛：有标记就完成发布，没标记就回滚暂存目录。

**媒体安全**：上传时校验「真实的图片内容 + 扩展名 + MIME + 大小」，用 SHA-256 做内容寻址（同一张图重复上传只存一份），写入用「临时文件 + rename」的原子方式；删除**先检查引用关系**（有没有文章在用它当封面），然后 `rename` 到隔离目录而不是直接 `unlink`，失败时还能恢复。

### ③ 代码落点

- SSRF：`internal/aiclient/http.go:149`
- RAG 上游 URL 校验：`internal/rag/settings.go:99`
- 备份导出与恢复：`internal/logic/backup/backup.go:64`（Export）、`:147`（age 加密）、`:188`（Restore）、`:202`（获取租约）、`:249`（读归档）、`:442`（`readArchive` 校验）
- 启动时恢复收敛：`internal/logic/backup/backup.go:344`、`cmd/notes-of-ashen/main.go:99`
- 媒体：`internal/logic/media/media.go:40`（允许的格式）、`:48`（内容寻址 key 规则）、`:88`（SHA-256）、`:153`（内容校验）、`:209`（删除与隔离）、`:299`（原子写入）

### ④ 可能的追问 + 应答

- **Q：备份为什么要加密而不是加个密码校验就行？**
  A：因为归档里有**全部用户数据和媒体文件**，落盘或传输过程中一旦泄露就是全量泄露。用 age + scrypt 口令派生，归档本身是密文。

- **Q：媒体为什么用 SHA-256 做文件名？**
  A：因为内容寻址带来两个好处：**天然去重**（同一张图只存一份）和**可缓存**（Nginx 上 `immutable` + 一年过期，因为文件名和内容绑定，内容变了文件名就变了）。

- **Q：恢复失败会不会把数据搞坏？**
  A：恢复用租约串行化，并且媒体先写暂存目录、数据库里写 marker，最后才发布。所以最坏情况是「暂存目录没发布」，而不是「媒体被半覆盖」。启动时会做一次收敛。

### ⑤ 诚实边界

- 恢复流程的**崩溃收敛逻辑**在代码层完整，但真实「杀掉进程再启动」的演练我没有全部覆盖；审查报告也明确说真实备份恢复演练应该在隔离环境补做。
- 异地副本、跨主机回滚未验证。

## 可能被问倒的 3 个问题

1. **「JWT 和 Session 你怎么选的？」**
   → 应答思路：我用了**混合方案**。Access Token 是无状态 JWT（好处是不用每次查 session 存储、多实例天然可扩展），但我加了 `token_version` 这个轻量的状态校验来获得「可撤销」能力。Refresh Token 则完全走**有状态**（数据库存哈希），因为它必须能撤销。所以不是二选一，而是按「需不需要立即撤销」分别设计。

2. **「XSS 能偷走 Token 吗？」**
   → 应答思路：Access Token 在前端内存里，如果页面被 XSS 注入，理论上可以被读走——但它的生命周期只有 30 分钟，而且攻击者要能注入 JS 才能拿到。Refresh Token 放在 **HttpOnly Cookie** 里，JS 读不到，所以攻击者无法获得长期凭证。另外我配了 **CSP**（`script-src 'self'`，不允许内联脚本），并且 Markdown 渲染没有把原始 HTML 直接注入页面的路径。**不要声称完全免疫 XSS。**

3. **「CSRF 呢？」**
   → 应答思路：主要防线是 Refresh Token Cookie 的 **SameSite=Strict**（跨站请求带不上它），再加上 CSP 和 `form-action 'self'`。需要说明的是：Access Token 走 `Authorization` 头，浏览器不会自动带上，所以写操作本身也需要显式带 Token，这天然比「靠 Cookie 鉴权」更抗 CSRF。
