## 三、自我介绍话术（可以直接背）

### 3.1 30 秒版

> 我做的是一个叫 **Notes of Ashen** 的个人博客系统，前后端分离。后端是 **Go + go-zero REST**，前端是 **React 18 + TypeScript + Vite**，用 **Docker Compose + Nginx** 部署。除了博客该有的文章、分类标签、媒体库、管理后台之外，我做了两块 **AI 能力**：一块是 AI 辅助写作，另一块是**基于 RAG 的知识库问答**——把公开文章切段、向量化存进 Qdrant，用户提问时先检索再让大模型基于证据回答，并用 SSE 流式返回。整个项目大约 3 万行 Go、2 万行前端代码，跑了 131 次提交。

### 3.2 2 分钟版（在上面的基础上接着讲）

> 我在设计上比较在意三件事。
>
> 第一是**可选能力不能拖垮主流程**。MySQL、Redis 是核心，必须起；RabbitMQ、Meilisearch、Qdrant 都是可选的，用 Docker Compose 的 profile 控制，关掉的时候后端自动降级——比如搜索关闭就回退到 MySQL 查询，RAG 关闭则问答入口直接不可用。
>
> 第二是**AI 相关的安全与可控**。AI 的 API Key 只存在数据库里，用 AES-GCM 加密，密钥由 `APP_AUTH_ACCESS_SECRET` 按**独立用途**派生，文章 AI 和 RAG 各用一套派生域，互相不能解密；AI 上游地址是管理员可配的，所以出站请求做了 SSRF 防护——建连时重新解析域名，只要命中内网、保留地址就拒绝，同时不继承系统代理、不跟随重定向。
>
> 第三是**RAG 的一致性和可恢复性**。文章改动会写一条同步任务到 MySQL，后台 Worker 用租约领取任务去更新向量；如果 embedding 配置变了，会换一个新的 epoch 全量重建，新旧向量在物理上隔离，避免维度混用。检索时我还会再校验一次文章可见性和内容哈希，保证转成草稿或已删除的文章不会被当作证据。

## 四、项目亮点与不足（统一口径）

### 4.1 亮点（挑 2–3 个讲，别全说）

| 亮点 | 一句话卖点 | 代码落点 |
| --- | --- | --- |
| RAG 来源可见性再校验 | 文章下线后，历史问答的引用和旧回答会被重新校验，不会把已下线内容当证据 | `internal/logic/rag/rag.go:461`、`:509` |
| 索引重建的 epoch 隔离 | 每个 collection 版本有单调递增 epoch，检索/删除都带 epoch 过滤，重建立刻 fail-closed | `internal/rag/worker.go:676`、`internal/ragclient/qdrant.go:119` |
| 分布式并发租约 | SSE 长连接用 Redis ZSET 做租约限制，令牌唯一、心跳续租、续租失败主动断开上游流 | `internal/middleware/concurrency.go:57`、`:124` |
| AI 密钥分级加密 | `v3:` AES-GCM 密文，密钥按用途派生（`ai-settings` / `rag-settings`），互不通用 | `internal/logic/ai/settings.go:501`、`internal/rag/secrets.go:85` |
| 出站 SSRF 防护 | 每次拨号重新解析并校验公网 IP，不继承代理、不跟随重定向 | `internal/aiclient/http.go:149` |
| 双 Token + 会话失效 | Access 走 Header、Refresh 走 HttpOnly Cookie，改密/改角色立即让旧令牌失效 | `internal/middleware/auth.go:104`、`model/user.go:239` |
| 迁移不可变 + 状态校验 | 28 个编号迁移，只能前向修复，启动时检测「镜像未知的已应用迁移」 | `internal/migration/migration.go` |
| 工程化测试 | 真实集成测试 + 三浏览器 E2E + 前端包体积预算 | `scripts/test-integration.ps1`、`frontend/scripts/check-bundle-size.mjs` |

### 4.2 不足（**务必按「发现 → 影响 → 改法 → 验证」四步说**，别只承认问题）

我在项目里做过两轮自我审计，写成了 `docs/PROJECT-REVIEW.md` 和 `docs/PROJECT-REVIEW-2026-09-14.local.md`，里面有 8 项实测确认的问题。挑最能体现工程意识的几条：

1. **Nginx 反代在 API 容器 IP 变化后 502**（R01）
   - 发现：静态 `proxy_pass http://api:19000` 在加载配置时解析地址，容器重建后 IP 变了但 Nginx 还在连旧 IP；`resolver` 指令并不会让这种写法持续更新解析结果。Web 容器自己还是 healthy，因为它的探针只探静态首页。
   - 影响：页面外壳能打开，但所有 API 都不可用。
   - 改法：改用能跟随 Docker DNS 更新的上游写法（变量 + `resolver`），并把 Web 的就绪检查覆盖到 API 反代链路。
   - 验证：重建 API 容器让 IP 变化后，对外请求自动恢复；API 反代失败时就绪检查不得继续报成功。

2. **全局乱码转换会改写并持久化 Markdown 原文**（R02）
   - 发现：响应拦截器对所有字符串递归做 `fixVisibleMojibakeDeep`，包括正文和代码块。作者如果就是要展示编码字面值，会被改掉并保存回数据库。
   - 影响：文章原文可能被静默篡改。
   - 改法：数据层保持原始字符串，历史乱码改成定向修复工具，不做全局自动转换。
   - 验证：含中文、Latin-1 字面值、编码示例和代码块的文章，创建/读取/编辑/保存/导出后原文一致。

3. **RAG 过期令牌返回 403，无法触发前端续期**（R04）
   - 发现：RAG 复用了「可选认证」中间件，过期凭据被当成匿名访问，访问级别检查再返回 403；前端只对 401 续期。
   - 影响：登录用户停留久了提问会失败。
   - 改法：区分「缺少凭据」和「凭据失效」，失效返回 401。
   - 验证：`guest`/`user`/`editor` 三档 × 有效/缺失/过期/撤销四种凭据组合全覆盖。

4. **发布 tag 可复用，制品追溯不可靠**（`docs/PROJECT-REVIEW.md` 第 4 节）
   - 发现：同一个 tag 被重新构建后指向了不同镜像，发布历史里记录的镜像 ID 和实际运行的不一致。
   - 影响：回滚边界不可靠。
   - 改法：禁止覆盖已存在的发布 tag，发布记录同时保存镜像 digest、Git commit 和工作区状态，脏工作区默认拒绝发布。
   - 验证：同一个 tag 不能被重新指到不同镜像；从发布记录能唯一解析出当前运行镜像。

5. **前端首屏体积预算只覆盖入口文件**（O02）——入口约 311 KiB，但 HTML 直接引用的三个脚本合计 563 KB（gzip 186 KB）。改法是把直接引用与预加载资源一起纳入预算。

> **面试技巧**：主动说「我列了 8 项问题并做了优先级排序（P1/P2/P3）」，比含糊说「还有些小 bug」强得多。但**不要只讲不足不讲改法**，那会显得你在自我否定。

## 五、现场演示脚本（如果要开电脑演示）

按这个顺序演示，3–5 分钟能展示完主要能力：

1. **首页 / 文章详情**（10 秒）：说明 Markdown 渲染管线——代码高亮、LaTeX 公式、Mermaid 图、图片灯箱；指出这就是前端按需加载的体现。
2. **登录**（10 秒）：打开浏览器开发者工具 Network，指出 **refreshToken 在 HttpOnly Cookie 里、JS 读不到**；Access Token 在 `Authorization: Bearer` 头里。
3. **后台写文章 + AI 辅助**（60 秒）：点「AI 补全」，说明它一次性返回标题、slug、摘要、SEO、分类和标签建议，并强调**只输出 JSON**（`response_format: json_object`）。
4. **RAG 问答**（90 秒）：在 `/ask` 提一个文章里有的问题，指出**答题是逐字流式出现的**（SSE），回答里带 `[1] [2]` 引用，下方显示参考文章；然后用历史记录面板展示私有会话。
5. **后台 RAG 设置**（30 秒）：展示 embedding 模型/维度、rerank 模型、历史保留天数档位；说明改 embedding 配置会触发全量重建并 fail-closed。
6. **系统页**（20 秒）：展示依赖健康探测（MySQL/Redis/Meilisearch/Qdrant/SMTP）与加密备份入口。

**卡壳预案**：
- 服务没起来 → 直接讲代码和设计，说「环境没起，我可以打开代码给你看关键实现」，比硬撑强。
- 答不上细节 → 「这块当时是这么考虑的……具体实现我需要翻一下代码」，然后真的打开文件。**面试官更在意你会不会查证，而不是背得全**。

## 七、诚实边界（这一节请务必读完）

1. **本文只写代码里真实存在的实现。** 凡代码没有的、或我没有验证过的，文中会写「未实现」「未验证」，不要把它们当成你的成果去讲。
2. **不要夸大**：不要说自己做过压测、上过生产、扛过多少 QPS——除非你真的做过。可以说「本地 Docker 环境验证过全链路」。
3. **AI 上游的真实行为**（如 DashScope 在极端并发下的表现、成本）本文只写代码中可确认的部分；线上未验证的一律标注。
4. **不要泄露**：文中只出现环境变量**名字**，绝不出现真实密钥、密码、域名、邮箱。演示时也注意别把 `.env` 投屏。
5. **被问「这是你独立写的吗」**：如实说明你的参与程度。这个项目的完整度足以支撑「我主导设计并实现了它」的讲述，但不要编造团队规模或上线数据。
