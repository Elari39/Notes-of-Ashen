## 本册速记卡

- **分层**：`handler`（只解析/鉴权/转发）→ `logic`（业务）→ `model`（SQL）；`svc` 负责依赖装配。
- **配置**：`etc/notes-of-ashen.yaml` 打底，`ApplyEnv()` 用环境变量覆盖；启动时强校验（拒绝空值、占位值、弱密钥）。
- **中间件链**：`RequestID` → 安全访问日志 → 维护模式 → 认证 → 限流/并发 → Handler。
- **统一响应**：`{"code":0,"message":"success","data":...}`。
- **两个主动关闭的框架默认**：go-zero 内置 access log（5xx 会转储含凭证的请求）和 MaxBytes（413 写法被 Nginx 误判 502）。
- **迁移**：28 个不可变编号迁移，用 `embed.FS` 内嵌进二进制，启动时校验状态。
- **优雅停机**：`defer` 是 LIFO，先 `server.Stop()` 处理完在途请求，再 `ctx.Close()` 关连接池。

## 主题：目录分层与职责边界

### ① 一句话答案

请求自上而下穿过 `handler` → `logic` → `model` 三层：Handler 只处理 HTTP，Logic 装业务规则，Model 装 SQL；`svc` 在启动时把数据库、Redis、缓存、Worker 这些依赖装配好交给各层。

### ② 展开讲 30–60 秒

| 目录 | 职责 | 不该做的事 |
| --- | --- | --- |
| `internal/handler` | 路由注册、请求解析、取鉴权上下文、调 logic、返回响应 | 写业务规则、直接写 SQL |
| `internal/logic` | 业务规则、事务编排、权限二次校验、缓存读写 | 解析 HTTP、拼响应体 |
| `model` | 数据访问：SQL、扫描、事务辅助 | 判断业务语义、返回 HTTP 错误 |
| `internal/svc` | 依赖装配与释放（`ServiceContext`） | 业务逻辑 |
| `internal/types` | 接口出入参结构 | 包含行为 |
| `internal/middleware` | 横切关注点：认证、限流、并发、日志、请求 ID、维护模式 | 业务逻辑 |
| `internal/response` / `internal/errors` | 统一响应与错误类型 | — |
| `internal/validation`、`internal/cache`、`internal/mq`、`internal/emailer`、`internal/search` 等 | 通用能力 | — |

**为什么 Handler 要保持轻量**：如果把业务写在 Handler 里，逻辑就只能通过 HTTP 触发，单元测试要起服务或者 mock `ResponseWriter`；抽到 logic 之后，测试可以直接调函数。而且同一份 logic 还能被后台任务（比如 RAG Worker、会话清理）复用。

### ③ 代码落点

- Handler 示例：`internal/handler/article/article.go`
- Logic 示例：`internal/logic/article/article.go`
- 依赖装配：`internal/svc/servicecontext.go`
- 请求辅助：`internal/httphelper/helper.go`

### ④ 可能的追问 + 应答

- **Q：为什么不用依赖注入框架？**
  A：Go 里显式构造比反射注入更清楚。`svc.NewServiceContext` 一个函数把所有依赖装配好，看一个文件就知道服务依赖什么。

- **Q：`model` 层为什么不返回业务错误？**
  A：保持单一职责。Model 只区分「找到了 / 没找到（`ErrNotFound`）/ 数据库出错」，至于「没找到」在业务上是 404 还是 403，由 logic 决定。

- **Q：`types` 包和 `model` 里的结构为什么要分开？**
  A：`model` 的结构对应数据库行，含内部字段（比如密码哈希、密文）；`types` 的结构对应接口出入参，是能对外暴露的字段。分开可以避免内部字段意外序列化给客户端。

### ⑤ 诚实边界

- `api/notes-of-ashen.api` 是接口契约描述文件，但**不是自动生成代码**的，改动时需要手写同步 handler/logic/types。这在效率上是取舍。

## 主题：改一个接口要动哪些文件（工程规范题）

### ① 一句话答案

至少同步四处：**接口契约**、**后端类型与实现**、**前端 API 封装与类型**、**文档**；涉及错误结构或权限变化时还要看统一响应与错误映射。

### ② 展开讲 30–60 秒

面试官问这个，考的是你有没有「接口是一份契约」的意识。我的联动清单是：

1. `api/notes-of-ashen.api` —— 契约描述
2. `internal/types` —— 出入参结构
3. 对应的 `handler` / `logic` / `model` —— 实现
4. `docs/API.md` —— 接口文档
5. 前端 `frontend/src/api/*.ts`、`frontend/src/types/*.ts` —— 调用与类型
6. 相关页面与 store
7. 如果改了错误结构：`internal/response`、`internal/errors`、前端 `frontend/src/utils/error.ts`

这条清单我写在了 `AGENTS.md` 里当成项目约定，因为**前后端类型漂移是最容易出的低级 bug**：后端加个字段忘了同步前端类型，TS 编译不会报错，但运行时是 `undefined`。

### ③ 代码落点

`AGENTS.md`（「接口联动清单」一节）、`api/notes-of-ashen.api`、`internal/types/types.go`、`docs/API.md`。

### ④ 可能的追问 + 应答

- **Q：怎么防止类型漂移？**
  A：现状是「约定 + 人工核对 + 文档同步」。更好的做法是从 `.api` 或 OpenAPI 自动生成前端类型，这是我知道但还没做的改进方向。**不要声称已经自动化了。**

- **Q：前端类型是怎么和后端对齐的？**
  A：`frontend/src/types/api.ts` 与 `types/index.ts` 手写对应后端字段，配合统一响应解包一起用。诚实说：目前靠人工同步。

### ⑤ 诚实边界

这是**流程性保障，不是技术保障**。没有代码生成、没有契约测试。

## 主题：配置系统

### ① 一句话答案

`etc/notes-of-ashen.yaml` 提供默认值，`Config.ApplyEnv()` 用 `APP_*` 环境变量覆盖，`.env` 文件只是本地开发的便利（真实环境变量优先级更高）；启动时做严格校验，不合格直接拒绝启动。

### ② 展开讲 30–60 秒

配置分几块：服务与超时、数据库、Redis、认证、搜索、RAG、RabbitMQ、邮件、媒体、备份、代理。

加载顺序是：

1. `conf.MustLoad` 读 YAML 拿到基础配置；
2. `config.LoadDotEnv(os.Getenv("APP_ENV_FILE"))` 加载 `.env`（如果存在），方便本地 `go run` 时不用手动 export；
3. `c.ApplyEnv()` 用环境变量覆盖——**真实环境变量赢过 `.env` 文件**；
4. `ValidateConfig()` + `ValidateOptionalDependencyProfiles()` 校验。

**校验为什么这么严**：因为它挡的是「部署时的低级错误」。比如 `.env` 里的占位符没替换、密钥太短、可选能力开关打开了但对应的 Compose profile 没开——这些如果不在启动时拦下来，就会变成运行期的诡异故障。

还有个细节：**迁移容器不能依赖 Redis 和认证密钥**。`-migrate-only` 分支里只读取数据库 DSN 就去跑迁移，原因是迁移任务只该依赖数据库；如果它还要求 Redis 可用或密钥合法，就可能因为无关配置把部署卡死。

### ③ 代码落点

- 配置结构与环境覆盖：`internal/config/config.go`
- `.env` 加载：`internal/config/dotenv.go`
- 启动流程与各诊断参数：`cmd/notes-of-ashen/main.go:37`、`:53`（migrate-only）、`:66`（public-site 校验）、`:75`（可选依赖校验）
- 默认配置：`etc/notes-of-ashen.yaml`
- 环境变量模板：`.env.example`

### ④ 可能的追问 + 应答

- **Q：为什么把 AI 的 API Key 放数据库而不是环境变量？**
  A：因为它需要**运行时由管理员在后台修改**，改完立即生效，不该要求重启进程。进程级配置放环境变量，运行时配置放数据库——这条边界我在 `AGENTS.md` 里写成了硬约束。

- **Q：`ApplyEnv` 里最麻烦的是什么？**
  A：可选布尔字段的语义。比如站点设置更新里的可选布尔字段用**指针**表示：字段缺失 = 保留当前值，显式 `false` = 关闭。如果不用指针，就区分不了「没传」和「传了 false」。

- **Q：为什么要有 `-validate-optional-dependencies-only` 这种一次性参数？**
  A：为了把「配置错误」在部署阶段暴露，而不是等 API 启动到一半失败。Compose 里它是个独立的 `config-check` 容器。

### ⑤ 诚实边界

- `.env.example` 里有几个预留变量（如 `APP_DISPLAY_NAME`）当前后端**并未读取**，只是文档记录。别说成已实现的功能。

## 主题：中间件链

### ① 一句话答案

全局先挂三层：`RequestID`（注入请求 ID）、安全访问日志（只记元数据）、维护模式（Redis 标记拦截写请求）；然后按路由再挂认证与限流/并发。

### ② 展开讲 30–60 秒

`RegisterHandlers` 里的注册顺序决定了执行顺序：

1. **`RequestID`**：给每个请求注入 `X-Request-Id` 并放进 context，所有错误日志都带它，排障时可以按一个 ID 把一条请求的日志串起来。
2. **安全访问日志**：项目自己实现的，**不记录查询串、Header、Cookie 和请求正文**，只记请求元数据。这是为了替代 go-zero 内置的访问日志。
3. **维护模式**：读 Redis 里的维护标记，维护期间拦截写请求。
4. **认证**（按路由）：普通受保护接口用 `authRequired`，注销这类「Access Token 过期也要能收尾」的接口用 `authOptional`。
5. **限流 / 并发**（按路由）：登录、注册、发验证码、找回密码、RAG 用的是 **fail-closed**；图形验证码、点赞、AI 辅助、流量上报用的是默认的 **fail-open**。

### ③ 代码落点

`internal/handler/routes.go:32`（RequestID）、`:34`（访问日志）、`:35`（维护模式）、`:36`（认证）、`:39` 起（各级限流）、`:51`（两个包装函数）。

### ④ 可能的追问 + 应答

- **Q：中间件顺序能随便换吗？**
  A：不能。`RequestID` 必须最先，否则日志里没有关联 ID；维护模式要在业务之前，否则维护期还写数据；认证要在限流之后还是之前取决于你的目的——我这里是认证在前（先确认身份），限流用的是 IP 维度，所以顺序影响不大，但**明确顺序能避免以后改错**。

- **Q：为什么认证和访问日志要分开？**
  A：职责不同，而且访问日志必须**在认证之前**执行才能记录到被认证拒绝的请求（这类请求恰恰是安全排查最关心的）。

### ⑤ 诚实边界

每层中间件的详细实现（尤其是维护模式的具体键与响应）本文未逐行展开，需要精确回答时请打开 `internal/middleware/` 对应文件。

## 主题：统一响应与错误处理

### ① 一句话答案

成功统一返回 `{"code":0,"message":"success","data":...}`，无数据时省略 `data`；失败用项目统一的错误类型，同时给出正确的 HTTP 状态码。

### ② 展开讲 30–60 秒

两套语义并存、各司其职：

| 层 | 表达什么 | 例子 |
| --- | --- | --- |
| HTTP 状态码 | 传输/通用语义 | 401 未认证、403 无权限、404 不存在、413 请求体过大、429 太频繁、503 服务不可用 |
| 响应体 `code` | 业务语义 | `0` 成功；非 0 表示具体业务错误 |

封装上我只用几个函数：`response.Ok`（带数据成功）、`response.NoData`（无数据成功）、`response.ErrorCtx`（带 context 的错误，便于日志关联）。错误类型集中在 `internal/errors`，比如 `BadRequest`、`Unauthorized`、`Forbidden`、`NotFound`、`TooManyRequests`、`ServiceUnavailable`。

**为什么错误必须显式处理**：这是我在项目约定里写的硬要求——Go 的 `err` 容易被忽略，一旦忽略，故障就会以「数据没写进去但接口返回成功」这种最难查的形式出现。所以宁可返回错误也不要静默吞掉。

### ③ 代码落点

`internal/response/response.go`、`internal/errors/errors.go`、`frontend/src/utils/error.ts`（前端映射）。

### ④ 可能的追问 + 应答

- **Q：为什么 `message` 用英文而前端显示中文？**
  A：后端 `message` 是稳定的机器可读标识，前端在 `error.ts` 里做「错误码/状态码 → 中文文案」的映射。这样后端不改文案也能调整前端措辞，也便于将来做多语言。

- **Q：错误信息会不会泄露内部细节？**
  A：会刻意避免。比如 AI 上游错误的正文可能回显请求内容（甚至密钥），所以只保留「安全摘要」（如 `upstream http status 429`），并把密钥替换成 `[REDACTED]`。

### ⑤ 诚实边界

错误码是一个**枚举式的集合**，我没有为每个业务错误定义唯一数字编号——部分场景只靠 HTTP 状态码 + message。严格来说这不够理想。

## 主题：请求体与参数防护（含一个「踩坑」故事）

### ① 一句话答案

请求体上限由各 Handler 的 `ParseLimited` / `MaxBytesReader` 统一管理，**并且关掉了 go-zero 内置的 MaxBytes 与 access log 中间件**。

### ② 展开讲 30–60 秒（这段很适合在面试里当「踩坑经历」讲）

go-zero 内置了两个中间件，我都主动关闭了，原因写在了 `main.go` 的注释里：

1. **内置访问日志（`Middlewares.Log = false`）**：它会在 5xx 时把**完整请求**转储到日志。问题在于请求里可能有认证凭证和 AI API Key。所以我关掉内置实现，换成项目自己的安全访问日志中间件——只记录元数据。

2. **内置请求体上限（`Middlewares.MaxBytes = false`）**：它在 `ContentLength` 超限时会**直接写 413 而不读取请求体**。这在直连场景没问题，但请求经过 Nginx 转发时，上游提前关闭连接会让 Nginx 把响应误判成 **502**（而不是 413）。后果是客户端看到的是「网关错误」，完全误导排查方向。

   我的处理是：把体积上限交给各 Handler 自己管（`ParseLimited` / `MaxBytesReader`），并且在返回响应前**把请求体排空**，让连接能正常复用、代理不会误判。

这个故事的价值在于：它体现的是「框架默认行为在真实部署链路（反向代理）下会失效」这类经验，而不是背 API。

### ③ 代码落点

`cmd/notes-of-ashen/main.go:83`（关闭 access log 的注释）、`:86`（关闭 MaxBytes 的注释）、`internal/httphelper/helper.go`（`ParseLimited`、`StandardJSONBodyLimit`、`SmallJSONBodyLimit`）、`internal/middleware/accesslog.go`。

### ④ 可能的追问 + 应答

- **Q：为什么「不读请求体」会导致 502？**
  A：因为连接被提前关闭时，Nginx 还没把请求体发完就发现上游断了。Nginx 对「上游提前断开」的默认处理是 502。要让代理看到真正的 413，必须在返回前把请求体读完（排空）。

- **Q：各个接口的上限是多少？**
  A：分档设置：普通 JSON 用 `StandardJSONBodyLimit`，小的用 `SmallJSONBodyLimit`，RAG 聊天请求单独设 16 KiB（`internal/handler/rag/rag.go:25`），媒体上传和备份恢复有自己的上限配置。具体数值以代码为准，别背数字。

### ⑤ 诚实边界

`docs/API.md` 里有一处关于「超过 6 MiB 返回 400」的表述和实际实现的 413 不一致（审查报告 O04 记录过）。被问到就说「文档与实现的这处不一致我已经记下来了，应该统一成 413」。

## 主题：数据访问层与连接池

### ① 一句话答案

所有 SQL 集中在 `model.Store` 里，连接池在 `Open` 时配置，并额外设置了空闲连接回收时间，避免远程 MySQL 场景下的「死连接」问题。

### ② 展开讲 30–60 秒

`model.Open` 做了这些事：

- 设置 `MaxOpenConns` / `MaxIdleConns`（来自配置，默认 20 / 10）；
- `SetConnMaxLifetime(1h)`；
- `SetConnMaxIdleTime(10m)` —— 这个值是有讲究的：默认 0 表示空闲连接永不回收，但云环境的安全组/NAT 常常在 5–10 分钟静默断掉空闲 TCP，连接池如果还留着这些死连接，下次请求就会拿到 `bad connection` / `EOF` / `i/o timeout`。设 10 分钟比常见空闲超时短，又不至于频繁重建连接。
- 启动时 `Ping`，并且**失败时做一次 MySQL 握手探测**：如果 TCP 能连上但对方不发 MySQL 握手包，就明确提示「可能端口填错了 / 被防火墙或代理拦了」，而不是只丢一个 `connection refused`。

事务用 `model.WithTx` 这个辅助函数：函数返回错误就回滚；**`Commit` 失败时也回滚**，因为此时事务状态未定，不能让业务误以为写入成功。

另外，`AffectedRows` 会被显式校验——更新语句影响 0 行通常意味着「目标记录不存在或状态已变」，这属于业务失败，不是成功。

### ③ 代码落点

`model/db.go:29`（Open 与连接池）、`:40`、`:45`（空闲回收）、`:46`（Ping）、`:113`（握手探测）、`:197`（WithTx）。

### ④ 可能的追问 + 应答

- **Q：`MaxOpenConns` 设 20 会不会太小？**
  A：看场景。单机个人站 + 有几个长连接（SSE）会被占用，20 够用而且能避免把数据库打满。这是「连接池是保护数据库的手段，不是越大越好」的体现。

- **Q：为什么不用 ORM？**
  A：想要完全控制 SQL。这个项目里有不少「带条件的动态列表查询」和「一次性批量查询避免 N+1」的场景，手写 SQL 更直接，也便于加索引优化。取舍是写起来啰嗦。

- **Q：N+1 怎么处理的？**
  A：批量接口（比如文章列表要带标签）走批量查询再在内存里聚合，而不是每篇文章查一次标签。

### ⑤ 诚实边界

连接池参数是经验值，**没有做过压测调优**。别声称做过性能调优。

## 主题：数据库迁移

### ① 一句话答案

28 个编号迁移文件用 `embed.FS` 内嵌进二进制，启动（或独立任务）时按序执行；**已发布的迁移不可修改，只能新增前向迁移**；启动时还会校验「数据库里的迁移版本是不是当前镜像认识的」。

### ② 展开讲 30–60 秒

几个关键设计：

1. **不可变编号**：`000001_initial_schema.sql` 到 `000028_rag_embedding_dimensions_default.sql`。一旦某个迁移在环境上跑过，就不能再改它的内容——因为改了对已经跑过的环境没有效果，只会让环境之间产生结构差异。要修复只能加新的前向迁移。
2. **内嵌进二进制**：用 Go 的 `embed.FS`，所以部署时不需要额外分发 SQL 文件，二进制自带 schema 定义。
3. **独立迁移任务**：Compose 里 `migrate` 是单独的一次性容器（`-migrate-only`），API 等它成功退出才启动。这样多副本 API 不会竞争执行 DDL。
4. **状态校验**：`validateState` 会检查数据库里是否已应用了「当前镜像不认识」的迁移版本——这通常意味着「你把新版本回滚成旧镜像了，但数据库结构还是新的」。这种情况必须明确报错，而不是继续运行。
5. **诊断参数**：`-migration-version` 打印镜像内最高迁移版本，`-schema-version` 打印数据库已应用的最高版本，方便对比。

大部分迁移是加表和加索引，也有一批**专门做索引优化**的（比如全文索引、操作日志的筛选索引、下拉令牌的清理索引），还有几个是数据修复类的（如清理孤立的文章版本、清理无效头像地址）。

### ③ 代码落点

`internal/migration/migration.go`、`deploy/mysql/migrations/embed.go`、`deploy/mysql/migrations/000001_initial_schema.sql` 起、`cmd/notes-of-ashen/main.go:39`（版本参数）、`:116`（`runMigrations`）、`docker-compose.yml:135`（migrate 服务）。

### ④ 可能的追问 + 应答

- **Q：为什么不用 golang-migrate / goose？**
  A：自己实现的核心是「内嵌 + 状态校验 + 只前向」这三点，代码量不大；而且我想完全控制错误提示与版本比较。取舍是少了成熟工具的高级功能（比如 dirty 状态修复工具）。

- **Q：迁移失败会怎样？**
  A：migrate 容器以非零退出，Compose 不会启动 API（`service_completed_successfully`），并且保留容器日志供排查。**这是「失败就开始不了」而不是「带着半截结构跑」。**

- **Q：加了索引的迁移怎么保证不锁表太久？**
  A：这是我知道的**改进方向**。MySQL 8 的 InnoDB 加二级索引通常支持在线 DDL，但项目里没有显式写 `ALGORITHM=INPLACE, LOCK=NONE`，大表上应该显式声明并评估。

### ⑤ 诚实边界

- 迁移里包含数据修复语句（`UPDATE`/`DELETE`），我在本地环境验证过；**没有在真实大数据量上评估过执行时长**。
- 表的完整清单与字段请查 `deploy/mysql/migrations/*.sql`，不要凭记忆答字段名。

## 主题：缓存策略

### ① 一句话答案

缓存集中在几处：站点设置、文章列表、认证用的用户快照；缓存层故障时**降级直查数据库**，不把缓存变成一个新增的故障点。

### ② 展开讲 30–60 秒

缓存的取舍原则是「**只缓存读多写少、且不一致代价可接受的数据**」：

- **站点设置**：读得极其频繁（每个页面都要读），改动很少，适合缓存 + 更新时失效。
- **文章列表**：公开列表是读热点，更新文章时失效。
- **认证用户快照**：这里最典型——认证中间件每个 Bearer 请求都需要知道用户的 `role` 和 `status`，如果每次都查库，压力很大。所以缓存 30 秒，**而且只缓存这两个最小字段**，绝不把 `PasswordHash` 之类写进缓存。

关键设计是**缓存的失败语义**：缓存是优化，不是依赖。缓存未命中或 Redis 不可用就直查数据库，绝不因为缓存故障返回 500。

### ③ 代码落点

`internal/cache/cache.go`、`internal/logic/article/cache.go`、`internal/logic/site/cache.go`、`internal/logic/admin/cache.go`、`internal/middleware/auth.go:25`（缓存抽象）、`:40`（30 秒 TTL）、`:149`（未命中降级）、`:171`（`EvictAuthUserCache`）。

### ④ 可能的追问 + 应答

- **Q：缓存和数据库不一致怎么办？**
  A：写操作后主动失效（比如改角色后 `EvictAuthUserCache`），而不是等 TTL 过期。TTL 只作为兜底。

- **Q：30 秒 TTL 会不会导致权限变更延迟生效？**
  A：会有最多 30 秒的窗口，所以我在改变鉴权语义的操作（禁用/启用用户、改角色、改密码）里**显式删除缓存**，TTL 只是兜底。更严格的做法是让缓存版本号参与鉴权判断。

- **Q：为什么不用 Redis 做分布式锁？**
  A：RAG 索引重建那里确实用了**租约（lease）**——它比锁更适合这个场景，因为租约自带过期和续租，进程崩溃后不会永久死锁。这部分在 `05` 和 `03` 里讲。

### ⑤ 诚实边界

缓存的具体键设计与失效时机需要精确回答时请打开对应 `cache.go`；本文只讲原则。

## 主题：异步操作日志与降级

### ① 一句话答案

写操作产生的事件投递到 RabbitMQ，由消费者写入 `operation_logs` 表；MQ 关闭时这条链路整体降级，不影响主流程。

### ② 展开讲 30–60 秒

**为什么异步**：操作日志是「顺手记录」的需求，不应该让用户的写请求卡在日志落库上。所以请求路径里只做「投递事件」，落库交给消费者。

拓扑是标准的 exchange / queue / routing key：

- exchange：`notes-of-ashen.events`
- queue：`notes-of-ashen.operation_logs`
- routing key：`operation.log`

默认值都在 `etc/notes-of-ashen.yaml` 里，也可用 `APP_RABBITMQ_*` 覆盖。

**降级**：RabbitMQ 是可选能力，`APP_RABBITMQ_ENABLED=false` 时不会去连它（Compose 里它也需要 `COMPOSE_PROFILES=messaging` 才启动）。此时操作日志链路不可用，但**文章发布、登录等核心功能完全不受影响**——这就是「可选能力不能拖垮主流程」的具体体现。

### ③ 代码落点

`internal/mq/event.go`、`internal/config/config.go`（RabbitMQ 配置分区）、`etc/notes-of-ashen.yaml:54`、`docker-compose.yml:311`（rabbitmq 服务与 profile）。

### ④ 可能的追问 + 应答

- **Q：投递失败怎么办？会不会丢日志？**
  A：会有丢失风险——当前实现没有做本地持久化重投或 outbox。**这是个可以改进的点**：更稳的做法是把事件先写进数据库的 outbox 表，再由后台任务投递，这和 RAG 索引同步用的思路是一样的（RAG 那边我确实用了 MySQL outbox，日志这边没有）。

- **Q：为什么 queue 和 exchange 名字里带项目名？**
  A：避免和同一个 RabbitMQ 实例上的其他应用冲突。

### ⑤ 诚实边界

**操作日志投递没有 outbox 保障，可能丢事件。** 被问到要如实说，并给出改进方向。

## 主题：优雅停机与启动恢复

### ① 一句话答案

`defer` 是后进先出，所以先注册「关闭依赖」再注册「停止服务」，实际执行时先停服务（处理完在途请求）再关连接池；启动时还有一步「恢复上次中断的操作」。

### ② 展开讲 30–60 秒

`main.go` 里的顺序是精心安排的：

```go
ctx := svc.NewServiceContext(c)
defer ctx.Close()      // 先注册 → 最后执行
defer server.Stop()    // 后注册 → 先执行
```

因为 `defer` 是 LIFO（后进先出），所以实际执行顺序是 `server.Stop()` 在前、`ctx.Close()` 在后。含义是：**先停止接受新请求并等待在途请求处理完，再关闭数据库/Redis/MQ 连接池**。如果反了，正在处理的请求会突然拿不到数据库连接，用户看到的就是随机的 500。

启动时还有两件「收敛」工作：

1. **`recoverPendingRestore`**：如果上一次进程在「整站恢复」中途异常退出，这次启动要判断该提交还是回滚。它先尝试获取恢复租约——如果租约被另一个实例持有，说明那边可能还在写暂存目录，**这时不能去清理**，只记录日志并跳过；否则按数据库里的恢复标记决定「完成媒体发布」或「丢弃未提交的暂存目录」。
2. **生产站点地址校验**：开了 `APP_REQUIRE_PUBLIC_SITE_URL` 时，启动前要求数据库里的 `siteBaseUrl` 是合法的 HTTPS 地址。

### ③ 代码落点

`cmd/notes-of-ashen/main.go:90`（服务器创建）、`:92`、`:99`（恢复）、`:100`（两个 defer 的顺序与注释）、`:104`（注册路由）、`:107`（启动）。

### ④ 可能的追问 + 应答

- **Q：为什么恢复要判断租约，而不是直接清理？**
  A：因为**多实例**场景。租约被别的实例持有时，它可能正在写暂存目录；此时清理会破坏它的数据。所以「不能确定安全时就不做」，等它自己完成或超时。

- **Q：`server.Stop()` 会等多久？**
  A：它会等待在途请求完成；配合服务超时配置（`APP_TIMEOUT`）和容器停止信号，避免无限等待。

### ⑤ 诚实边界

「处理完在途请求」的具体等待时长与超时行为本文没有逐行核对，需要精确回答时看 go-zero `rest.Server.Stop` 的行为与项目超时配置。

## 主题：可维护性约定与测试

### ① 一句话答案

约定是：最小必要改动、优先复用、不新增占位实现、错误必须处理、改动要能验证；测试分三层——单元测试、`sqlmock`、真实集成测试。

### ② 展开讲 30–60 秒

**代码约定**（写在 `AGENTS.md` 里）：

- 先读代码再改，最小必要改动，不做无关重构；
- 错误不忽略；不引入无必要依赖；
- 注释解释**「为什么」而不是「做了什么」**——仓库里大量注释是这个风格。举两个例子：
  - `internal/middleware/ratelimit.go:27`：解释为什么日志/验证码/注册接口要 fail-closed——「避免 Redis 故障下被绕过限流」。
  - `internal/middleware/concurrency.go:57`：解释为什么并发槽位不能用单纯计数器——「长于 TTL 的旧请求若在计数器过期后结束，会错误地释放后来请求的槽位」。

**测试分三层**：

| 层 | 用什么 | 验证什么 |
| --- | --- | --- |
| 单元测试 | `go test` | 纯逻辑、策略函数、解析器（如分块、提示词、校验器） |
| 数据库单测 | `sqlmock` | SQL 语句与扫描逻辑，不需要真实 MySQL |
| 真实集成测试 | `scripts/test-integration.ps1` 起真 Compose | 黑盒 HTTP 全链路、迁移、并发、故障注入、浏览器 E2E |

**为什么要有真实集成测试**：因为单测覆盖不了「配置 + 迁移 + Nginx + 真实数据库」的组合问题。比如「首次注册成为管理员」「令牌轮换」「历史 schema 自动迁移」这些只有在真实环境才测得出来。

### ③ 代码落点

`AGENTS.md`、`internal/**/*_test.go`、`model/*_sqlmock_test.go`、`test/integration/http_integration_test.go`、`scripts/test-integration.ps1`、`docs/TESTING.md`。

### ④ 可能的追问 + 应答

- **Q：测试覆盖率多少？**
  A：**我没有统计过覆盖率百分比，不要编数字。** 可以说「核心的业务逻辑、限流、认证、备份校验都有对应测试；前端有 101 项单测（数字来自审查报告），后端单测 + 集成测试分两层」。

- **Q：哪些地方故意不测？**
  A：需要真实外部服务的路径（真实 SMTP、真实生产 HTTPS、异地备份恢复、跨主机回滚）没有自动化测试，靠本地手动验证。这类要么成本高、要么会改数据，我有意识没纳入 CI。

- **Q：集成测试会不会污染开发数据？**
  A：不会。脚本为每个阶段生成全新的 Compose 项目名、独立卷、随机数据库/认证凭据、随机端口，结束时 `down --volumes --remove-orphans` 清掉；失败时保留的是**不含临时环境文件**的日志。

### ⑤ 诚实边界

- 覆盖率数字未统计。
- 并发与故障注入测试覆盖了部分场景（并发迁移、Redis 认证失败、恢复失败注入），但**不是全场景并发验证**；审查报告里也明确标注了三项「尚未在线复现」的静态风险（S01–S03）。

## 可能被问倒的 3 个问题

1. **「go-zero 到底帮你做了什么？如果换 Gin 你要多写多少？」**
   → 应答思路：帮我省掉的是 `rest.Server` 的路由与中间件机制、`conf` 配置加载（含 YAML + 结构体校验）、`logx` 日志、内置 Prometheus 指标端点。换 Gin 的话这些要自己接：配置加载与校验、日志与错误聚合、指标暴露。但也要诚实说：我因为安全原因**关掉了它两个内置中间件**，所以并不是全盘接受框架默认。

2. **「你怎么保证一个接口改动不会漏改前端？」**
   → 应答思路：靠一份显式的联动清单（`.api` 契约 → `internal/types` → handler/logic/model → `docs/API.md` → 前端 api/types/页面 → 错误映射），写在项目约定里。**但这是流程保障不是技术保障**，真正的解法是从契约自动生成前端类型，这是我已知的改进方向。

3. **「如果线上突然大量 500，你怎么排查？」**
   → 应答思路：先看 `/healthz`（整体就绪）和后台的系统健康页（依赖明细：MySQL/Redis/Meilisearch/RabbitMQ/SMTP/媒体/备份 schema）。然后用 `X-Request-Id` 把一条具体请求的日志串起来——这是我在中间件链最前面注入它的原因。访问日志**不含查询串、Header、Cookie 和正文**是有意的，所以敏感信息不会进日志，但排障时需要结合业务日志。
